01 · the problem

A free path to the goal

Every mobile robot faces the same first question: how do I get over there? The goal is a place; the world between here and there is full of walls, furniture, people, and things the map didn’t mention. The straight line is almost always blocked.

So navigation is the search for a collision-free path — a continuous route through the empty space to the goal. What makes it hard isn’t drawing the line; it’s that the robot only partly knows the world, the world moves, and whatever path it picks has to be one the robot’s body can actually follow.

the actual math — one level deeper

Split the robot’s configuration space C into free space C_free and obstacles C_obs. A path is a continuous curve τ:[0,1]→C_free with τ(0)=start, τ(1)=goal.

Partial and changing knowledge means C_obs is only estimated from sensors — so planning and re-planning interleave as the estimate updates.

02 · plan it

Two ways to find a path

Given the free space, how do you actually find a route through it? One answer is to sample: scatter random points, keep the ones that don’t hit anything, and connect them into a growing tree until a branch reaches the goal. Try enough points and you’ll find a path if one exists.

The other answer is to optimize: start from a rough guess — even a bad one — and repeatedly nudge it to lower a cost that rewards short, smooth, obstacle-free motion. One explores by trying many motions; the other refines a single one until it fits. Most real systems use both.

the actual math — one level deeper

Sampling (RRT): draw a random q, steer the nearest tree node toward it, keep the edge if collision-free; probabilistically complete — finds a path if one exists, given enough samples.

Optimization: minτ ∫ cost(τ,τ̇) dt subject to dynamics and collision constraints; solved with iLQR/MPC-style updates from an initial guess.

03 · the stack

A map to plan on, a loop to dodge

In practice a robot runs two loops at once. The global planner works on a stored map — usually an occupancy grid marking free and blocked cells, with a cost that pushes paths away from walls — and finds a route all the way to the goal.

But the map is always a little out of date, so a fast local planner runs many times a second on the live sensor feed, choosing immediate motions that follow the global route and dodge whatever just appeared. Plan globally on what you know; react locally to what you see.

the actual math — one level deeper

Global: run A* / Dijkstra over the costmap grid c(x) to get a least-cost route to the goal.

Local: each cycle pick controls (v,ω) minimizing distance-to-path + a collision penalty over a short horizon (DWA / MPC) — a fast reactive loop under the slow global one.

04 · the world moves

Navigating among people

Static obstacles stay put; people don’t. Navigating a crowd means the robot must predict where each person is heading over the next few seconds and thread a path through the gaps that will exist, not the ones that exist now.

This is genuinely hard because prediction is uncertain, and if the robot assumes the worst about everyone, the predicted futures blanket every open direction — so the only ‘safe’ move is to stop. That’s the notorious freezing-robot problem: over-caution is its own failure, and good crowd navigation is really good prediction.

the actual math — one level deeper

Predict each agent’s future distribution p(x_t) and treat it as a time-varying obstacle; plan a path that keeps collision probability below a threshold.

Freezing: if predicted occupancy fills the free space, no feasible low-risk path remains — the fix is joint / interaction-aware prediction, not more caution.

05 · learn it

From pixels, and from words

The newest strand skips the explicit pipeline. A network takes the raw view and a goal — a target image, an object name, or a plain-language instruction — and outputs the next move directly, learning from demonstrations or from reward in simulation.

This is what lets a robot follow ‘go past the kitchen and stop at the second door’ in a building it has never seen, with no map handed over. It leans on the same web-pretrained vision-language models as the rest of the field — and inherits their strength (broad generalization) and their weakness (shaky precise geometry).

the actual math — one level deeper

Learn a policy πθ(a | obs, goal) by imitation or RL; goal is an image, an object class, or language tokens.

Vision-and-language navigation grounds instruction tokens against the visual stream step by step, emitting move / turn / stop until it reports done.

The benefits people actually get

01

Sampling-based motion planning (RRT / PRM)

robotics
the problem

The robot needs to get from one configuration to another without hitting anything, but the free space is complicated: high-dimensional, full of narrow passages, and impossible to enumerate. You can’t simply enumerate all paths or hand-draw one in 7-DOF arm space.

the approaches

The classical backbone: scatter random collision-free configurations and connect nearby ones into a graph or tree, then read off a path. It handles high-dimensional spaces and odd kinematics where hand-drawing a route is hopeless.

Recent work speeds convergence, improves path quality, and pushes sampling onto needles, AUVs, and nonholonomic vehicles.

worked example — one concrete run
  1. Start with one node: the robot’s current configuration (7 joint angles). Goal node: the target pose.
  2. Sample a random configuration q_rand in the 7-DOF joint space — uniformly at first, then biased toward the goal with probability 0.05 to keep progress.
  3. Find the nearest node in the current tree (Euclidean distance in joint space). Steer toward q_rand by stepping 0.2 rad per joint at most.
  4. Check the new edge for collision by querying the forward kinematics at 10 interpolated configurations. If any link overlaps an obstacle, discard.
  5. Add the collision-free node and edge to the tree. After ~2,000 samples, a branch reaches within 0.1 rad of goal — declare success and read off the path.
  6. Post-process: shortcut the path by trying to directly connect non-adjacent nodes, cutting a 42-step path to ~18 straight moves.

Trajectory optimization & MPC

robotics
the problem

A sampling planner finds a path, but that path is jagged and ignores the robot’s actual dynamics — a drone can’t snap to arbitrary headings or stop instantly. You need a path the body can truly execute, and then you need to re-solve it every few milliseconds as the world changes.

the approaches

Instead of sampling, write down a cost — short, smooth, energy-cheap, clear of obstacles — and minimize it subject to the robot’s dynamics. Model-predictive control re-solves it every cycle so the plan tracks a changing world.

The work is speed (these solves are heavy), good initialization to dodge local minima, and differentiable planning fused with learning.

worked example — one concrete run
  1. Start with a straight-line guess from start to goal: 20 waypoints uniformly spaced, ignoring every obstacle.
  2. Compute the cost: sum of squared jerk (for smoothness) + 1000 × max(0, −d_obs) for each waypoint that penetrates an obstacle (d_obs = signed distance to nearest obstacle).
  3. Gradient step: compute ∇cost for all waypoint positions and step them by lr=0.05. Obstacle-penetrating waypoints shoot outward; jagged waypoints smooth toward their neighbors.
  4. After 50 iterations the path wraps cleanly around the obstacle and the cost drops from ~840 to ~12.
  5. MPC re-solve every 50 ms: freeze the first control, advance one step, warm-start the next solve with the tail of the previous solution — the plan always looks 2 s ahead.
  6. At 10 Hz re-solve rate, the drone tracks a moving target or dodges a suddenly-closing door without replanning from scratch.
  • ROBOShadow Program Inversion with Differentiable Planning — unifies program-parameter and trajectory optimization, differentiably
  • ROBOReal-Time Whole-Body Control of Legged Robots with Model-Predictive Path Integral Control — MPPI samples trajectories in parallel for real-time control
  • ROBOHigh Accuracy Aerial Maneuvers via Variational Integrator Discretized Trajectory Optimization — structure-preserving discretization for accurate aerial trajectories
  • ROBOTime-Optimal Trajectory Generation with Multi-level Continuous Kinodynamics Constraints — time-optimal trajectories under layered kinodynamic limits

Safe navigation & collision avoidance

robotics
the problem

Good average behavior isn’t enough: a single collision is a failure. You need a formal certificate that the robot will never enter an obstacle — but the tighter you draw the safety margin, the more of the free space you rule out, until cluttered corridors become impassable.

the approaches

Layer a safety filter over any planner: monitor distance to obstacles and forbid controls that could lead to a collision. Control-barrier functions and reachability analysis give formal guarantees, not just good behavior on average.

The tension is conservatism — guarantees need margins, and too-large margins make cluttered spaces impassable.

worked example — one concrete run
  1. Define the safety set h(x) = d(x, obstacle) − r_safe, where r_safe = 0.3 m. The robot is safe as long as h(x) ≥ 0.
  2. The CBF condition: the chosen control u must satisfy ˙h(x,u) + αh(x) ≥ 0. With α=2, this means ‘the safety margin must be improving (or at least not shrinking too fast).’
  3. Nominal planner proposes u_nom (move straight toward goal at 0.5 m/s). Check: does it satisfy the CBF constraint?
  4. If not, solve a small QP each 10 ms: find u* closest to u_nom that does satisfy it. The QP has 2 variables and 1 constraint — it solves in <0.1 ms.
  5. The corrected u* curves the robot away just enough to keep h ≥ 0, without stopping or replanning.
  6. Formal guarantee: if h(x_0) ≥ 0 at the start and the QP is always feasible, h never goes negative — the robot never hits the obstacle, provably.

  • ROBOVision Transformers for End-to-End Vision-Based Quadrotor Obstacle Avoidance — learned high-speed obstacle dodging from images
  • ROBOSafety-Critical Control for Aerial Physical Interaction in Uncertain Environment — safety-critical control under model uncertainty
  • ROBOSAFE-GIL: SAFEty Guided Imitation Learning for Robotic Systems — injects safety guidance into imitation learning

Learned & end-to-end navigation

both
the problem

Classical pipelines hand-specify every sub-problem: map it, plan on it, control toward it. But the real world is too messy for every rule to be written down — narrow gaps, dark corridors, and texture-less walls break hand-specified detectors and cost functions one by one.

the approaches

Train a network to map observations straight to motion — from demonstrations or from reward in simulation — skipping the explicit map-plan-execute pipeline. It captures intuitive, human-like navigation that’s hard to hand-specify.

The open issues are the usual ones for learning: data hunger, distribution shift, and hard-to-certify safety.

worked example — one concrete run
  1. Collect 50 hours of human teleoperation through a building, recording (RGB image, velocity command) pairs at 10 Hz — 1.8 million training pairs.
  2. Train a ResNet-50 + GRU to predict (v, ω) from 4 stacked frames. Loss = MSE on both outputs; train for 80 epochs on 4 GPUs.
  3. At inference the network reads the current 4 frames and emits a velocity command 30 ms later — the entire map-plan-control stack collapsed to one forward pass.
  4. Where it works: the training corridors, lighting conditions, and obstacle types it saw. Success rate: 87% door-to-door in the training building.
  5. Where it breaks: a new building with different wall colors — success drops to 41%. A residual RL fine-tune on 2 hours of real experience recovers to 79%.
  6. The irreducible tension: no network output comes with a safety proof. Add a reactive collision-stop layer that halts if any depth reading < 0.4 m to keep deployment safe.
  • ROBOFrom Imitation to Refinement — Residual RL for Precise Assembly — residual RL sharpens an imitation-learned policy
  • CVPRExtending Embodied Question Answering from Perception to Decision — a four-stage agent from scene understanding to instant decision
  • CVPROctoNav: Towards Generalist Embodied Navigation — one agent for point/object/image/instruction goals, think-before-action
  • ROBOValidity Learning on Failures: Mitigating Distribution Shift in AV Planning — learns from failure cases to fight distribution shift

Vision-and-language navigation (VLN)

both
the problem

The robot is given a sentence — ‘walk past the plant, turn left at the painting, stop at the second door’ — and must ground each phrase against what the camera actually shows, in a building it has never seen. Each word is a constraint on the next step, and the constraints can be vague or ambiguous.

the approaches

Follow a natural-language route — ‘turn left at the plant, stop by the window’ — by grounding each phrase against the live view and deciding the next step. The core problem is bridging fuzzy language and precise geometry.

Recent systems add self-aware reasoning, fast-slow control, and hierarchical waypoints to survive new buildings and instruction styles.

worked example — one concrete run
  1. Tokenize the instruction into 14 tokens. Encode the current panoramic view (12 heading × 30° patches) into 12 visual tokens with a ViT.
  2. Cross-attend the visual tokens against the instruction tokens: the phrase ‘turn left at the plant’ attends most strongly to the image patch that contains a green blob at the left-front heading.
  3. Score all navigable headings (the discrete R2R action space): score(h) = dot(lang_feat, view_feat_h). Pick the heading with the highest score — here, 285° (left-front).
  4. Move there. Update the progress pointer: ‘past the plant’ is done; now attend to ‘turn left at the painting.’
  5. Waypoint 4 of 8: the cross-attention score for the painting-patch jumps to 0.91; the robot turns left.
  6. Stop criterion: when the stop action scores highest across all headings (the ‘door 2’ phrase has been matched and no further instruction remains), the agent declares done. Success rate on R2R val-unseen: 72%.

  • CVPRGeneral VLN via Fast-Slow Interactive Reasoning — a fast action policy plus slow LLM reflection
  • CVPRBridging the 2D-3D Gap: Hierarchical Semantic-Geometric Map for VLN — a map that links VLM semantics to 3D geometry
  • ROBOLanguage-Guided Object Search in Agricultural Environments — language-directed search over an outdoor farm

Object-goal & image-goal navigation

vision
the problem

The goal isn’t coordinates but a thing: find the fridge, or reach the place shown in this photo. The robot has no map and must explore an unknown space, searching intelligently rather than exhaustively, and recognize when it has arrived — the ‘last-mile viewpoint’ problem.

the approaches

The goal isn’t coordinates but a thing: find the fridge, or reach the place shown in this photo. The robot must explore an unknown space and recognize when it has arrived — the ‘last-mile’ viewpoint problem.

Generative sub-goals, 3D scene graphs, and frontier value maps drive smarter exploration toward the target.

worked example — one concrete run
  1. Goal: find the fridge. The robot starts in a living room with no map.
  2. Encode the goal with a CLIP text embedding e_goal = CLIP(“fridge”). Encode the current view: e_view = CLIP(camera_image).
  3. Compute a frontier value map: score each unexplored frontier cell f by cos(e_goal, CLIP(top-down semantic of nearby region f)). The kitchen frontier scores 0.68; bedroom frontier: 0.23. Move toward the highest-scoring frontier.
  4. After 11 steps the robot enters the kitchen. CLIP similarity between camera and “fridge” now spikes to 0.81. Stop exploring — found it.
  5. Last-mile: the fridge is partly occluded. Generate a sub-goal image (inpaint the canonical frontal view) and navigate to viewpoint that maximizes pixel similarity to it.
  6. Success rate on ObjectNav HM3D: 61% on seen categories, 43% on unseen — the gap is the distribution-shift problem.

Semantic mapping & open-vocabulary maps

both
the problem

An occupancy grid tells the robot what cells are blocked, but not what anything is. When asked to find ‘the sink’ or ‘somewhere comfortable to sit,’ it has no answer — and you cannot pre-label every object, because you cannot know in advance what the robot will be asked to find.

the approaches

Build a map that stores meaning, not just occupancy: language-aligned features at each place, so the robot can later be asked for ‘the sink’ or any object never labelled in advance. This is where navigation meets open-vocabulary perception.

Selective queries and instance-level fields keep it real-time on the robot.

worked example — one concrete run
  1. As the robot explores, every incoming RGB-D frame is run through a CLIP image encoder at 5 Hz. Each pixel’s CLIP feature (512-d) is projected into the map at the corresponding 3D voxel.
  2. Features accumulate: voxels seen from multiple viewpoints average their CLIP vectors, making the embedding more stable.
  3. Query arrives: ‘coffee mug.’ Encode it: e_query = CLIP(“coffee mug”). Compute cosine similarity to every voxel’s feature.
  4. Top-5 voxels cluster on the kitchen counter at (2.3, 4.1, 0.9) m. The planner targets that location.
  5. Compression: 512-d vectors on millions of voxels is ~2 GB for a 200 m² apartment. Compress with PCA to 32-d → 128 MB with <4% retrieval accuracy drop.
  6. Open-vocabulary payoff: the robot finds ‘fire extinguisher’ correctly at inference time — a category never seen during training.

  • CVPROVI-MAP: Open-Vocabulary Instance-Semantic Mapping — decoupled instance geometry + selective VLM semantic queries
  • CVPROv3R: Open-Vocabulary Semantic 3D Reconstruction from RGB Videos — instance-level open-vocab reconstruction from video

Topological & scene-graph navigation

both
the problem

Dense metric maps are heavy and brittle: a moved chair can invalidate meters of cost-map, and planning over a 200 m² grid is slow. People navigate buildings by thinking in rooms and doorways, not centimeter cells. The challenge is formalizing that coarse structure without losing enough geometry to plan useful paths.

the approaches

Drop the dense grid for a graph of places and connections — rooms as nodes, doorways as edges. Planning becomes cheap graph search, resilient to small geometry changes, and it maps naturally onto how people give directions.

Hierarchical and dynamic scene graphs scale this to whole buildings and moving objects.

worked example — one concrete run
  1. During exploration, detect room boundaries with a room-classifier (CNN on the panoramic scan). Each detected room becomes a node: {id, centroid, semantic label}.
  2. Connect adjacent rooms with an edge when a doorway is detected: each edge stores (door_width, direction, traversal_cost). A 12-node graph covers a whole floor.
  3. Query: navigate from ‘office’ to ‘kitchen’. Run Dijkstra on the graph: 3-hop path, total cost 18.4 (weighted by door widths and distances).
  4. Execute hop 1: inside the office, switch to a local metric planner to reach the detected doorway at (3.1, 7.2) m.
  5. A chair is moved, blocking the corridor. The topological path is unchanged; only the local metric hop re-plans around the new obstacle. No global re-planning.
  6. Add objects as leaf nodes (the coffee machine is a child of ‘kitchen’). A query for ‘coffee machine’ resolves to the kitchen node in one graph lookup.

  • ROBOKey-Scan-Based Mobile Robot Navigation via Graphs of Scan Regions — integrated mapping/planning/control over scan-region graphs

Social & human-aware navigation

robotics
the problem

Moving among people is a different problem from moving around furniture: people predict you, react to you, and have expectations about personal space and intent. Treat them as moving obstacles and the robot either freezes (every direction looks blocked) or cuts through personal space in a way that feels aggressive.

the approaches

Move through people politely and safely: predict their trajectories, respect personal space, and signal intent — without freezing when the crowd is dense.

The frontier is interaction-aware prediction (people react to the robot too) and future-aware planning.

worked example — one concrete run
  1. At time t=0, the robot tracks 4 pedestrians with a social-force model. Each person’s predicted position at t+2 s is a Gaussian: mean at extrapolated velocity, covariance from uncertainty.
  2. Inflate each prediction into a time-varying cost region: cost(x,t) = exp(−½ d(x,μ_ped(t))² / (2σ²)) × social_weight (higher inside 1.2 m personal space).
  3. Plan a path minimizing ∫ (distance_to_goal + social_cost) dt over a 3 s horizon with MPC.
  4. The robot passes behind pedestrian 2 (the gap opens at t=1.4 s) rather than crossing in front.
  5. Interaction feedback: pedestrian 3 sees the robot and slows down. Update their predicted mean velocity from 1.2 to 0.6 m/s and re-plan in 50 ms.
  6. Freezing-robot fix: if every path costs >10 (crowd too dense), shrink the social_weight by 0.7 and re-plan — prefer a mildly uncomfortable pass over stopping forever.

Off-road & terrain-aware navigation

robotics
the problem

On pavement, the cost of each cell is binary — blocked or free. On a trail, sand slows you, steep slopes can tip you over, and loose rock can kill a wheel. The terrain cost is a continuous scalar the robot must estimate from vision and touch, for ground it may never have crossed before.

the approaches

Off the paved path, the question isn’t just ‘is it free?’ but ‘can I traverse it?’ — mud, sand, slopes, and rubble each carry a cost the robot must estimate from vision and feel.

Learned traversability and VLM commonsense increasingly judge terrain the robot has never seen.

worked example — one concrete run
  1. Build a cost map from the front camera: run each image patch through a CNN trained on <speed, slip> telemetry from past traversals. Output: traversability score c(x,y) ∈ [0,1] per 0.2 m cell.
  2. Overlay slope from the IMU-fused elevation map: add 0.4 × tan(slope_angle) to c(x,y). A 15° slope on loose gravel scores 0.82 (near-impassable).
  3. A VLM reads the scene: “This looks like wet clay.” → multiply all clay-colored cells’ cost by 1.3 (learned multiplier from semantic annotations).
  4. Plan with A* on the fused cost map: optimal path skirts the clay patch and the steep slope, adding 8 m to the route but reducing slip risk from 0.6 to 0.12.
  5. At execution, proprioceptive feedback: if slip > 0.3 on a cell, raise its cost by 0.5 for future plans and slow from 0.8 m/s to 0.3 m/s.
  6. Unknown terrain gets a VLM prior: a boulder field never seen in training is labeled ‘rugged terrain’ by GPT-4V and assigned cost 0.7 — the planner routes around it rather than gambling.

  • ROBOVLM-GroNav: Robot Navigation Using Physically Grounded VLMs Outdoors — a VLM judges outdoor terrain traversability

Kinodynamic planning

robotics
the problem

A car can’t spin in place; a truck-trailer has a hitch that limits the turning angle; a legged robot has to maintain balance through each step. Ignoring these physics produces paths the body literally cannot follow. Planning in the full state space (position + velocity + joint angles) is much larger and harder, but unavoidable.

the approaches

A car can’t turn in place and a truck-trailer can’t sidestep — kinodynamic planning bakes the robot’s motion limits (curvature, momentum, reverse) into the search, so the path is one the body can truly execute.

It doubles or worse the search space, so learned heuristics and hybrid search are the levers.

worked example — one concrete run
  1. State space for a car: (x, y, θ, v) — position, heading, speed. Control: (steering δ ∈ [−30°,30°], accel a ∈ [−3, 2] m/s²).
  2. Kinematic model: ˙x = v cosθ, ˙y = v sinθ, ˙θ = v tanδ / L (L=2.8 m wheelbase), ˙v = a.
  3. RRT in (x,y,θ,v) space: sample (x_rand, y_rand, θ_rand, v_rand), find nearest tree node, integrate the dynamics for 0.4 s with the best (a,δ) that steers toward the sample.
  4. After 5,000 samples a branch reaches the goal. The path has smooth arcs that respect the turning radius and speed limits — no hairpin turns, no velocity jumps.
  5. For a tractor-trailer: add the trailer angle ψ to state → 5D space, add the hitch constraint ˙ψ = v sin(θ−ψ) / l. The planner finds the jackknife-free reverse parking path.
  6. Speed-up trick: a learned heuristic (neural network mapping (x_near, x_goal) → estimated cost-to-go) biases sampling toward promising states, cutting 5,000 samples to 800.

Mapless & reactive navigation

robotics
the problem

Building a map takes time and memory, and it goes stale. In environments that change faster than the robot can map them — a crowded market, a cave being explored for the first time — you need a robot that can act on raw sensor readings right now, with no stored model to consult. The danger is that purely reactive strategies can walk straight into dead-ends they cannot reason their way out of.

the approaches

Skip the map entirely: react to raw sensor readings right now. Memory-free and instant, it thrives in dynamic or unknown spaces — but a purely reactive robot can walk straight into a dead-end it can’t reason its way out of.

Learned reactive policies and congestion estimation soften the local-minimum trap.

worked example — one concrete run
  1. Sensor input every 20 ms: 360° LIDAR scan, 180 range readings at 2° resolution.
  2. Bug algorithm step: if the reading in the goal direction > 1.5 m, drive straight. Otherwise, follow the wall on the right at 0.4 m offset.
  3. After 3.2 s of wall-following the robot rounds the corner and the goal direction is clear again. Resume straight-line approach.
  4. The dead-end trap: a U-shaped room. Wall-following brings the robot around all three walls and back to the entrance — stuck in a loop. Congestion detector: if the robot has been in a 1 m radius for >8 s, declare a local minimum.
  5. Escape: back up 1.5 m and choose the second-best gap direction instead of the wall side. This breaks the loop.
  6. A learned policy variant: CNN takes the 180-d scan and outputs (v, ω) directly, trained with RL in simulation across 4,000 random maps. The policy implicitly learns to avoid dead-ends by recognizing the U-shape in the scan pattern.

  • ROBOFocus Bug: Learning Environmental Awareness for Efficient Mapless Navigation — learns where to attend for map-free navigation
  • ROBOBrain-Inspired Spatial Continuous State Encoding for Spiking-Based Navigation — neuromorphic reactive navigation encoding
  • ROBOOptimizing Underwater Robot Navigation: DRL + Multi-Modal Sensor Fusion — deep-RL reactive navigation underwater

Navigation foundation & world models

both
the problem

A classical planner needs an explicit map and a hand-specified cost. A learned policy needs labeled demonstrations in the right building. What if the robot could generalize from video of millions of different places — predicting what will happen, reasoning about spatial goals, and planning by imagining futures without ever being in a specific room before?

the approaches

Pretrain one big model on oceans of video and robot data, then reason about spatial goals, predict what an action will do, and plan by imagining futures — zero-shot in places it never trained on.

The tension is latency and hallucination: big models are slow and confidently wrong about geometry.

worked example — one concrete run
  1. Pretraining: a transformer is trained on 300k hours of egocentric video + 50k robot trajectories, learning to predict the next frame given the current frame and a proposed action token.
  2. At test time, the robot is in a new building with no map. Goal: reach a ‘bookshelf.’
  3. Propose an action (‘turn left 30°’), roll out the world model for 5 imagined steps. Does the imagined future show a bookshelf? Similarity to CLIP(“bookshelf”) = 0.34 (no).
  4. Propose ‘move forward 1 m’: imagined CLIP similarity = 0.71. Take that action.
  5. Repeat for 12 real steps (each with 5 imagined rollouts). The robot reaches the bookshelf without a pre-built map — entirely by imagining consequences.
  6. The hallucination problem: on step 9, the model imagines a doorway that isn’t there and tries to walk through a wall. A depth-sensor safety stop prevents the collision. World models are confident and sometimes wrong about geometry.

  • ROBOReMEmbR: Reasoning Over Long-Horizon Spatio-Temporal Memory for Navigation — builds and queries long-horizon spatial memory
  • CVPRMotus: A Unified Latent Action World Model — optical-flow latent actions bridge video and robot data
  • CVPRSocialNav: Human-Inspired Foundation Model for Socially-Aware Navigation — a VLM social-reasoning brain + flow-matching action expert

Map-free localization & place recognition

vision
the problem

GPS works outdoors in open space. Inside buildings, underground, or at centimeter accuracy, you need to know where you are by matching what you see to something previously seen. The problem is that the same place can look completely different from a different angle, in different light, or months later — and matching must be fast enough to keep up with a moving robot.

the approaches

Know where you are without a prebuilt map, by matching the current view against references or across viewpoints — the anchor that keeps goal-directed navigation honest when there’s no GPS.

Cross-view geolocalization and language-to-map matching are the fast-moving edges.

worked example — one concrete run
  1. Offline: walk through the building once, saving a database of (image, pose) pairs at every 0.5 m. Encode each image with NetVLAD into a 4096-d descriptor. Total: 1,200 reference frames.
  2. Online query: robot takes a new image. Encode it: 4096-d descriptor. Nearest-neighbor lookup in the database: 12 ms on a 1200-entry index.
  3. Top-5 candidates returned (cosine similarity >0.87). The best match is frame #847, pose (14.2, 3.1, 92°).
  4. Geometric verification: match SIFT keypoints between query and candidate. Find 64 inliers with RANSAC (threshold 3 px). Inlier ratio 0.71 → accept.
  5. Refine pose with PnP on the 64 inlier 3D–2D correspondences: final pose (14.27, 3.08, 91.4°) — 0.08 m, 0.6° error.
  6. Cross-view challenge: a satellite-to-ground match for outdoor geolocalization. The same intersection looks completely different from above vs. street level. A flow-based model aligns the two views progressively, achieving <4 m outdoor localization without GPS.

  • CVPRVLM-Loc: Localization in Point Cloud Maps via Vision-Language Models — text-to-point-cloud localization via BEV + scene graphs
  • ROBOLiteVLoc: Map-Lite Visual Localization for Image Goal Navigation — lightweight visual localization for image-goal nav
  • CVPRSinGeo: Unlock Single Models’ Potential for Cross-View Geo-Localization — one robust model across view configurations

Simulation, benchmarks & sim-to-real

vision
the problem

Navigation research needs thousands of episodes in diverse buildings — far more than any real robot fleet can provide. Simulators give that, but they are wrong in ways that matter: the physics of friction, the exact lighting on a texture, the precise timing of sensor noise. A policy that achieves 90% success in simulation may score 50% on the real robot the first day.

the approaches

Navigation research runs on simulators — photoreal houses, procedural scenes, terrain curricula — that give reproducible tests and cheap, massive training, then transfer to real robots via domain randomization.

The gap is fidelity: photorealism isn’t physics, and agents that ace the benchmark can still stumble outdoors.

worked example — one concrete run
  1. Collect one 10-minute scan of a real apartment with a depth camera. Reconstruct it into a Gaussian-splat mesh in 4 minutes — photoreal render at 80 fps.
  2. Drop the splat into Habitat-sim (MuJoCo physics). Now train a navigation policy with PPO for 50M sim steps. Each frame is photographic; physics is exact. Wall time: ~6 hours on 8 GPUs.
  3. Domain randomization: randomly vary camera exposure (+/−1.5 EV), add sensor noise (σ=0.01 m depth), randomize friction (0.5–1.2), add random furniture placement. Policy must handle all variants.
  4. Deploy on the real robot. First-day success rate: 74% (vs. 58% without the splat—randomization pipeline).
  5. Failure analysis: the remaining 26% fail at narrow doorways (<0.75 m) and shiny floors (depth noise spikes). Fix: add synthetic glare patches and door-width randomization in the sim. Second-day: 83%.
  6. The gap that remains: benchmark win (90%) vs. real-world (83%) vs. different apartment (61%). The gap is the field’s honest remaining problem.

  • CVPRGeniBench: 176 scenes, 491.6 km of coherent trajectories — closed-loop image-goal benchmark with real-robot tests
  • ROBODP-Habitat: Bridging Simulation and Reality for Dynamic Pedestrian Navigation — sim-to-real visual navigation among pedestrians
  • CVPRPanoEnv: 3D Spatial Intelligence in Panoramic Environments with RL — geometry-grounded panoramic navigation training

Part IV

Where it stands

Getting a robot reliably from A to B in the open world is far from finished. What is genuinely still hard:

Generalization past the training world. Learned navigators still degrade in buildings, lighting, and clutter unlike their training data — distribution shift is the field’s limiting factor.
Certifying learned motion. Classical planners come with safety proofs; learned and foundation-model navigators don’t — verifying them formally is largely unsolved.
Language that means geometry. VLMs read instructions well but reason about exact distances and free space poorly, so language navigation still leans on separate geometric grounding.
Crowds that react back. People adjust to the robot, so one-way prediction breaks; interaction-aware prediction that avoids the freezing-robot trap is still hard.
Real-time under a heavy model. Foundation-model and world-model navigators are slow and memory-hungry; fitting them inside a control loop on a small robot is an open squeeze.
The sim-to-real gap. Simulators underspecify friction, contact, and the messiness of the real world, so benchmark wins don’t always survive the sidewalk.
