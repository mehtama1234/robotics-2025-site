01 · the problem

A free path to the goal

Every mobile robot faces the same first question: how do I get over there? The goal is a place; the world between here and there is full of walls, furniture, people, and things the map didn’t mention. The straight line is almost always blocked.

So navigation is the search for a collision-free path — a continuous route through the empty space to the goal. What makes it hard isn’t drawing the line; it’s that the robot only partly knows the world, the world moves, and whatever path it picks has to be one the robot’s body can actually follow.

the actual math — one level deeper

Split the robot’s configuration space C into free space C_free and obstacles C_obs. A path is a continuous curve τ:[0,1]→C_free with τ(0)=start, τ(1)=goal.

Partial and changing knowledge means C_obs is only estimated from sensors — so planning and re-planning interleave as the estimate updates.

02 · plan it

Two ways to find a path

Given the free space, how do you actually find a route through it? One answer is to sample: scatter random points, keep the ones that don’t hit anything, and connect them into a growing tree until a branch reaches the goal. Try enough points and you’ll find a path if one exists.

The other answer is to optimize: start from a rough guess — even a bad one — and repeatedly nudge it to lower a cost that rewards short, smooth, obstacle-free motion. One explores by trying many motions; the other refines a single one until it fits. Most real systems use both.

the actual math — one level deeper

Sampling (RRT): draw a random q, steer the nearest tree node toward it, keep the edge if collision-free; probabilistically complete — finds a path if one exists, given enough samples.

Optimization: minτ ∫ cost(τ,τ̇) dt subject to dynamics and collision constraints; solved with iLQR/MPC-style updates from an initial guess.

03 · the stack

A map to plan on, a loop to dodge

In practice a robot runs two loops at once. The global planner works on a stored map — usually an occupancy grid marking free and blocked cells, with a cost that pushes paths away from walls — and finds a route all the way to the goal.

But the map is always a little out of date, so a fast local planner runs many times a second on the live sensor feed, choosing immediate motions that follow the global route and dodge whatever just appeared. Plan globally on what you know; react locally to what you see.

the actual math — one level deeper

Global: run A* / Dijkstra over the costmap grid c(x) to get a least-cost route to the goal.

Local: each cycle pick controls (v,ω) minimizing distance-to-path + a collision penalty over a short horizon (DWA / MPC) — a fast reactive loop under the slow global one.

04 · the world moves

Navigating among people

Static obstacles stay put; people don’t. Navigating a crowd means the robot must predict where each person is heading over the next few seconds and thread a path through the gaps that will exist, not the ones that exist now.

This is genuinely hard because prediction is uncertain, and if the robot assumes the worst about everyone, the predicted futures blanket every open direction — so the only ‘safe’ move is to stop. That’s the notorious freezing-robot problem: over-caution is its own failure, and good crowd navigation is really good prediction.

the actual math — one level deeper

Predict each agent’s future distribution p(x_t) and treat it as a time-varying obstacle; plan a path that keeps collision probability below a threshold.

Freezing: if predicted occupancy fills the free space, no feasible low-risk path remains — the fix is joint / interaction-aware prediction, not more caution.

05 · learn it

From pixels, and from words

The newest strand skips the explicit pipeline. A network takes the raw view and a goal — a target image, an object name, or a plain-language instruction — and outputs the next move directly, learning from demonstrations or from reward in simulation.

This is what lets a robot follow ‘go past the kitchen and stop at the second door’ in a building it has never seen, with no map handed over. It leans on the same web-pretrained vision-language models as the rest of the field — and inherits their strength (broad generalization) and their weakness (shaky precise geometry).

the actual math — one level deeper

Learn a policy πθ(a | obs, goal) by imitation or RL; goal is an image, an object class, or language tokens.

Vision-and-language navigation grounds instruction tokens against the visual stream step by step, emitting move / turn / stop until it reports done.

Sampling-based motion planning (RRT / PRM)

robotics
the problem

The robot needs to get from one configuration to another without hitting anything, but the free space is complicated: high-dimensional, full of narrow passages, and impossible to enumerate. You can’t simply enumerate all paths or hand-draw one in 7-DOF arm space.

the approaches

The classical backbone: scatter random collision-free configurations and connect nearby ones into a graph or tree, then read off a path. It handles high-dimensional spaces and odd kinematics where hand-drawing a route is hopeless.

Recent work speeds convergence, improves path quality, and pushes sampling onto needles, AUVs, and nonholonomic vehicles.

worked example — one concrete run
  1. Start with one node: the robot’s current configuration (7 joint angles). Goal node: the target pose.
  2. Sample a random configuration q_rand in the 7-DOF joint space — uniformly at first, then biased toward the goal with probability 0.05 to keep progress.
  3. Find the nearest node in the current tree (Euclidean distance in joint space). Steer toward q_rand by stepping 0.2 rad per joint at most.
  4. Check the new edge for collision by querying the forward kinematics at 10 interpolated configurations. If any link overlaps an obstacle, discard.
  5. Add the collision-free node and edge to the tree. After ~2,000 samples, a branch reaches within 0.1 rad of goal — declare success and read off the path.
  6. Post-process: shortcut the path by trying to directly connect non-adjacent nodes, cutting a 42-step path to ~18 straight moves.

    Second-Order Stein Variational Dynamic Optimization — variational sampling for dynamic trajectory optimization

    Sampling-based planners scatter random configurations and connect nearby ones, but the samples themselves can be poorly distributed, leaving gaps and wasting queries on redundant areas. This paper brings variational inference to the sampling problem: instead of random points, draw samples that minimize an energy function tied to the geometry, concentrating them where the free space is tightest and most informative.

    how it actually works
    1. Traditional RRT samples uniformly in the configuration space, ignoring structure.
    2. Compute a repulsive potential between sample particles and an attractive potential toward unexplored regions (or the goal).
    3. Update each sample by gradient steps that push particles away from each other (diversity) and toward high-value regions (coverage).
    4. This yields a second-order update that refines the particle distribution across the space faster than raw RRT, concentrating density where the path is constrained.
    5. The payoff is fewer samples needed to find the same collision-free path, and better quality paths when multiple exist.

Trajectory optimization & MPC

robotics
the problem

A sampling planner finds a path, but that path is jagged and ignores the robot’s actual dynamics — a drone can’t snap to arbitrary headings or stop instantly. You need a path the body can truly execute, and then you need to re-solve it every few milliseconds as the world changes.

the approaches

Instead of sampling, write down a cost — short, smooth, energy-cheap, clear of obstacles — and minimize it subject to the robot’s dynamics. Model-predictive control re-solves it every cycle so the plan tracks a changing world.

The work is speed (these solves are heavy), good initialization to dodge local minima, and differentiable planning fused with learning.

worked example — one concrete run
  1. Start with a straight-line guess from start to goal: 20 waypoints uniformly spaced, ignoring every obstacle.
  2. Compute the cost: sum of squared jerk (for smoothness) + 1000 × max(0, −d_obs) for each waypoint that penetrates an obstacle (d_obs = signed distance to nearest obstacle).
  3. Gradient step: compute ∇cost for all waypoint positions and step them by lr=0.05. Obstacle-penetrating waypoints shoot outward; jagged waypoints smooth toward their neighbors.
  4. After 50 iterations the path wraps cleanly around the obstacle and the cost drops from ~840 to ~12.
  5. MPC re-solve every 50 ms: freeze the first control, advance one step, warm-start the next solve with the tail of the previous solution — the plan always looks 2 s ahead.
  6. At 10 Hz re-solve rate, the drone tracks a moving target or dodges a suddenly-closing door without replanning from scratch.

    Shadow Program Inversion with Differentiable Planning — unifies program-parameter and trajectory optimization, differentiably

    Trajectory optimization requires initializing a rough guess and iterating toward lower cost. Most planners use hand-designed initializations (straight line, predefined curves) that often land in poor local minima, especially in cluttered spaces. This paper unifies program parameters and trajectory optimization through differentiable planning: the trajectory itself becomes the output of a learned program, and gradients flow through the planning solver.

    how it actually works
    1. Encode a trajectory as the output of a parameterized program (e.g., a neural network or a symbolic function) with learnable weights.
    2. Run the trajectory through a collision-checking and dynamics simulation to compute the cost.
    3. Backpropagate gradients through the simulation and collision-checking to update the program parameters.
    4. The program learns to output trajectories that are already near-optimal, giving the optimizer a warm start that avoids poor local minima.
    5. Result: faster convergence, better final paths, and the learned program generalizes to new environments without retraining the trajectory optimizer.

    Legged robots must coordinate many joints and feet simultaneously while respecting contact dynamics and stability constraints.     how it actually works

    2. Simulate each rollout forward through a dynamics model (contact forces, friction, joint limits) to compute its cost (deviation from desired motion, energy, stability margin).

    4. The weighted average defines the next control command to send to the robot.
    5. At 100+ Hz, this is faster than iterative optimization because the samples run in parallel and the final blend is closed-form.

Safe navigation & collision avoidance

robotics
the problem

Good average behavior isn’t enough: a single collision is a failure. You need a formal certificate that the robot will never enter an obstacle — but the tighter you draw the safety margin, the more of the free space you rule out, until cluttered corridors become impassable.

the approaches

Layer a safety filter over any planner: monitor distance to obstacles and forbid controls that could lead to a collision. Control-barrier functions and reachability analysis give formal guarantees, not just good behavior on average.

The tension is conservatism — guarantees need margins, and too-large margins make cluttered spaces impassable.

worked example — one concrete run
  1. Define the safety set h(x) = d(x, obstacle) − r_safe, where r_safe = 0.3 m. The robot is safe as long as h(x) ≥ 0.
  2. The CBF condition: the chosen control u must satisfy ˙h(x,u) + αh(x) ≥ 0. With α=2, this means ‘the safety margin must be improving (or at least not shrinking too fast).’
  3. Nominal planner proposes u_nom (move straight toward goal at 0.5 m/s). Check: does it satisfy the CBF constraint?
  4. If not, solve a small QP each 10 ms: find u* closest to u_nom that does satisfy it. The QP has 2 variables and 1 constraint — it solves in <0.1 ms.
  5. The corrected u* curves the robot away just enough to keep h ≥ 0, without stopping or replanning.
  6. Formal guarantee: if h(x_0) ≥ 0 at the start and the QP is always feasible, h never goes negative — the robot never hits the obstacle, provably.

    2. Define a safety function h(x) = distance to nearest splat surface − safety margin (0.3 m).

    4. If the command is unsafe, solve a small quadratic program to find the closest-to-nominal command that does satisfy the constraint (2 variables, 1 constraint, <1 ms).
    5. Send the safety-corrected command; the formal guarantee is that h never goes negative, so no collision ever occurs.

04

Learned & end-to-end navigation

both
the problem

Classical pipelines hand-specify every sub-problem: map it, plan on it, control toward it. But the real world is too messy for every rule to be written down — narrow gaps, dark corridors, and texture-less walls break hand-specified detectors and cost functions one by one.

the approaches

Train a network to map observations straight to motion — from demonstrations or from reward in simulation — skipping the explicit map-plan-execute pipeline. It captures intuitive, human-like navigation that’s hard to hand-specify.

The open issues are the usual ones for learning: data hunger, distribution shift, and hard-to-certify safety.

worked example — one concrete run
  1. Collect 50 hours of human teleoperation through a building, recording (RGB image, velocity command) pairs at 10 Hz — 1.8 million training pairs.
  2. Train a ResNet-50 + GRU to predict (v, ω) from 4 stacked frames. Loss = MSE on both outputs; train for 80 epochs on 4 GPUs.
  3. At inference the network reads the current 4 frames and emits a velocity command 30 ms later — the entire map-plan-control stack collapsed to one forward pass.
  4. Where it works: the training corridors, lighting conditions, and obstacle types it saw. Success rate: 87% door-to-door in the training building.
  5. Where it breaks: a new building with different wall colors — success drops to 41%. A residual RL fine-tune on 2 hours of real experience recovers to 79%.
  6. The irreducible tension: no network output comes with a safety proof. Add a reactive collision-stop layer that halts if any depth reading < 0.4 m to keep deployment safe.

the problem

The paper trains a transformer on millions of hours of navigation video and robot actions, learning to predict the next frame and score goal similarity. At test time, the robot imagines 5-step futures for each action candidate and picks the one whose imagined scene is closest to the language goal. Unified video-language prediction lets navigation work in new buildings zero-shot by reasoning about geometry and semantics through simulation.

    how it actually works

    What it operates on: Video frames, action tokens (move forward, turn left, etc.), and language goal tokens (from a text encoder).

    The key operations: (1) Pretraining: a transformer is trained on 300k hours of egocentric video paired with navigation actions. The model learns to predict the next frame: &hat;f_t+1 = model(f_t, a_t; θ). (2) At test time, encode the goal: goal_emb = CLIP("kitchen") or similar. (3) For each action candidate (move, turn left/right, stop), roll out the world model for 5 steps: imagine f_t+1, f_t+2, ..., f_t+5 by repeatedly applying the model. (4) Compute goal similarity for each imagined frame: sim = cosine_similarity(CLIP(imagined_frame), goal_emb). Pick the action whose imagined trajectory has the highest average similarity. (5) Execute the action in the real world and repeat.

    Why it works: Video prediction learns spatial reasoning (what's beyond the visible wall?) and temporal reasoning (how does the view change with my action?). The model doesn't need explicit geometry because it learned to predict it from millions of hours. Grounding language goals via CLIP embeddings lets the same model work for any goal without retraining.

  • ROBO
    ReMEmbR: Reasoning Over Long-Horizon Spatio-Temporal Memory for Navigation — builds and queries long-horizon spatial memory

    A world model that predicts the next frame is fast but forgets—after 5 imagined steps, drift and hallucination compound. Navigation over longer horizons (30+ steps) needs to remember where the robot has been and what it has seen, not just dream forward. The paper builds a spatio-temporal memory graph as the robot explores: nodes are observed places, edges encode temporal and spatial connections. At decision time, the robot queries this memory to reason about long-horizon routes and avoid revisiting dead-ends. Explicit episodic memory grounds imagination in reality, so world-model navigation stays grounded over long sequences.

    how it actually works

    What it operates on: A sequence of observed frames and proprioceptive readings (robot pose, action history) building a spatial-memory graph over time.

    The key operations: (1) As the robot navigates, every K frames (e.g., every 2 meters traveled), insert a memory node: store the frame embedding (via a pretrained CLIP encoder), the estimated pose, and a timestamp. (2) Connect nodes: two nodes are spatially linked if their pose distance is < 3 meters; temporally linked if visited within the same minute. Edges store traversal cost (time or distance). (3) At decision time, given a goal description, query the memory graph: find nodes with high similarity to the goal (CLIP embedding). Compute a least-cost path through the graph (Dijkstra). (4) Execute the first step of that path in the real world. Update the graph with new observations.

    Why it works: The graph is a compressed, queryable version of the robot's history. Reasoning over it avoids the hallucination drift of pure imagination—paths are grounded in real places the robot has seen. The graph also detects loops (nodes with similar embeddings are the same place), so the robot doesn't repeat dead-ends.

  • CVPR
    Motus: A Unified Latent Action World Model — optical-flow latent actions bridge video and robot data

    Video and robot trajectories tell different stories: a video shows pixel-space motion (things moving), while a trajectory is the robot's commanded actions (forward, turn). Predicting from video alone doesn't generalize to robots because pixel motion and command motion are not the same thing. The paper learns a unified latent action space: optical flow in video is decoded into the same action tokens that command real robots, so one world model can predict both video futures and robot motion. Unified latent actions bridge video-only learning and robot-only learning, letting the model transfer between them.

    how it actually works

    What it operates on: Video sequences and robot trajectory sequences, with optical flow computed from video.

    The key operations: (1) Define a latent action space: a small set of action codes (e.g., 8-32 tokens representing forward, turn left/right, stop at multiple speeds). (2) Train an encoder on optical flow from video: encode the pixel-space motion between frame pairs into latent-action tokens. (3) Train the same encoder on robot telemetry: encode (velocity, angular velocity) into the same action tokens. (4) Train a shared world model in latent action space: given frame f_t and action a_t (in latent space), predict f_t+1. (5) At training time, mix video sequences (where actions are inferred from flow) and robot sequences (where actions are directly known). The shared model learns to predict either.

    Why it works: Optical flow and robot command are two views of the same thing: how the world should change. Learning one latent action space for both forces the model to find a unified representation. A robot trained on both video and proprioceptive data learns faster and generalizes better than either alone, because the two modalities constrain each other—the action must explain both the pixel change and the state change.

  • CVPR
    SocialNav: Human-Inspired Foundation Model for Socially-Aware Navigation — a VLM social-reasoning brain + flow-matching action expert

    Navigating around people is different from navigating around furniture—people react, adjust speed, and have social expectations about personal space and eye contact. A classical planner that treats people as time-varying obstacles produces jerky, aggressive paths. The paper trains a large vision-language foundation model on human navigation videos (people navigating crowds, giving and receiving advice), learning to reason about social dynamics. At runtime, the VLM outputs a high-level social strategy ("pass behind the crowd", "slow down and let them pass"), which an action expert (trained on expert robot trajectories) executes with smooth, low-jerk commands. VLM social reasoning + action expertise makes robot paths human-like and respectful.

    how it actually works

    What it operates on: Visual scene (RGB image of the crowd), detected pedestrian positions and velocities, and the goal location. The VLM processes images and language jointly.

    The key operations: (1) Encode the scene: a vision encoder extracts spatial features from the camera view. Detected pedestrians are annotated with positions and velocity vectors. (2) The foundation VLM (pretrained on vast navigation video and instruction data) reasons about social strategy: it outputs a natural-language description like "pass behind the taller person on the left" or "yield and let the group move first." (3) A separate action expert (a policy network trained on expert demonstrations) takes this language strategy plus the scene and outputs (v, ω) commands at 10 Hz. (4) The action expert is trained via behavioral cloning on expert human-robot navigation footage, so it knows how to smoothly execute social strategies.

    Why it works: Foundation VLMs understand social norms from massive data. Rather than hand-code social rules, the VLM reasons about the specific situation (is this a narrow corridor or an open room?). The action expert then handles low-level control, decoupling high-level social reasoning from reactive steering. This two-level split makes the robot both socially aware (via VLM) and smooth (via expert control).

Map-free localization & place recognition

vision
the problem

GPS works outdoors in open space. Inside buildings, underground, or at centimeter accuracy, you need to know where you are by matching what you see to something previously seen. The problem is that the same place can look completely different from a different angle, in different light, or months later — and matching must be fast enough to keep up with a moving robot.

the approaches

Know where you are without a prebuilt map, by matching the current view against references or across viewpoints — the anchor that keeps goal-directed navigation honest when there’s no GPS.

Cross-view geolocalization and language-to-map matching are the fast-moving edges.

worked example — one concrete run
  1. Offline: walk through the building once, saving a database of (image, pose) pairs at every 0.5 m. Encode each image with NetVLAD into a 4096-d descriptor. Total: 1,200 reference frames.
  2. Online query: robot takes a new image. Encode it: 4096-d descriptor. Nearest-neighbor lookup in the database: 12 ms on a 1200-entry index.
  3. Top-5 candidates returned (cosine similarity >0.87). The best match is frame #847, pose (14.2, 3.1, 92°).
  4. Geometric verification: match SIFT keypoints between query and candidate. Find 64 inliers with RANSAC (threshold 3 px). Inlier ratio 0.71 → accept.
  5. Refine pose with PnP on the 64 inlier 3D–2D correspondences: final pose (14.27, 3.08, 91.4°) — 0.08 m, 0.6° error.
  6. Cross-view challenge: a satellite-to-ground match for outdoor geolocalization. The same intersection looks completely different from above vs. street level. A flow-based model aligns the two views progressively, achieving <4 m outdoor localization without GPS.
  • CVPR
    GeoFlow: Real-Time Fine-Grained Cross-View Geolocalization via Iterative Flow — flow-based cross-view geolocalization in continuous pose

    A satellite image and a street-level photo show the same intersection, but one is from above and one is from ground level—the perspectives are radically different. Matching them for outdoor localization is hard because the views are so misaligned. The paper iteratively aligns a satellite image to a ground view by predicting optical flow, warping the satellite image, and repeating. Each iteration brings them into alignment. Iterative flow-based warping aligns radically different views without hand-specified geometric models, enabling continuous-pose outdoor localization from cross-view matching.

    how it actually works

    What it operates on: A ground-level query image (street view from a camera) and a satellite map patch, both roughly centered on the same intersection but with unknown rotation and scale.

    The key operations: (1) Encode both images into feature maps (via a shared CNN). (2) Compute an initial flow field that aligns ground features to satellite features, using a correlation-based or learned flow estimator. (3) Warp the satellite image according to the flow: resample pixels at positions offset by the flow vectors. (4) Compute a new flow field between the warped satellite and the ground image. (5) Repeat steps 3–4 for 5–10 iterations. (6) After convergence, the final warp matrix directly gives the 2D translation, rotation, and scale between the views, which translates to the robot's latitude/longitude (within a few meters) and heading.

    Why it works: Flow-based alignment handles large perspective differences because it's a dense, pixel-level optimization—it doesn't rely on feature matching which fails when views are radically different. Iterative refinement (warping then re-computing flow) converges to a consistent alignment. The final warp, once known, immediately reveals the relative pose between ground and satellite viewpoints.

  • CVPR
    VLM-Loc: Localization in Point Cloud Maps via Vision-Language Models — text-to-point-cloud localization via BEV + scene graphs

    A point cloud is a 3D geometric map, but it's not semantic—it's just XYZ coordinates of walls and objects. Querying a point cloud for "where is the red door?" requires matching pixels to 3D geometry, which is tedious. The paper renders a point-cloud map from multiple viewpoints into synthetic images, encodes them with a VLM (which understands both geometry and language), and builds a database of (viewpoint, semantic feature) pairs. At runtime, a query text ("red door") is encoded into a VLM embedding, and nearest-neighbor search over the database finds the viewpoint where the query is most similar. VLM-indexed point clouds let robots localize by natural language without explicit geometry-to-language bridging.

    how it actually works

    What it operates on: A precomputed point-cloud map and a query text string (goal description).

    The key operations: (1) Offline: for a grid of viewpoints (e.g., every 0.5 m over the map), render a synthetic egocentric view from the point cloud (using standard graphics). Each rendered image is stored with its viewpoint pose. (2) Encode each rendered image with a CLIP VLM: extract a 512-d semantic embedding. Store (pose, embedding) in a database. (3) At query time: encode the goal text (e.g., "red door") with the same CLIP encoder: emb_query = CLIP("red door"). (4) Compute cosine similarity between emb_query and all stored embeddings. Return the top-5 viewpoints with highest similarity. (5) Use the stored pose of the best match as the target for the planner.

    Why it works: The VLM embeds both visual content and language semantically into the same space. A "red door" is a visual pattern the VLM has seen before, and the embedding captures that. Rendering the point cloud from many viewpoints creates a comprehensive indexed space, so a query can find not just "a door" but "a red door visible from a specific place."

  • ROBO
    LiteVLoc: Map-Lite Visual Localization for Image Goal Navigation — lightweight visual localization for image-goal nav

    Image-goal navigation means the robot is shown a target photo and must navigate to a place that looks like it, without being told coordinates or a map. Localizing via visual similarity alone—"where does the current view match this target photo?"—is expensive if you have thousands of reference images. The paper learns a compact visual-localization encoder that maps images to pose estimates directly, using only a handful of reference examples. Lightweight pose regression from visual similarity lets robots navigate to image goals with minimal memory and fast matching.

    how it actually works

    What it operates on: A target image (the goal) and a stream of camera frames from the robot, plus a small database of (image, pose) pairs from the environment (perhaps 50–200 samples).

    The key operations: (1) Train a siamese encoder on the reference database: it learns to map an image into a pose-predictive feature space where images from nearby locations have similar features. (2) Encode the goal image: goal_feat = encoder(goal_image). (3) At runtime, encode each incoming frame: frame_feat = encoder(current_frame). (4) Compute similarity or distance from frame_feat to goal_feat. Use this distance as a reward: move toward the goal if similarity increases, backtrack if it decreases. (5) Optionally, use top-k reference images with highest similarity to goal to refine the pose estimate via geometric verification (SIFT matching + RANSAC).

    Why it works: The siamese network learns that nearby places have similar visual features, so the distance in feature space correlates with distance in real space. A lightweight encoder (vs. full SLAM or dense mapping) is fast and memory-cheap. The trade-off is precision: it works best for distinctive places, but recovers gracefully even in repetitive environments by combining visual similarity with occasional geometric verification.

  • CVPR
    SinGeo: Unlock Single Models’ Potential for Cross-View Geo-Localization — one robust model across view configurations

    Cross-view geolocalization models are typically trained on one view configuration (e.g., satellite-to-street). Swap the views (street-to-satellite) or introduce a new view (UAV drone perspective) and performance crashes because the model overfits to its training configuration. The paper builds a model that normalizes for view differences internally, learning to extract view-invariant features. A single model then works across any pair of views: satellite-to-street, street-to-street, drone-to-satellite, etc. View-invariant feature extraction unifies cross-view localization across configurations, making one model reliable and general.

    how it actually works

    What it operates on: Two images from different views (satellite and street-level photos) and a set of possible view-pair types (satellite-to-street, UAV-to-ground, etc.).

    The key operations: (1) Learn separate branch encoders for each view modality: satellite encoder, street encoder, aerial encoder. Each branch learns to extract features that are reliable to lighting, season, and camera artifacts specific to that view. (2) Normalize branches with view-specific normalization layers (BatchNorm or AdaIN tuned per view type). (3) After normalization, project all branches into a common semantic space via a shared projection head. (4) Train with a metric loss (e.g., triplet loss): pull together correct cross-view pairs (same location) and push apart incorrect pairs (different locations). (5) At test time, encode both query images with their respective branches, normalize, project, and compute cosine similarity in the shared space.

    Why it works: View-specific branches learn modality-specific features (satellite images have cadastral boundaries, streets have cars and signs). Normalization removes view-specific artifacts, and the shared projection maps all normalized features into a unified space. This two-level hierarchy—modality-specific then view-invariant—decouples reliability to view differences from reliability to location matching.

Simulation, benchmarks & sim-to-real

vision
the problem

Navigation research needs thousands of episodes in diverse buildings — far more than any real robot fleet can provide. Simulators give that, but they are wrong in ways that matter: the physics of friction, the exact lighting on a texture, the precise timing of sensor noise. A policy that achieves 90% success in simulation may score 50% on the real robot the first day.

the approaches

Navigation research runs on simulators — photoreal houses, procedural scenes, terrain curricula — that give reproducible tests and cheap, massive training, then transfer to real robots via domain randomization.

The gap is fidelity: photorealism isn’t physics, and agents that ace the benchmark can still stumble outdoors.

worked example — one concrete run
  1. Collect one 10-minute scan of a real apartment with a depth camera. Reconstruct it into a Gaussian-splat mesh in 4 minutes — photoreal render at 80 fps.
  2. Drop the splat into Habitat-sim (MuJoCo physics). Now train a navigation policy with PPO for 50M sim steps. Each frame is photographic; physics is exact. Wall time: ~6 hours on 8 GPUs.
  3. Domain randomization: randomly vary camera exposure (+/−1.5 EV), add sensor noise (σ=0.01 m depth), randomize friction (0.5–1.2), add random furniture placement. Policy must handle all variants.
  4. Deploy on the real robot. First-day success rate: 74% (vs. 58% without the splat—randomization pipeline).
  5. Failure analysis: the remaining 26% fail at narrow doorways (<0.75 m) and shiny floors (depth noise spikes). Fix: add synthetic glare patches and door-width randomization in the sim. Second-day: 83%.
  6. The gap that remains: benchmark win (90%) vs. real-world (83%) vs. different apartment (61%). The gap is the field’s honest remaining problem.
  • CVPR
    OctoNav-Bench: 45k+ instruction-trajectory pairs across 400+ scenes — a large multi-capability navigation benchmark

    Training a navigation policy requires thousands of expert demonstrations, but collecting real-robot teleoperation is slow and expensive. Simulation provides unlimited data, but sim-to-real gaps remain: friction is different, LIDAR noise is underspecified, lighting is unrealistic. The paper constructs a large-scale benchmark by rendering 400+ diverse simulated scenes (houses, apartments, offices, outdoor paths) and rolling out expert trajectories under different instructions ("go to the kitchen", "find a red object") with careful domain randomization (friction, lighting, sensor noise). A policy trained on this data transfers to real robots with minimal fine-tuning. Massive diverse simulation + randomization produces data-efficient, real-world-ready policies without collecting every example on a real robot.

    how it actually works

    What it operates on: A physics simulator (Habitat or SAPIEN) and a diverse dataset of 3D scene meshes (Matterport, ScanNet, Replica).

    The key operations: (1) For each scene, spawn the robot at random start positions and set a random goal (object, room, or instruction). (2) Roll out an expert policy (e.g., optimal-path-following oracle) to generate the expert trajectory, recording (RGB image, depth, instruction tokens) at 10 Hz and (linear velocity, angular velocity) commands. (3) Domain randomization: vary camera exposure, add synthetic Gaussian noise to depth, randomize surface friction coefficients, randomly place movable objects, vary lighting color temperature. (4) Collect 45k+ (observation, instruction, action) tuples across all scene and randomization configurations. (5) Train an imitation-learning or RL policy on this dataset. Evaluate on held-out scenes and then real-world deployment.

    Why it works: Large-scale, diverse data with systematic randomization covers the space of real-world variations. The oracle expert ensures high-quality labels. Diversity across 400+ scenes fights overfitting to specific lighting or furniture layouts. The result is a policy that has seen enough variability to generalize when the real world presents unseen textures or friction.

  • CVPR
    GeniBench: 176 scenes, 491.6 km of coherent trajectories — closed-loop image-goal benchmark with real-robot tests

    Benchmark diversity is one thing; trajectory coherence is another. A policy trained on random expert walks may succeed at reaching isolated goals, but it won't understand that coherent long-horizon behavior—navigating through a sequence of rooms, solving multi-step tasks—is different from one-off goal-reaching. The paper constructs a benchmark where each trajectory is a long, meaningful sequence: the robot must traverse a complex path spanning multiple buildings, following waypoints in a coherent order. The result is 176 scenes with 491.6 km of coherent "expert journeys", giving policies access to complex behaviors rare in random-goal datasets. Coherent multi-step trajectories train policies for realistic, long-horizon navigation instead of isolated goals.

    how it actually works

    What it operates on: 176 complex 3D environments (multibuilding scenes) and a set of long-horizon task sequences (e.g., "exit the office, go to the break room, grab coffee, return to the office").

    The key operations: (1) Design task sequences as waypoint chains: Δ_1, Δ_2, ..., Δ_K (e.g., K=8 waypoints per trajectory). (2) For each task sequence, roll out a closed-loop expert policy: navigate to Δ_1, then Δ_2, etc. Optionally, the expert makes realistic mistakes (takes wrong turns, backtracks) to make training more reliable. (3) Record closed-loop observations: (RGB, depth, goal pose Δ_current) and actions (v, ω) at 10 Hz. The trajectory is a sequence of images showing the robot progressing through the waypoint chain. (4) Collect 491.6 km total of trajectories (likely 100+ trajectories per scene). (5) At training time, expose policies to these long sequences: random start point in a sequence, predict the next action toward the next waypoint. The policy learns both short-term reaction (obstacle avoidance) and long-term structure (multi-hop planning).

    Why it works: Coherent long-horizon sequences expose the policy to behaviors (commitment to a goal despite initial setbacks, multi-step replanning) that random-walk data lacks. The robot learns that navigation is a sequence of decisions, not isolated reflexes. This trains policies that survive real deployment, where the task isn't "reach this one chair" but "complete a multi-step errand."

  • ROBO
    DP-Habitat: Bridging Simulation and Reality for Dynamic Pedestrian Navigation — sim-to-real visual navigation among pedestrians

    Simulation is cheap; real robots navigating crowds are expensive to test. Simulators populate pedestrians via hand-tuned crowds (all walk at constant speed, predictable patterns) that look nothing like real people (who stop, speed up, make eye contact, react to robots). A policy trained on simulated crowds fails on real ones because pedestrian behavior is more complex. The paper trains pedestrian dynamics in simulation by observing real-world crowd video and fitting learned models of how real people move. Then the robot learns to navigate using these realistic simulated crowds, and the learned policy transfers directly to real humans. Learned pedestrian dynamics make simulation faithful to reality, enabling zero-shot transfer from sim to real crowds.

    how it actually works

    What it operates on: Real-world crowd video footage (e.g., from pedestrian datasets) and a physics simulator (Habitat).

    The key operations: (1) Extract pedestrian trajectories from real crowd video using pose tracking or motion detection. (2) Train a pedestrian behavior model: given the current positions and velocities of nearby people, predict each person's next velocity. Use a social-force model or neural network to capture how real people adjust speed and direction based on neighbors and obstacles. (3) Integrate the learned pedestrian model into the simulator. Now simulated crowds have realistic behaviors: people jam at doorways, create local swirls, yield to robots sometimes and hold their ground other times. (4) Train a navigation policy with RL in this realistic simulator, with the robot as an agent among simulated pedestrians. Reward progress to goal, penalize collisions. (5) Deploy the policy on a real robot navigating real crowds. No fine-tuning needed.

    Why it works: Real crowd dynamics are learnable from video—behavioral models capture the patterns without hardcoding. Because the simulator now matches real pedestrian behavior, a policy trained there doesn't need to relearn behavior characteristics on real humans. The bridge is the learned pedestrian model, which captures the essential complexity: reaction, yielding, density effects.

  • CVPR
    PanoEnv: 3D Spatial Intelligence in Panoramic Environments with RL — geometry-grounded panoramic navigation training

    Navigating through a single panoramic scene (360-degree image) is different from navigating across a 3D map: the robot sees the entire surroundings at once, but must reason about depth and move through 3D space while staying consistent. Most agents train on rectangular frames and underutilize the panoramic view. The paper builds a reinforcement-learning environment where navigation is conducted in panoramic images grounded by depth, geometry, and topology. The agent learns to reason about the entire 360-degree space at once, making spatial decisions more globally optimal. Panoramic reasoning with grounded geometry trains spatially-intelligent agents that use the full visual field for better, less myopic navigation.

    how it actually works

    What it operates on: Panoramic images (equirectangular 360-degree projections) paired with depth and semantics at every pixel. The environment includes 3D navigation graphs that connect navigable locations.

    The key operations: (1) Represent state as a panoramic image + depth map. The panoramic projection captures the entire scene without the myopia of a narrow field-of-view camera. (2) An agent network ingests the panoramic state and outputs a discrete action (turn left 90°, move forward, etc.) or a continuous heading angle. (3) Actions are converted to 3D motion: move forward in the direction the agent is facing, update pose, fetch new panorama from the graph of precomputed viewpoints. (4) Reward: (reached goal?) + (progress to goal in graph distance) - (time penalty). (5) Train with PPO across a dataset of scenes (Matterport, etc.). Regularize to make spatial decisions (if the goal is visible 45° to the left in the panorama, prefer left-turn actions).

    Why it works: Panoramic images present the entire visual context in one shot, reducing the need for the agent to maintain mental maps. The geometry-grounding (depth, navigation graph) makes spatial reasoning concrete: the agent can compute distances and visibility directly from the panorama. Agents trained on full panoramic context make more coherent long-range decisions than those trained on sequential narrow frames.

Part IV

Where it stands

Getting a robot reliably from A to B in the open world is far from finished. What is genuinely still hard:

Generalization past the training world. Learned navigators still degrade in buildings, lighting, and clutter unlike their training data — distribution shift is the field’s limiting factor.
Certifying learned motion. Classical planners come with safety proofs; learned and foundation-model navigators don’t — verifying them formally is largely unsolved.
Language that means geometry. VLMs read instructions well but reason about exact distances and free space poorly, so language navigation still leans on separate geometric grounding.
Crowds that react back. People adjust to the robot, so one-way prediction breaks; interaction-aware prediction that avoids the freezing-robot trap is still hard.
Real-time under a heavy model. Foundation-model and world-model navigators are slow and memory-hungry; fitting them inside a control loop on a small robot is an open squeeze.
The sim-to-real gap. Simulators underspecify friction, contact, and the messiness of the real world, so benchmark wins don’t always survive the sidewalk.
