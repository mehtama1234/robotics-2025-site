The big picture — connecting the dots

The central challenge in motion planning is a collision of two hard truths: the math to find the optimal path is too slow to compute in real time, but the robot cannot wait. For decades, this meant a choice — plan ahead and hope the world does not change, or re-plan often and accept rough, jerky movements. The papers here break this tradeoff by changing what "good enough" means. Instead of computing one perfect path, they sample thousands of candidate paths on parallel hardware and score them by safety, smoothness, and goal-reaching. Instead of planning in abstract space, they bake the robot's actual body limits, steering geometry, and physics directly into the planner so the solver never proposes something the hardware cannot do. And instead of trusting a model, they measure the real world's drift and cancel it in real time, mid-movement. The result is planning that works when the world changes, when you have only a few milliseconds, and when the space is tight enough that there is almost no clearance.

Four angles the field is attacking from:

  • ① Parallel sampling with model predictive path integral control. Evaluate thousands of trajectories in parallel on a GPU; score each by safety and smoothness; pick the best or blend good ones. Take Your Best Shot: Sampling-Based Planning for Autonomous Photography uses this to choose viewpoint trajectories for a camera robot. CNSv2: Probabilistic Correspondence Encoded Neural Image Servoing combines sampling with visual feedback for manipulation.
  • ② Breaking hard spaces into soft pieces. When a space is too cluttered to solve all at once, split the problem: solve for one obstacle constraint at a time, or decompose multi-obstacle spaces into tangent-line chains. Narrow Passage Path Planning Using Collision Constraint Interpolation feeds collision rules into the solver incrementally. Context-Aware Collaborative Pushing of Heavy Objects Using Sampled Candidate Trajectories handles spaces full of movable objects.
  • ③ Embedding the robot's physics and geometry into planning. Do not plan in abstract space; encode how the robot actually moves. SEB-Naver: A SE(2)-based Local Navigation Framework for Car-like Robots on Uneven Terrain models steering geometry on slopes. Inverse Kinematics on Guiding Vector Fields for Robot Path Finding ensures proposals respect joint limits. EHC-MM: Embodied Holistic Control for Mobile Manipulation blends base motion and arm manipulation into one QP optimization, avoiding jerky mode switches.
  • ④ Predicting and canceling what will go wrong. Model the task mechanics and deformation, predict drift, reject disturbances. Safe Leaf Manipulation for Accurate Shape and Pose Estimation of Occluded Fruits predicts leaf deformation to plan gentle pushing moves. Dual-BEV Nav: Dual-Layer BEV-Based Heuristic Path Planning for Mobile Robots uses layered representations to reason about traversability. Vision-Based Movement Primitives for Lunar Hazard Avoidance uses learned motion primitives to navigate without a full terrain model.

The throughline: motion planning is shifting from trying to compute perfection in advance to sampling intelligently, respecting real constraints, and reacting quickly when the world does not match the model. The field can now close the control loop in milliseconds on tasks from tight-passage navigation to lunar crater avoidance, and the clearest wins come from encoding the robot's geometry and physics directly into the optimization rather than planning in the abstract and hoping it works. Still open: reliable real-time planning in very cluttered spaces with many movable obstacles; large model-reality gaps that require no re-planning; and a unified framework that combines speed, safety, body constraints, and disturbance rejection in one system that works across different robot morphologies and tasks.

The problem — in depth

Every robot that moves has to answer one question over and over, many times each second: given where I am right now, what should my joints do next? This sounds simple, but it is deeply hard.

The right answer is to solve a precise math problem: find the exact sequence of joint commands that gets the robot to its goal as fast and safely as possible, while avoiding every obstacle and respecting every limit the hardware has. That problem, solved exactly, takes far too long to compute. A robot arm reacting to a moving ball, or a mobile robot weaving through a crowd, cannot wait. It needs an answer now, then again in a fraction of a second, then again. So the field is always chasing the same tradeoff: the more correct the answer, the slower it arrives; the faster the answer, the rougher the motion.

This gets harder still because the world keeps changing in ways the robot did not expect. A person shifts direction. A crane load starts to swing. Wind pushes a drone off course. A leaf moves. An object turns out to be heavier than expected. The math the planner used a moment ago now describes a world that no longer exists.

There is also a structural problem that shows up across many of these papers. A robot is not a point in space — it is a body with links and joints, and each link can collide with something. Checking whether a proposed path is safe requires testing the whole body's shape against every nearby obstacle, and doing that for millions of candidate paths per second is expensive. In tight spaces, where nearly every path grazes something, the planner's job is even harder: it must thread through gaps that may be barely wide enough, or find that the only way through is to move something out of the way first.

These problems connect to the one big challenge every robot faces. A robot must take in an unclear, changing world, decide what to do, move a real body, and do it fast, cheap, safe, and general. Motion planning sits right at the junction of decide and move. A plan that arrives too late is useless. A plan that ignores the body's limits cannot be followed. A plan that ignores disturbances will drift. The 115 papers in this topic are all trying to close that gap.

The approaches — how the field actually tackles it

Trying many paths in parallel and scoring them

In plain terms Instead of finding one perfect route, the robot tries thousands of possibilities at once and picks the fastest-and-safest one—like rolling dice rapidly and keeping the winning roll.
The sub-problemFinding the one perfect path is too slow to compute in real time, but scoring many candidate short paths in parallel and picking the best one is fast. The challenge is making sure the planner can re-solve this fast enough when the world changes.
Time-based planning via sampling — Trajectory Planning with Signal Temporal Logic Costs Using Deterministic Path Integral Optimization. Uses sampling to plan paths that satisfy time-based rules (like "be in zone A between seconds 3 and 7") without rewriting those rules for standard solvers.
Reactive swing planning — High Speed Robotic Table Tennis Swinging Using Model Predictive Control. Re-solves the best swing from scratch every time the robot gets a new estimate of where the ball will land.
Viewpoint sampling for photography — Take Your Best Shot: Sampling-Based Planning for Autonomous Photography. A camera robot samples many candidate viewpoints and picks the one that reveals the most new information about the scene.

A planner sampling thousands of candidate paths in parallel on fast hardware can re-plan every few milliseconds, fast enough to track a moving target or react to sudden changes.

Handling tight spaces by breaking them into simpler pieces

In plain terms When a space is packed tight, don't solve it all at once—solve it one obstacle at a time, or chain simple moves together, so the solver makes actual progress instead of getting jammed.
The sub-problemIn narrow or cluttered spaces, most candidate paths hit something, so the planner gets stuck. The trick is to decompose the hard problem into easier pieces so the solver can make progress one step at a time.
Incremental collision rules — Narrow Passage Path Planning Using Collision Constraint Interpolation. Splits the environment into convex regions and feeds collision rules to the solver one at a time instead of all at once, keeping the solver from getting stuck at the start.
Tangent-line decomposition — Improving Efficiency in Path Planning: Tangent Line Decomposition Algorithm. Breaks the full multi-obstacle problem into a chain of single-obstacle steps, each solved by a simple tangent line, shrinking the search space dramatically.
Focused search among movables — Search-Based Path Planning in Interactive Environments Among Movable Obstacles. Ignores most objects that are far from the path and focuses attention only on obstacles actually in the way.

When the planner works through the environment one obstacle at a time or chains simple solutions together, it finds paths through tight spaces that a global solver would miss.

Building a model of how the body and world behave — and using it

In plain terms Instead of planning in fantasy-land and hoping it works, bake the actual robot's limits and how the real world pushes back into the planner itself—so bad ideas get rejected before they're even tried.
The sub-problemA plan that ignores how the robot's body actually moves or how the world responds to commands will fail when executed. Encoding the real physics and geometry into the planner from the start means no invalid paths are ever proposed.
Neural planning with kinematic constraints — iKap: Kinematics-Aware Planning with Imperative Learning. Bakes the math of joint-to-motion into neural network training so the network never proposes a path the hardware cannot follow.
Steering geometry on slopes — SEB-Naver: A SE(2)-based Local Navigation Framework for Car-like Robots on Uneven Terrain. Derives the math for how a car-like robot steers on sloped ground and uses it to plan smooth paths that respect real steering limits.
Underwater arm dynamics — Dynamic End Effector Trajectory Tracking for Small-Scale Underwater Vehicle-Manipulator Systems. Builds a full model of how a robot arm mounted on an underwater vehicle interacts with water and uses it to design a controller.
Hydraulic flow limits in cranes — Near Time-Optimal Hybrid Motion Planning for Timber Cranes. Models the hydraulic pump's flow limits and uses that model to plan fast motions that the pump can actually supply.

When the planner knows how the robot's body and the world actually behave, it can plan faster and safer because it never proposes something the hardware cannot execute.

Canceling disturbances and model errors directly

In plain terms The world never matches the plan exactly—wind pushes, objects are heavier than expected. Instead of replanning everything, a fast watchdog catches the drift and corrects it on the fly.
The sub-problemThe best plan drifts when the real world does not match the model. Rather than waiting for the planner to generate a new path, a separate loop detects drift and corrects it in real time.
Velocity-damped collision avoidance — Collision Avoidance in Model Predictive Control Using Velocity Damper. Adds a safety rule that considers not just how far the robot is from an obstacle but how fast it is closing in, catching unsafe situations a distance-only rule would miss.
3D rotation disturbance rejection — Robust Orientation Control of Robot Manipulator Using Orientation Disturbance Observer. Rebuilds a standard disturbance-canceling tool to work directly with 3D rotation math, letting the arm resist outside forces trying to knock its tip off direction.
Robust transport under model error — Robust Nonprehensile Dynamic Object Transportation. Plans a path by minimizing how sensitive the outcome is to errors in the object model, so the chosen path stays safe even when the model is wrong.

When a controller detects and corrects drift in real time, it can work safely even when the model does not match reality exactly.

Adapting to the task's structure — sequential steps, coverage, and multi-body systems

In plain terms Different jobs have their own rhythm: mowing a lawn doesn't need backtracking, coordinating two arms matters, assembly needs strict order. Build that rhythm into the planner and the whole thing gets simpler and faster.
The sub-problemDifferent tasks have their own structure — coverage requires no backtracking, multi-arm systems need coordination, sequential assembly demands one step at a time. Baking task-specific structure into planning makes the controller simpler and faster.
Energy surface for step-by-step tasks — No Plan but Everything Under Control. Builds a mathematical energy surface that changes as the task progresses, so the robot follows it downhill without an explicit plan — the surface itself encodes what to do next.
Coverage with adaptive footprint — Improving Coverage Performance of a Size-Reconfigurable Robot. Plans a sweep path for a robot that can change its own size, adding penalties for retracing and unnecessary resizing.
Smooth base-to-arm blending — EHC-MM: Embodied Holistic Control for Mobile Manipulation. Uses a smooth blending function to shift one controller's attention between driving and arm use based on distance to target, avoiding abrupt mode switches.
Coordinated arm and thruster — A Control Strategy for an Orbital Manipulator. Coordinates the robot arm and an end-effector thruster so thrust always points away from the satellite being serviced.

When the controller understands the task's structure — whether it's coverage, sequencing, or coordinating multiple actuators — it can use a single unified system instead of mode-switching between separate plans.

Where it stands

The field can now plan and re-plan motion fast enough to close the loop in many real tasks — table tennis, crane operation, underwater manipulation, lunar digging. The clearest gains come from parallel sampling on fast processors and from building physical constraints directly into planners. What remains hard is planning reliably in very tight spaces with many movable objects, handling large mismatches between the model and the real world without a new plan, and combining all these ingredients — speed, safety, body constraints, disturbance rejection — in a single system that works across different robots and tasks.

Safe Leaf Manipulation for Accurate Shape and Pose Estimation of Occluded Fruits

The big idea — first principles

The problem. A robot must find and measure fruit hidden under leaves. Pushing leaves risks tearing the plant, but without clearing them the robot cannot see what it is grasping. The system cannot know in advance how each leaf will move under gentle pressure.

The approach. Predict how leaves will deform before pushing them by building a physical model of the plant, then simulate each candidate push to see how much fruit it would reveal, and choose the sequence of pushes that exposes the fruit with minimal damage.

What's unique. Earlier work predicted leaf deformation in isolation or estimated visibility in isolation; here they are unified: the planner chooses each push by jointly simulating deformation and visibility to find moves that reveal the fruit while keeping deformations small.

ICRA 2025 · 6 citations · mobile-manipulation

What it does

A robot equipped with a gripper and camera must find and grasp fruit hidden under leaves. This method plans a sequence of gentle leaf-pushing moves to expose the fruit for clear viewing and measurement, without tearing the plant. It is a mobile-manipulation approach: the robot moves its base to reach the fruit, then coordinates careful arm motions with predictions of how each leaf will deform under pressure.

The method, in detail

The system works in three stages:

Stage 1: Segmentation and scene understanding.

RGB-D sensor data (an image from a camera plus depth values) is fed into GroundedSAM (a segmentation model), which classifies every pixel as leaf, branch, fruit, or background. This produces a 3D point cloud — a set of (x, y, z) positions — for each object type.

Stage 2: Shape completion.

Fruit and branches are often only partially visible. The method applies scene-consistent shape completion: it fits a geometric model (using a technique similar to As-Rigid-As-Possible, or ARAP, warping) to complete the hidden parts of branches and fruit. For fruit shape, it uses DeepSDF, a neural network trained to recognize pepper and other fruit shapes even from fragmentary views. The key trick is "scene-consistent": the completed shape must match what was observed and not contradict the known structure of the plant.

Stage 3: Deformation prediction and grasp planning.

Before the robot acts, it builds an embedded deformation graph (EDG) from the completed plant model. This is a sparse set of control points (vertices) that can be moved; when you drag one control point, neighboring parts of the plant deform smoothly. The system then simulates what happens if the gripper pushes on a leaf: the EDG predicts the new leaf shape. A visibility predictor (OctoMap, a voxel-based 3D occupancy grid) estimates how much of the fruit will become visible from the robot's camera viewpoint after that push. The system then plans a sequence of push actions that maximizes final fruit visibility while penalizing large deformations (to avoid tearing leaves).

The key trick: The framework unifies leaf deformation simulation with visibility estimation. Instead of planning moves in isolation, it reasons about "if I push here, the leaf deforms this way, and then I can see the fruit from this angle — is that better?"

EHC-MM: Embodied Holistic Control for Mobile Manipulation

The big idea — first principles

The problem. A robot with a moving base and an arm must decide whether to drive forward or carefully manipulate. Older systems switched abruptly between these modes—drive hard until close, then switch to gentle arm motion—causing jerky, inefficient movement.

The approach. Encode both base and arm control into one Quadratic Programming optimization that solves all at once. A smooth weighting function shifts the system's attention from base mobility to arm precision as the target gets closer, avoiding mode switches.

What's unique. The "Distant Mobility, Close Grasping" principle is not new, but encoding it as a single smooth blending function in the optimizer (not multiple separate controllers) means base and arm motion never fight each other—they collaborate within one unified step.

ICRA 2025 · 4 citations · mobile-manipulation unified control

What it does — 2-3 plain sentences, and which sub-approach it is

A robot with a moving base and an articulated arm needs to decide when to prioritize driving forward versus carefully manipulating an object. EHC-MM is a unified controller that seamlessly blends base motion and arm control into a single optimization step, using a smooth weighting function that shifts the robot's focus based on how close it is to its target and how hard it would be to reach. This is the mobile-manipulation sub-approach: whole-body control coordinating a mobile base + arm + camera perception into one real-time decision loop.

The method, in detail — step by step, plain words but technical

Inputs: Current robot state (base position/velocity, arm joint angles, camera frame); target object location; task-space goal for manipulation (where to position the end-effector).

The core trick: The paper encodes the "Distant Mobility, Close Grasping" (DMCG) principle—meaning *drive to the object from far away, then switch to careful manipulation up close*—as a single Quadratic Programming (QP) optimization problem. Most systems plan these two modes separately; EHC-MM unifies them.

The math: The QP objective is:

  • Minimize: 0.5 * x^T Q x + C^T x, where x is the vector of all control commands (base velocities + arm joint velocities).
  • Q matrix encodes the interaction between base and arm motion (so they don't fight each other).
  • C vector bakes in two goals: (1) maximizing manipulability (how many directions the arm can move), and (2) auxiliary tasks like obstacle avoidance or camera framing.

The blending function sig(ω): The critical innovation is a smooth sigmoid function that measures *reachability*—a parameter ω that captures how difficult the end-effector is to move to the target. When ω is large (target far, hard to reach), sig(ω) weights the QP heavily toward base motion. As the robot closes in and ω shrinks, sig(ω) smoothly shifts the weighting toward arm precision control. This avoids sudden jerky switches between modes.

Monitor-Position-Based Servoing (MPBS): Vision module that keeps the camera pointed at the target while the arm manipulates. Traditional position-based servoing (PBS) only tracks visual errors to move the end-effector; MPBS adds a term that adjusts the arm's orientation to maintain line-of-sight to the manipulated object, preventing the target from drifting out of frame during dynamic motion.

Optimization setup: The QP is solved at real-time control rates (typically 50–100 Hz) on the robot's onboard computer. Constraints enforce joint angle limits, collision-free space (via signed-distance fields or simple box constraints), and actuator torque limits. A QP solver such as qpSWIFT or Quadratic Program Interior Point (QPIP) computes the optimal control in milliseconds.

Training/learning: This is *not* a learned model. The method is classical control-theoretic; all parameters (Q, C, ω tuning) are hand-tuned or identified via offline experiments on the robot platform (RealMan compound arm) to balance mobility and manipulation.

Reviewing it yourself — what to read first, and how hard the code is to follow

Read the arXiv paper first: [https://arxiv.org/abs/2409.08527](https://arxiv.org/abs/2409.08527). Section 2 covers the QP formulation mathematically; Section 3 explains MPBS. The method is sound but the paper is dense—expect 1–2 hours to fully digest.

Code difficulty: *Moderate to hard.*

  • The QP solver setup is straightforward (bind constraint matrices, call solver).
  • The tricky parts are (1) computing sig(ω) correctly as a smooth reachability measure, (2) populating the Q and C matrices to encode the right trade-offs, and (3) tuning the robot-specific parameters in config/yaml for your arm's dynamics and workspace.
  • If you have experience with ROS2 and control theory (Jacobians, constraint handling), you can read this in ~4–6 hours.
  • If you are unfamiliar with QP solvers or ROS, plan 2–3 days to understand the data flow and tune parameters.

Gotchas:

  • sig(ω) must be smooth and bounded; a poorly implemented sigmoid (e.g., too steep) will cause oscillations in the blending.
  • Q matrix conditioning: if Q is ill-conditioned, the QP solver may fail or produce nonsensical velocities. Must carefully normalize joint contributions.
  • Real-time safety: the QP solves in ~3 ms, but latency in reading sensor state or publishing commands can add 10+ ms. Must test closed-loop latency on real hardware.

CNSv2: Probabilistic Correspondence Encoded Neural Image Servo

The big idea — first principles

The problem. A robot arm watching a camera must move the end-effector to match a target pose. Older visual-servoing picks the single best feature match, which breaks entirely when lighting is bad or the object has no texture—the match just disappears.

The approach. Instead of picking one definite match, represent each possible feature match as a probability spread. Convert those soft matches into a canonical spatial grid, then feed that to a neural network that predicts both the speed and direction to move.

What's unique. Standard methods make a binary choice (match found / not found); this treats matching as inherently uncertain and builds that uncertainty into the representation itself, so the network learns to servo reliably even when the best match is ambiguous or missing.

ICRA · 3 citations · visual-servoing

What it does

CNSv2 controls a robot arm by watching a camera and dynamically computing motor commands to move the end-effector toward a goal pose. Unlike older methods that fail when lighting is bad or objects have no visible texture, CNSv2 represents each possible feature match as a probability spread rather than picking a single definite match—then feeds those soft match scores into a neural control policy. It's a visual-servoing approach: driving motion from camera error signals.

The method, in detail

The system has three pipeline stages:

1. Feature extraction & dense matching. A frozen pretrained vision transformer (AM-RADIOv2.5 with ViT-B backbone) extracts coarse features from the current camera image and a reference target image, both downsampled to 1/16 resolution. A dot-product similarity kernel computes a dense matching-score matrix between all image patches—instead of picking the single best match for each feature, the softmax scores remain as probabilities across all possible matches.

2. Probabilistic correspondence encoding. The matching scores are not fed directly to the controller. Instead, they're converted into a fixed-size "translation-equivariant" feature map by projecting the soft matches onto predefined spatial grid anchors using quadratic B-spline basis functions. This trick (borrowed from material-point methods in physics simulation) ensures the representation is independent of image resolution and robustly encodes uncertainty about where features actually are.

3. Neural controller & velocity denormalization. A transformer network with axial rotary positional embeddings (2D RoPE) takes these probabilistic feature maps and predicts two outputs: (a) log-norm of the desired velocity (magnitude on a log scale), and (b) a unit direction vector pointing in 3D space. Crucially, these predictions are normalized—independent of the actual camera and scene. A separate analytical denormalization step then scales the velocity using the camera's intrinsic matrix and an essential matrix transform computed from the soft correspondences, adapting the control command to real-world intrinsics and distances.

Training setup: Entirely in simulation (NVIDIA IsaacSim). The authors sampled 6,852 diverse 3D models from the GSO and OmniObject3D datasets. Two parallel data-generation processes run: one picks object poses uniformly at random, the other uses DAgger—an online curriculum learning strategy—to generate hard cases where the policy is uncertain. Heavy domain randomization (object textures, materials, lighting, camera poses) ensures robustness. Loss is L1 on velocity magnitude (log-scale) and cosine similarity on direction.

The key trick: Instead of binary keypoint matches (which break in clutter, bad light, or textureless scenes), probabilistic soft matches + transformation to canonical grid anchors + denormalization creates a representation that is robust to illumination and texture while still running at real-time speed (~40 fps reported, likely on high-end GPU).

Take Your Best Shot: Sampling-Based Planning for Autonomous Photography

The big idea — first principles

The problem. A camera robot must choose where to move next to capture the most informative photo of a partially hidden target. Computing the optimal full trajectory is too slow. Greedily choosing the closest viewpoint is fast but wastes shots on redundant angles.

The approach. Sample many candidate viewpoints, simulate camera rays from each one to predict how much new information it would reveal, and move to the viewpoint with the highest information gain. Repeat at each step.

What's unique. Rather than planning a full path first, this method evaluates only candidate *next locations* and scores each by actual information (rays cast through 3D space), making fast local decisions that naturally lead to efficient coverage without global trajectory optimization.

What it does — 2-3 plain sentences

A mobile robot equipped with a camera autonomously chooses where to drive next to capture the most informative photograph of a partially hidden target, then decides to move there. This is a sampling-based path planning approach: instead of computing a full trajectory first, the system proposes many candidate viewpoints and picks the best one based on how much new information it would reveal.

The method, in detail

The robot starts with a partial 3D model of the scene (from previous views or rough map data). At each decision step:

  • Information evaluation: For each candidate viewpoint (a location the robot could move to), the system simulates camera rays from that viewpoint through the 3D space and counts how many parts of the target are visible vs. occluded. This ray-tracing calculation estimates the *information gain* — how much new visual coverage would be unlocked if the robot moved there.
  • Probabilistic interpolation: Since the scene is only partially known, some regions are uncertain. A Gaussian process (a statistical model that learns smoothly from sparse data) interpolates the traversability and visibility across the entire space, allowing the system to estimate information reward even for untested viewpoints.
  • Derivative-free optimization (DFO): Rather than using calculus-based gradient descent, the system uses a black-box optimization method (derivative-free) that repeatedly samples candidate viewpoints from across the environment and evaluates each one's information score. This is robust because the information landscape is complex and may have no smooth gradients.
  • Motion execution: Once the highest-scoring viewpoint is chosen, the robot plans a collision-free path to it and drives there.

The key trick: the algorithm avoids expensive full-trajectory planning by evaluating *discrete candidate locations* and picking the single best next pose to visit. Each visit adds new visual information, progressively building a complete 3D model or capturing the target from all desired angles with minimal wasted images.

Narrow Passage Path Planning Using Collision Constraint Interpolation

The big idea — first principles

The problem. Optimization-based path planners fail in tight spaces. The solver starts at a point buried in obstacles and tries to satisfy collision constraints from all obstacles at once. The linear approximation violates so many rules immediately that no progress is possible—the solver stalls.

The approach. Instead of including all obstacle constraints from the start, add them gradually. Solve for a subset of nearby obstacles first, then add the next group and re-solve using the previous answer as the warm start, continuing until all obstacles are included.

What's unique. The gradual constraint introduction mimics moving *through* the tight space itself—the solver never faces an infeasible jump because constraints appear in spatial order as the path progresses through the passage.

ICRA 2025 · 3 citations · path-planning

What it does — 2-3 plain sentences

This paper tackles the hard problem of finding robot paths through tight, constrained spaces where existing optimization-based planners get stuck. The method works by decomposing obstacles into simple convex shapes and feeding collision rules to the solver one at a time instead of all at once. This is a path-planning approach: it computes collision-free trajectories offline using math optimization, not sampling or reactive steering.

The method, in detail

Problem setup: Standard path planners use gradient-based optimization (Sequential Quadratic Programming, or SQP) to minimize a cost function while respecting collision constraints. But when the start point is deep inside an obstacle—common in narrow passages—the solver fails immediately because its linear approximation violates so many constraints at once that no progress is possible.

The trick: Instead of presenting all collision constraints at the start, the authors decompose the environment into convex objects, then introduce those constraints gradually. The process works like this:

  • Decompose the static environment into convex obstacles (e.g., boxes, ellipsoids, convex hulls).
  • Start the optimization with collision constraints only from a small subset of obstacles—ones near the start and goal.
  • Run SQP to solve this easier subproblem.
  • Add the next group of constraints and repeat, using the previous solution as the warm-start.
  • Continue until all obstacles are included.

The optimization: At each iteration, SQP linearizes the nonlinear constraints and solves a Quadratic Program (QP). The paper uses SubADMM (Alternating Direction Method of Multipliers via subdivision) to solve these QPs stably, especially when constraints conflict. For collision detection, they compute signed distance fields (SDFs) on interpolated obstacle shapes, then use the Frank-Wolfe algorithm to find the closest point (guaranteed global optimum for convex SDFs). For fixed obstacles, they use GJK-EPA (a faster geometric algorithm).

Why it works: By interpolating constraints smoothly into the problem, the solver is never forced to make an infeasible jump. The warm-start from each subproblem keeps SQP in a region where its linear approximation is valid. This is especially powerful in narrow passages because the gradual constraint introduction mimics the spatial progression through the passage itself.

The big idea — first principles

The problem. A robot crossing rough outdoor terrain sees immediate detail through its camera or LiDAR (rocks, ditches, slopes) but cannot see whether the wider landscape ahead is passable—a locally safe path may lead to a dead-end or dangerously steep slope further out.

The approach. Build two overhead maps: a detailed local one showing immediate obstacles and ground safety, and a coarser global one estimating traversability across 50+ meters. Score candidate waypoints against both maps and move to the one that is locally safe and globally viable.

What's unique. Local detail prevents collisions, global probability prevents bad long-term routes. Neither alone is enough—a patch may be locally flat but globally isolated (dead-end), or locally rough but globally the only way through. Scoring both prevents greedy local decisions from trapping the robot.

What it does — 2-3 plain sentences

Dual-BEV Nav builds two overhead terrain maps from sensor data and uses them together to guide a robot across rough outdoor ground. A detailed local map proposes safe nearby paths; a coarser global map rates how passable the whole landscape is. The planner picks the route that satisfies both, allowing robots to navigate successfully even when GPS is poor and terrain is unstructured.

The method, in detail

The system operates in a two-stage pipeline:

Local BEV Planning Model (LBPM):

  • Builds a high-resolution bird's-eye-view representation of terrain within the robot's sensor range
  • Identifies traversable regions by assessing local ground geometry (slopes, obstacles, roughness)
  • Generates candidate waypoints that are geometrically feasible to reach from the robot's current position
  • Prioritizes paths that hug passable terrain and avoid sharp drops, rocks, or deep ditches
  • Operates at sensor update rates (real-time or near-real-time for onboard compute)

Global BEV Planning Model (GBPM):

  • Maintains a lower-resolution probability map of traversability across a wider area (e.g., 50–100 m radius or larger)
  • Encodes which terrain patches are safe to cross based on aggregated sensor data or learned terrain classifiers
  • Handles occlusions by probabilistically estimating traversability of unseen or partially visible regions
  • Guides long-range route selection and goal targeting

  • The local planner proposes paths; the global planner scores them
  • Candidate waypoints from LBPM are projected onto the GBPM probability map
  • The route that maximizes combined local feasibility and global traversability probability is selected as the next waypoint
  • The robot moves toward that waypoint, then the cycle repeats at the next planning step
  • Key trick for unstructured terrain: does not assume flat ground or pre-mapped corridors; instead dynamically fuses real-time local detail (which prevents collisions) with global risk estimates (which prevents dead-ends and unsafe slopes over long distances)

Outputs: Next intermediate waypoint; traversable path to that waypoint

Critical design principle: Local and global traversability are orthogonal—a patch may be locally smooth but globally isolated, or globally accessible but locally rough. By scoring both, the planner avoids paths that are locally optimal but globally risky.

Inverse Kinematics on Guiding Vector Fields for Robot Path Following

The big idea — first principles

The problem. A robot must follow a predefined path but older steering methods (pure pursuit, carrot-following) rely on ad-hoc tuning that cannot be predicted—the robot may overshoot, oscillate, or respond slowly depending on how the gain was chosen.

The approach. Represent the path as a level set (the zero-contour of a smooth function) and treat the robot's distance from that contour as a "virtual joint." Use inverse kinematics on this virtual joint to guarantee the error behaves like a linear system with predictable, controllable transient response.

What's unique. Instead of ad-hoc steering gains, this method connects path-following to classical control theory (pole placement, damping ratios), letting designers specify exactly how fast and smoothly the robot converges to the path—then guarantee it will happen that way.

ICRA 2025 · 3 citations · inverse-kinematics sub-approach

What it does

The paper borrows a technique from robot arm control—inverse kinematics—and applies it to path-following problems in autonomous mobile robots. Instead of solving for joint angles (as in arms), it treats the distance from a target path as a "virtual joint" and uses that to give designers fine control over how quickly and smoothly a robot converges onto a path. The core idea is that by treating path-following as an inverse kinematics problem, the designer can inject precise transient behavior (how the robot approaches the path) and feed-forward commands (acceleration signals) that existing steering methods cannot offer. This is a inverse-kinematics sub-approach, not path-planning; it solves *how to drive toward a path that is already defined* with predictable control dynamics.

The method, in detail

Problem setup: A path is defined implicitly (not as a sequence of waypoints, but as the zero-level set of a smooth function—imagine the path as a contour line on a map). The robot's state is its position and orientation; the "error" is how far it is from that contour.

Key insight—extending IK to vector fields: Traditional inverse kinematics solves: given a desired end-effector pose, what joint angles produce that pose? The authors generalize this: given a desired path (defined as a level set), construct a vector field whose integral curves (the paths a robot would trace if it always followed the vector field) converge to the target path. They treat the path-distance error as if it were a virtual "joint angle" and use inverse kinematics to ensure that as this virtual joint moves, the error behaves like a linear system (easy to control, predictable transients).

Mathematical formulation:

  • Path representation: The path is $\mathbf{h}(\mathbf{x}) = 0$, a level set in $m$-dimensional space. The signed distance $d$ from a point to the path can be approximated locally as $d \approx \alpha \cdot c$ where $\alpha$ is a scaling constant and $c$ is a virtual "joint" (the path-constraint variable).
  • Inverse kinematics applied to the constraint: The robot's velocity $\mathbf{v}$ controls how $d$ changes:

$$\dot{d} = \nabla h \cdot \mathbf{v}$$

Rearranging this to get the vector field:

$$\mathbf{v} = \text{(inverse of Jacobian)} \cdot (\text{desired rate of error reduction} + \text{feed-forward term})$$

This ensures $d$ decays in a controlled, linear fashion (e.g., exponential convergence like a damped spring).

  • Single-integrator robots in Euclidean space: For a robot whose velocity directly matches the control input, the vector field is:

$$\mathbf{v} = -kN \nabla h - kT \nabla^2 h / (\|\nabla h\|) \cdot v_{\text{tangent}}$$

where $k_N$ controls convergence speed toward the path, and the second term drives motion along the path.

  • Unicycles (constant-speed, differential steering): The math becomes harder because a unicycle cannot move sideways. The authors derive a control law that produces steering commands (angular velocity) to make the unicycle's orientation align with the vector field direction, ensuring convergence even with kinematic constraints.
  • Real-world tuning: The method introduces explicit gain functions $kN(x)$ and $kT(x)$ (position-dependent gains) so that the robot's transient behavior (how fast it zeros in on the path) and steady-state performance (smooth motion along the path) can be shaped independently. A designer can also inject a feed-forward signal to make the robot accelerate or decelerate along the path.

Why it matters: Existing path-following methods (like pure pursuit or follow-the-carrot) make ad-hoc tuning choices; this method ties those choices to linear systems theory, so you can *predict and control* the transient response using classical control design (pole placement, damping ratios, etc.).

SEB-Naver: A SE(2)-based Local Navigation Framework for Car-like Robots on Uneven Terrain

The big idea — first principles

The problem. A wheeled robot must drive across hills, slopes, and rough terrain. Older planners treat the ground as flat or pre-mapped, or they compute full 6D pose optimization which is too slow for real-time control. The robot also risks tipping over on steep slopes if the planner ignores pitch and roll.

The approach. Reduce planning to 2D (position + heading only); automatically infer the robot's full 3D pose (pitch, roll, height) from terrain geometry. Rate each terrain cell for safety by measuring slope and roughness. Solve a smooth trajectory that avoids obstacles, respects steering limits, and keeps the robot from tipping.

What's unique. SE(2) parameterization cuts the search space drastically (3D instead of 6D), and terrain-aware risk scoring prevents oversimplified path-planning that ignores the actual physics of driving on slopes—the optimizer sees pitch/roll constraints and avoids them automatically.

What it does

A navigation system for wheeled robots that drives over hills, slopes, and rough terrain by constantly assessing which ground is safe to cross and then computing steering commands that respect both the terrain's slope and the robot's steering limits. This is a reactive-nav system that blends traversability assessment with real-time trajectory optimization: it evaluates terrain risk across a local overhead map, then solves a smooth path that avoids obstacles, stays within steering and speed bounds, and keeps the robot from tipping over.

The method, in detail

Input: Sensor data from the robot (LiDAR or stereo camera depth) and the robot's current state (position, heading, velocity).

Step 1: Terrain Representation in SE(2) Space

Instead of tracking the robot in full 3D space (which requires solving in 6 dimensions), the system reduces the problem to SE(2)—just 2D position plus yaw angle (heading). A mapping function automatically computes the robot's full 3D pose (pitch, roll, height) from this SE(2) state by analyzing local terrain geometry. This cuts computation drastically.

Step 2: GPU-Accelerated Traversability Rating

A parallel GPU routine rates each small cell in the local map. For each cell, it:

  • Samples terrain height at points matching the robot's footprint shape
  • Computes terrain curvature (how bumpy the surface is)
  • Calculates how much the robot would pitch and roll on that slope
  • Fuses these scores: a risk metric that combines curvature κ_ter, pitch angle φx, and roll angle φy through weighted sum

This processes nearly one million grid points in ~50 milliseconds—fast enough to run 20 times per second.

Step 3: Differential Flatness Trajectory Planning

The planner parameterizes the trajectory using an intermediate variable s (arc length along the path). It defines the path as piecewise quintic polynomials (smooth 5th-order curves) in x(s), y(s), and how time t maps to s(t). This avoids singularities that break other planners when the robot moves backward or very slowly.

The planner computes the steering angle δ, longitudinal acceleration ax, and lateral acceleration ay analytically from these polynomials, accounting for gravity and slope effects on the terrain.

Step 4: Constrained Optimization

An optimization solver (Powell-Hestenes-Rockafellar augmented Lagrangian method) minimizes jerk (smooth acceleration changes) while enforcing:

  • Steering angle limits (the robot's front wheels have a max turn radius)
  • Speed bounds (minimum and maximum velocity)
  • Acceleration limits (terrain slope affects how hard the robot can push without slipping)
  • Attitude constraints (pitch and roll must stay below tipping thresholds)
  • Traversability scores from Step 2 (prefer high-score terrain)
  • Obstacle avoidance (stay clear of detected hazards)

The Trick: By parameterizing in SE(2) and using terrain-aware kinematic models, the planner runs 3–5 times faster than prior methods and can even reverse the robot if backward motion saves time on mountainous terrain.

Vision-Based Movement Primitives for Lunar Hazard Avoidance

The big idea — first principles

The problem. A lunar rover must execute pre-planned driving routines (circles, raster scans, pickup-and-return) while dodging rocks it did not expect. Re-planning from scratch is slow; purely reactive steering can loop forever or veer off mission. The rover cannot wait for Earth-based commands.

The approach. Encode mission patterns as dynamic movement primitives (smooth, learnable trajectory templates). As the rover drives, a vision system watches for rocks. When one appears, inject a deflection into the DMP's attractor dynamics to bend the path around it without halting or replanning.

What's unique. DMPs naturally absorb small perturbations; their attractor structure means local obstacle corrections do not break global mission coherence—the rover stays on mission while reacting to surprises as fast as vision can detect them.

What it does

This work enables an autonomous lunar excavator (IPEx) to follow engineered driving patterns while detecting and dodging rocks in real time. It combines parameterized trajectory templates (dynamic movement primitives, or DMPs—smooth pre-designed motion patterns with adjustable parameters) with a vision module that spots hazards and locally warps the planned path around them. This is a reactive-nav approach: the robot commits to a high-level mission pattern, then reflexively avoids obstacles it sees, without replanning from scratch.

The method, in detail

The setup: The IPEx rover needs to execute specific driving routines: cycling between excavation and unloading sites, sweeping around the lander, raster scans for mapping. These are encoded as dynamic movement primitives (DMPs)—a learned control framework where complex trajectories are represented as low-dimensional parameter vectors. Instead of storing full joint or wheel velocity sequences, a DMP encodes the motion as an attracting differential equation; you set the target and parameters, and the DMP smoothly generates motion toward it.

The trick: For each DMP template, a vision-based obstacle avoidance subsystem watches the rover's onboard camera feed in real time. When rocks appear (detected via image analysis of the terrain ahead), the system computes a deflection vector—how far off the current path the rover must move to clear the obstacle. This deflection is injected into the running DMP as a perturbation, bending the trajectory around the rock without halting execution or re-optimizing.

The exact flow:

  • Load mission (e.g., "drive in a 50 m circle, then return"). That mission is instantiated as one or more DMP trajectories with their parameters.
  • Begin executing the DMP trajectory on the rover's drive system (wheel commands at each timestep).
  • At each control cycle, the vision system scans the image for potential rock hazards in the near-term path.
  • If a rock is detected within collision distance, compute the avoidance deflection and modulate the DMP's target or gain to steer around it.
  • Resume the original DMP as soon as the obstacle clears.

Why it works: DMPs naturally accommodate small perturbations; their attractor dynamics absorb local control corrections without losing global coherence. Lunar terrain—rough, shadowy, often textureless—demands fast, local reactions that don't bottleneck on global re-planning or communication delays. By coupling a simple vision detector to a flexible learned trajectory, the method avoids the brittleness of purely reactive steering (which can get stuck in local loops) and the latency of trajectory optimization.

        self.num_points = len(target_points)
        self.target_points = target_points

        # Cluster points using AffinityPropagation or KMeans
        if self.num_points > 16:
            self.yhat, self.cluster_ids, self.cluster_points_count = \
                try_cluster_points(target_points, max_tries=3)
        else:
            self.yhat = np.arange(self.num_points)  # One cluster per point if few keypoints

        # Build two-level graph:
        # L0: individual keypoints (within-cluster dense edges)
        # L1: cluster centers (dense edges between all clusters)
        self.cluster_centers_index = []
        self.belong_cluster_index = np.zeros(len(self.target_points), dtype=np.int64)
        
        for i, c_id in enumerate(self.cluster_ids):
            mask = (self.yhat == c_id)
            cluster_points = target_points[mask]
            cluster_points_index = np.nonzero(mask)[0]
            cluster_median_pos = np.median(cluster_points, axis=0)
            
            # Pick closest point to cluster median as cluster center
            dist2median = np.linalg.norm(cluster_points - cluster_median_pos, axis=-1)
            min_dist_idx = np.argmin(dist2median)
            cluster_center_idx = cluster_points_index[min_dist_idx]

            l0_dense_edge_index.append(gen_dense_connect_edges(cluster_points_index))

            l0_to_l1_edge_index_j.append(cluster_points_index)
            l0_to_l1_edge_index_i.append(np.ones_like(cluster_points_index) * i)
            
            self.cluster_centers_index.append(cluster_center_idx)

        x_tar_clu = self.get_clu(x_tar, x_tar, pos_tar, pos_tar, l0_to_l1_edge_index, centers_index)
        
        # Concat current and difference (target - current)
        x_clu = torch.cat([x_cur_clu, x_tar_clu - x_cur_clu], dim=-1)
        x_clu = F.relu(self.out_enc(x_clu)) * cluster_mask.float().unsqueeze(-1)
        return x_clu

The key innovation: soft match probabilities (from the frontend detector) are encoded as uncertainty in the point positions themselves. The graph structure captures which points belong to the same visual region (clusters), and the network learns to aggregate uncertainty across clustered features.

The end-to-end inference pipeline

In cns/benchmark/pipeline.py, the CorrespondenceBasedPipeline.getcontrolrate() method runs the full servo step:


def get_control_rate(self, image: np.ndarray):
    """
    Arguments:
    - image: np.ndarray, bgr image (Note: here is bgr not rgb)
    
    Returns:
    - vel: np.ndarray, shape=(6,), [vx, vy, vz, wx, wy, wz], 
        camera velocity in camera coordinate
    - data: GraphData object for visualization or stopping criteria
    - timing: dict with frontend_time, midend_time, backend_time
    """
    timing = {"frontend_time": 0, "midend_time": 0, "backend_time": 0, "total_time": 0}

    # Step 1: Extract and match keypoints
    t0 = time.time()
    corr = self.frontend.process_current_frame(image)  # SIFT/ORB/SuperGlue matching
    timing["frontend_time"] = time.time() - t0

    if corr is None:  # No matches found
        vel = np.zeros(6, dtype=np.float32)
        data = None
    else:
        # Step 2: Convert matches → graph structure
        t0 = time.time()
        data = self.midend.get_graph_data(corr)
        timing["midend_time"] = time.time() - t0

        # Mark scene change (reset temporal state)
        if self.new_scene:
            data.start_new_scene()
        data.set_distance_scale(self.dist_scale)  # Add estimated depth prior
        self.new_scene = False

        # Step 3: Run neural controller
        t0 = time.time()
        vel = self.control(data)  # GraphVSController.__call__
        timing["backend_time"] = time.time() - t0

        # Store images for stopping criterion
        setattr(data, "cur_img", image)
        setattr(data, "tar_img", corr.tar_img)

    timing["total_time"] = timing["frontend_time"] + timing["backend_time"]
    return vel, data, timing

The neural controller (backend)

In cns/benchmark/controller.py, the GraphVSController loads the trained model and maintains hidden state:


class GraphVSController(object):
    def __init__(self, ckpt_path: str, device="cuda:0"):
        self.device = torch.device(device)
        ckpt = torch.load(ckpt_path, map_location=self.device)
        self.net: GraphVS = ckpt["net"]  # Load pretrained GraphVS model
        self.net.eval()
        self.hidden = None  # Temporal state (GRU)

    def __call__(self, data: GraphData) -> np.ndarray:
        with torch.no_grad():
            data = data.to(self.device)
            
            # Reset hidden state on new scene
            if getattr(data, "new_scene").any():
                print("[INFO] Got new scene, set hidden state to zero")
                self.hidden = None

            # Forward pass through graph neural network
            raw_pred = self.net(data, self.hidden)
            self.hidden = raw_pred[-1]  # Extract GRU hidden state for next frame
            
            # Denormalize raw predictions to actual velocity
            vel = self.net.postprocess(raw_pred, data)

        vel = vel.squeeze(0).cpu().numpy()
        return vel  # [vx, vy, vz, wx, wy, wz] in camera frame

The network architecture (GraphVS)

In cns/models/graph_vs.py, the network processes the graph through three stages:


class GraphVS(nn.Module):
    def __init__(self, input_dim, pos_dim, hidden_dim=128, regress_norm=True):
        super().__init__()
        self.regress_norm = regress_norm
        self.encoder = Encoder(input_dim, hidden_dim, pos_dim)
        self.backbone = Backbone(hidden_dim, pos_dim)
        self.decoder = Decoder(hidden_dim, regress_norm)
    
    def forward(self, data: GraphData, hidden: Optional[torch.Tensor] = None):
        # Extract graph structure
        x_cur = getattr(data, "x_cur")        # Current keypoint features
        x_tar = getattr(data, "x_tar")        # Target keypoint features
        pos_cur = getattr(data, "pos_cur")    # Current point positions (normalized)
        pos_tar = getattr(data, "pos_tar")    # Target point positions
        
        l1_dense_edge_index_cur = getattr(data, "l1_dense_edge_index_cur")
        l1_dense_edge_index_tar = getattr(data, "l1_dense_edge_index_tar")
        l0_to_l1_edge_index_j_cur = getattr(data, "l0_to_l1_edge_index_j_cur")
        l0_to_l1_edge_index_i_cur = getattr(data, "l0_to_l1_edge_index_i_cur")
        
        cluster_mask = getattr(data, "cluster_mask")
        cluster_centers_index = getattr(data, "cluster_centers_index")

        # Stage 1: Encode current and target into cluster-level difference features
        x_clu = self.encoder(
            x_cur, x_tar, pos_cur, pos_tar, cluster_mask, 
            l0_to_l1_edge_index_cur, cluster_centers_index)
        pos_clu = pos_tar[cluster_centers_index]  # Use target positions as cluster positions
        batch_clu = batch[cluster_centers_index]

        # Stage 2: Process through temporal GRU backbone
        # PEConvGRU aggregates information across clusters frame-to-frame
        if hidden is None:
            hidden = self.init_hidden(getattr(data, "num_clusters").sum()).to(x_cur)
        
        hidden, x_clu = self.backbone(
            hidden, x_clu, pos_clu, l1_dense_edge_index_cur, l1_dense_edge_index_tar, batch_clu)

        # Stage 3: Decode to 6-DoF velocity
        # Output: (1) direction vector [v_x, v_y, v_z, w_x, w_y, w_z]
        #         (2) log-scale magnitude (optional, if regress_norm=True)
        vel_si_vec, vel_si_norm = self.decoder(x_clu, cluster_mask, batch_clu)
        
        return vel_si_vec, vel_si_norm, hidden

Postprocessing: denormalization to real velocity

The network outputs are normalized (independent of camera intrinsics and scene scale). The postprocess() function in cns/models/functions.py scales them:


def postprocess(raw_pred, data: GraphData, post_scale: bool) -> torch.Tensor:
    vel_vec, vel_norm = raw_pred[0], raw_pred[1]  # Direction & magnitude
    
    # Combine direction and magnitude
    if vel_norm is None:
        vel = vel_vec
    else:
        vel = vel_vec / (torch.norm(vel_vec, dim=-1, keepdim=True) + 1e-7) * \
            alpha_p_elu(vel_norm, alpha=1)  # alpha_p_elu = alpha + elu(x)
    
    # Scale by distance prior (estimated depth)
    if post_scale:
        vel = vel.clone()
        vel[:, :3] *= getattr(data, "tPo_norm").view(-1, 1)  # tPo_norm is distance_scale
    
    return vel

The distancescale (set via pipeline.settarget()) represents the estimated depth from camera to scene. The network learns normalized control that adapts to real 3D scales via this scalar multiplier.

The core idea in code — SE(2) planning on uneven terrain

1. Terrain Representation: SE(2) Grid with Risk Scoring

SE(2) Grid (/src/unevenmapping/se2grid/se2gridcore/include/se2gridcore/SE2Grid.hpp):

Risk computation (from helpermath.h + terrainanalyzer config):

  • For each grid cell, for each yaw heading: sample terrain points at the robot's footprint (ellipsoid)
  • Compute curvature κ_ter (terrain roughness from normal variation)
  • Compute body pitch angle φx and roll angle φy (from local slopes)
  • Fuse into risk score:
    • 
  risk(x, y, yaw) = w_φ * (φ_x² + φ_y²) + w_κ * κ_ter²

If risk > threshold → cell is blocked.

The output is a volume: risk[yawidx](row, col) for each heading discretization.

void ReplanFSM::execFSMCallback(const ros::TimerEvent &e) {
    switch (exec_state_) {
        case SEQUENTIAL_START:
            init_state_ << cur_pos_, cur_yaw_, cur_vel_;
            planner_.setInitStateAndInput(init_state_, start_time);
            if (!planner_.process()) {  // **Calls PlanManager::process() → KinoAstar + SE(2) opt**
                break;
            }
            planner_.publishSimTraj2Controller();
            changeFSMExecState(EXEC_TRAJ, "FSM");
            break;
    }
