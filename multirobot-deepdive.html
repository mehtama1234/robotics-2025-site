Getting several robots to work together

145 papers · decide — how a team of robots picks who does what and stays coordinated

The big picture — connecting the dots

The hard part of multi-robot work is not the robots — it is the coordination. One robot decides its own next move and lives with the consequences. Ten or ten thousand robots must all know what the others are planning, detect when a plan breaks, and regroup without a person telling each one what to do. The central tension running through this group of papers is simple: coordination cannot live on a single central server, and yet it cannot work if every robot acts alone. A plan that works on paper — robot A picks up the object while robot B clears the path — will fail the moment robot B gets stuck or the network hiccups. The field's answer is converging on hybrid strategies: use a central LLM to propose a sensible decomposition once, then drop the work to distributed solvers or learned policies that can handle real-time failures without calling home. Everything below is people testing where that boundary belongs.

Five distinct angles of attack:

  • ① Propose once, execute distributed. COHERENT uses an LLM to break a task into robot-specific assignments, then watches each robot execute and feeds failures back to the model for re-planning. DELTA splits reasoning across two layers: LLM proposes sub-goals, a classical planner fills in verified action sequences, no LLM running live on the robot. LaMMA-P adds a logic checker so proposed plans are guaranteed feasible before robots move.
  • ② Move thousands without crashing. SIGMA uses mathematics (sheaf theory) to let each robot act as though it sees the global picture using only local information. Deploying Ten Thousand Robots learns to copy a fast classical planner and runs it on GPU for throughput classical methods cannot match. A learned planner with a collision-fixer outperforms both, trading bulk compute for post-hoc correction.
  • ③ Hold formation, reshape on command. Coordinated Multi-Robot Navigation with Formation Adaptation layers graph neural networks to decide reshaping with rigid collision avoidance at the bottom. ZeroCAP interprets a spoken instruction ("form a ring") by combining vision-language and language models to compute target positions with zero task-specific training.
  • ④ Mix people and robots as one team. Adaptive Task Allocation in Multi-Human Multi-Robot Teams trains two coupled learning loops: who-does-what at the top, real-time reassignment at the bottom when someone is slow or gone. Hypergraph-Based Coordinated Task Allocation models people, robots, and locations in one graph, training all three to pick tasks together. TriHRCBot solves the specific case of a robot holding an object steady for two people simultaneously.
  • ⑤ Survive network and robot failure. Cooperative Distributed Model Predictive Control runs the planning algorithm on every robot at once, using a message-passing trick (ADMM) so neighbors trade answers until all agree — no central server needed. FogROS2-PLR floods requests to multiple cloud servers and uses whichever reply arrives first, treating latency as the constraint, not reliability.

The throughline: the field is learning to separate what should happen (LLM or logic layer) from how to handle the mess when reality diverges (distributed execution, learned shortcuts, failure detection). No single paper has solved true real-time coordination of thousands of diverse robots in dynamic environments, but the 2025 work is productively messy: tighter feedback loops, better logic checkers, faster learned solvers, and growing acceptance that some work belongs distributed and some belongs in the cloud. Still open: teams recovering from cascading multi-robot failures without re-planning; truly scalable collision-free paths for more than ten thousand robots; and coordination layers that work as fast as the environment changes — environments that rewrite themselves in seconds still overwhelm the fastest planning systems.

The problem — in depth

A single robot already has a hard job. It must read its sensors, figure out where it is, decide what to do next, and then move its body — all in real time, in a world that keeps changing. Now multiply that by ten, or a hundred, or ten thousand robots that must all share a single goal.

The new difficulties are not just more of the same. They are different in kind.

First, the team may be made of different robot types. A drone can fly over a wall; a wheeled robot cannot. A robot arm can pick up a box; a drone cannot. When a shared task needs several of these steps in order — fly here, pick this up, carry it there — someone or something must figure out who does which part. Do it wrong and the whole job stalls.

Second, each robot can only see a small patch of the world at once. What one robot learns — an obstacle just appeared, a path is blocked — the others do not automatically know. The team must share information, but passing everything to everyone all the time is too slow and uses too much radio bandwidth.

Third, when a task has many steps across many robots, the number of possible orderings and assignments grows extremely fast. A plan that looks fine at the top level can turn out to be physically impossible once you check the details: the robot assigned to step four is already busy with step three and cannot be in two places at once.

Fourth, real robots fail. A battery dies. A sensor glitches. A drone falls. The rest of the team must notice this and keep going — without a person stepping in every time.

All of this connects directly to the central problem every robot faces: the world is messy and incomplete, time is short, and bodies are fragile. One robot managing its own slice of reality is already hard. A team that must coordinate slices is harder by an order of magnitude, because a mistake by one robot can cascade and ruin the work of every other.

The approaches — how the field actually tackles it

Using a language model to divide and assign work

In plain termsYou have a smart assistant (an LLM) that understands what you want, but it doesn't know what's actually possible — like telling a friend to carry a piano up a narrow staircase without checking. The trick: have it make a guess, watch what fails, then ask it to fix it and try again.
The sub-problemLanguage models understand tasks and sequences well, so they can break a mission into sensible pieces for different robots — but they do not know what is physically possible. Left alone, they produce infeasible plans. Pairing an LLM with a feasibility checker lets it propose and revise.
Propose once, revise on failure — COHERENT (ICRA). An LLM proposes a plan for heterogeneous robots, each robot tries its assigned subtask, and reports back success or failure; the LLM revises and loops until done.
LLM sets goals, logic planner fills in the moves — LaMMA-P (ICRA). The LLM decomposes the task into intermediate sub-goals; a formal planner (PDDL) finds provably feasible action sequences for each.
Separate reasoning from execution — DELTA (ICRA 2025). The LLM breaks down the task into ordered sub-goals, then a classical planner fills in low-level moves without the LLM running on each robot.
Ask once before training — YOLO-MARL (ICRA). The LLM writes out strategies and helper functions once before training starts; robots then train using those rules without calling the model again.

Pairing language models with formal planners or offline learning sidesteps hallucination and keeps feasibility checking tight — the LLM handles flexible reasoning, the planner or learned policy handles verified execution.

Moving many robots without collisions

In plain termsA thousand robots in one room all rushing to different destinations creates far too many collision possibilities for old-school math to solve in time. Instead, teach a quick learner to predict good paths, then let it run millions of scenarios in parallel on a GPU.
The sub-problemDozens or thousands of robots sharing one space create a combinatorial explosion of possible conflicts. Paths must not cross at the same moment, and the system must resolve conflicts faster than classical planners can handle at scale.
Learn to copy a fast classical planner — Deploying Ten Thousand Robots (ICRA). A neural network trained to mimic classical search-based planning can run on GPU and plan for ten thousand agents in parallel, matching quality and beating classical speed.
Local decisions, global coordination via math — SIGMA (ICRA 2025). Each robot acts on only its local view via a learned policy, but they coordinate using sheaf theory, a mathematical framework that connects every robot's view to the whole picture.
Simple learned planner plus collision-fixer — Work Smarter Not Harder (ICRA). A small neural network learns from a good classical planner, then a lightweight post-hoc fixer detects and corrects one-step conflicts in the network's output — outperforms much more elaborate methods.

Learned policies with post-hoc correction or sheaf-theoretic decentralization beat pure classical methods on throughput at scale while staying collision-free.

Holding a formation and reshaping it

In plain termsA flock of birds flies as a tight V to save energy and coordinate, and when they hit a canyon, they automatically squeeze into a line without anyone calling out orders. Robots need the same thing — move together as one shape that reshapes itself to fit the world.
The sub-problemA team often needs to move as a single shape — a line, triangle, or ring — while fitting through narrow spaces and avoiding obstacles. The right formation changes with the environment; robots must reshape themselves without explicit commands for each robot.
Two-layer control: network plans reshaping, robots steer — Coordinated Multi-Robot Navigation with Formation Adaptation (ICRA). A graph neural network decides when and how to reshape the group; each robot independently avoids collisions and steers itself, with spring-damper physics smoothing the shape changes.
Spoken commands to target positions — ZeroCAP (ICRA). A vision-language model understands the scene and a language model interprets a spoken command like "form a ring"; the system computes target positions for each robot with zero task-specific training.

Two-layer control and vision-language understanding let teams reshape themselves in real time without pre-programming every formation pattern.

Splitting jobs across a mixed team including people

In plain termsA team of people and robots building a house together starts with a plan — Alice paints while Bob carries. But Alice gets tired or runs out of paint. The system notices and shifts tasks on the fly: maybe Bob finishes the last wall while Alice restocks supplies.
The sub-problemTeams with both robots and people must share a workspace and reassign work in real time as people slow down, become unavailable, or tasks change mid-way. The system must watch for changes and update the assignment without halting the whole job.
Two-level learning: top assigns tasks, bottom reassigns on change — Adaptive Task Allocation in Multi-Human Multi-Robot Teams (ICRA). The top learning layer assigns tasks based on who is best at what; the bottom layer watches for changes and reassigns when needed.
One graph for robots, people, and locations — Hypergraph-Based Coordinated Task Allocation (ICRA). A hypergraph model links robots, people, and task locations together; a single shared learning process trains all three to pick tasks and avoid collisions at once.
Robot holds an object for two people simultaneously — TriHRCBot (ICRA). Watches both people with cameras and continuously moves the object to a position where both can reach it comfortably.

Joint learning across human and robot agents, with real-time reassignment and spatial awareness, keeps mixed teams coordinated through changes and task sharing.

Running the plan when the network or a robot fails

In plain termsImagine a factory floor where every robot calls headquarters for permission to move, then headquarters crashes — everything stops. Instead, each robot should solve the puzzle locally by talking only to its neighbors, so if the headquarters goes dark, the work keeps flowing.
The sub-problemA team relying on a central server stops working the moment that server goes down or the network hiccups. Fault tolerance requires every robot to solve the shared problem on its own, coordinating with neighbors without calling home.
Every robot plans on its own, neighbors trade answers — Cooperative Distributed Model Predictive Control (ICRA). Each robot solves the shared control problem locally and swaps partial answers with neighbors using a mathematical splitting method (ADMM) until all robots agree on a plan — no central server needed.
Flood requests to multiple servers, use the fastest reply — FogROS2-PLR (ICRA). Sends each computation request to several cloud servers over multiple paths and uses whichever answer arrives first, treating latency as the constraint, not reliability.

Decentralized consensus or redundant-cloud strategies eliminate single points of failure and let teams keep working through network delays and server outages.

Where it stands

Language models have made it much easier to write a sensible first plan for a mixed robot team from plain instructions, especially when paired with a logic checker that catches impossible steps. Moving many robots without collisions has improved sharply, with learned methods now approaching classical planners in quality and beating them in speed at large scale. Formation control and reshaping in real environments works in tested settings. What remains hard: teams that must reorganize themselves fully after multiple failures at once, teams that are much larger than tested so far (the jump from a hundred to ten thousand is still not smooth for many methods), and coordination in dynamic spaces where the environment changes faster than any plan can keep up with.

COHERENT: Collaboration of Heterogeneous Multi-Robot System with Large Language Models

The big idea — first principles

The problem. A team of different robot types (drone, legged robot, arm) must split a complex task into pieces, but each piece only certain robots can do. Asking an LLM to plan the whole thing at once produces infeasible steps; asking humans is slow.

The approach. Have an LLM propose one layer of subtasks and assign each to the right robot type, then watch each robot act and feed failures back to the model. The LLM revises and loops until the job is done.

What's unique. Instead of planning every action upfront, COHERENT uses a tight feedback loop where the LLM stays at the task-assignment level and each robot reports what actually broke. This keeps the LLM focused on where it is strong (reasoning about task structure) and away from low-level action hallucinations.

ICRA 2025 · 14 citations · llm-task-allocation

What it does

A language model breaks down a complex task into subtasks and assigns each to the right robot type (drone, legged robot, or arm), then watches as each robot acts and reports back, adjusting the plan in a loop until the task is done. This solves the problem that simpler LLM planners only work on teams of identical robots doing simple tasks.

Sub-approach: llm-task-allocation — a centralized LLM decomposes and allocates tasks across a heterogeneous robot team.

The method, in detail

Input and setup: You give the system a task description (e.g., "fetch the apple from the table and place it on the shelf"), a description of each robot's capabilities (quadrotor can fly and grasp, legged robot can climb stairs, robotic arm can reach high), and a scene representation as a graph (facts like "apple is on coffee table").

Proposal step: GPT-4 (specifically gpt-4-0125-preview) acts as the centralized task assigner. It receives a composite prompt containing the task, robot capabilities, scene facts, and a dialogue history of recent iterations (the system keeps only the last five loops to stay efficient). GPT-4 reads all this and outputs a decomposition: subtasks assigned to specific robot types, e.g., "quadrotor: fly to kitchen, legged_robot: fetch apple from table, arm: place apple on shelf."

Execution step: Each robot executor (also using GPT-4) receives its assigned subtask, its own action list (a predefined set of feasible actions for the current state), and partial observations of its environment. It picks one action to execute from that list, e.g., selecting "[grab] apple" from actions like \[move\], \[grab\], \[release\].

Feedback step: After acting, each robot reports self-reflection feedback to the task assigner, categorizing what happened: (1) failure (wrong step, wrong assignment, or the robot cannot execute), (2) success with partial progress (subtask partially done, needs more steps), or (3) success complete (subtask fully done).

Adjustment step: The task assigner reads all the feedback, appends it to its dialogue history, and generates a new proposal. The cycle repeats until all subtasks succeed.

The trick that makes it work: The system does not try to plan everything at once (which LLMs are bad at). Instead, it uses a tight feedback loop: propose one layer of subtasks, see what breaks, adjust, repeat. This keeps the reasoning focused and lets each robot report actionable information.

DELTA: Decomposed Efficient Long-Term Robot Task Planning Using Large Language Models

The big idea — first principles

The problem. Long robot tasks like "clear the table" require many steps in order. Pure LLM planning hallucinates infeasible action sequences. Pure classical planning is rigid and cannot reason about task structure from natural language.

The approach. Use the LLM to break the task into ordered sub-goals, and use a classical planner (PDDL + FastDownward) to find provably feasible action sequences for each sub-goal one at a time.

What's unique. DELTA separates the LLM's strength (flexible reasoning about task intent from language) from the planner's strength (guaranteed collision-free, physics-respecting execution). The scene graph grounds the LLM so it cannot make unfounded assumptions about the environment.

ICRA 2025 · 12 citations · LLM-based task decomposition and sequential planning

What it does

DELTA solves the problem of long-horizon robot planning by having an LLM break a complex task into a sequence of simpler sub-goals, which are then solved one at a time by a traditional automated planner. Instead of asking the LLM to generate every single action (which causes hallucinations), DELTA uses the LLM only for high-level reasoning and delegates low-level action sequencing to a formal planner. This is the llm-task-allocation sub-approach: the LLM decomposes and allocates sub-tasks, leaving the planner to handle the details.

The method, in detail

DELTA's pipeline has five sequential steps:

1. Domain Generation. The system takes a natural-language description of the robot's capabilities and the environment rules, then prompts an LLM (GPT or Llama) to generate a formal PDDL domain file—a declarative specification of what actions are possible and what their preconditions and effects are. This is a one-shot prompt; no training happens here.

2. Scene Graph Pruning. The environment is represented as a 3D scene graph (3DSG), which captures objects and their spatial relationships. The LLM is prompted to read this graph and prune away irrelevant objects—if the task is "pick up a fork," the LLM filters out furniture that has nothing to do with the task, leaving only objects, receptacles, and surfaces that matter.

3. Problem Generation. Given the pruned scene graph and the task goal in natural language, the LLM generates a PDDL problem file—a concrete specification of the initial state (which objects are where) and the goal condition (what state must be reached). Again, one-shot prompting; the LLM grounds its knowledge into the specific environment snapshot.

4. Goal Decomposition. The LLM is prompted to break the overall goal into an ordered sequence of intermediate sub-goals. For example, "clear the table" might decompose into: (1) locate all dirty dishes, (2) move each dish to the sink, (3) fill sink with water, (4) wash dishes, (5) dry and return. The LLM generates these as textual sub-goals.

5. Autoregressive Sub-task Planning. For each sub-goal in sequence, the system runs a classical automated task planner (such as FastDownward or similar) on the PDDL domain and a new PDDL problem derived from that sub-goal. The planner generates a concrete action sequence. If planning fails or the planner finds the sub-goal infeasible, this failure is reported; otherwise, the plan for that sub-goal is executed (in simulation or on the real robot), and the system moves to the next sub-goal.

The trick that makes it work: By decomposing via LLM and then delegating to a classical planner, DELTA avoids the LLM's tendency to hallucinate infeasible action sequences. The LLM's strength (understanding high-level task intent) is separated from the planner's strength (finding provably feasible, collision-free, physics-respecting action sequences). Scene graphs ground the LLM's reasoning to actual environment state, preventing the LLM from making unfounded assumptions.

LaMMA-P: Generalizable Multi-Agent Long-Horizon Task Allocation and Planning with LM-Driven PDDL Planner

The big idea — first principles

The problem. Heterogeneous robot teams must break down household tasks, assign each piece to the right robot (based on its capabilities), and execute collision-free. LLMs are flexible but hallucinate; classical planners are correct but rigid.

The approach. Use the LLM to identify preconditions and decompose tasks into PDDL-shaped subtasks; match each subtask to robots by capability; then run the classical planner to generate verified action sequences for each robot.

What's unique. LaMMA-P structures LLM outputs so they fit exactly into PDDL format, gaining both LLM flexibility for reasoning and classical planner correctness. The system loops—if a plan fails validation, the LLM regenerates it with corrected preconditions.

ICRA · 10 citations · llm-task-allocation

What it does

LaMMA-P combines a large language model with a classical logic planner (PDDL) to break down complex, multi-step household tasks and automatically assign each piece to the right robot in a heterogeneous team. The LLM handles high-level reasoning about what needs to happen; the logic planner converts those decisions into concrete, verifiable action sequences each robot can execute. This is a hybrid approach that avoids the hallucinations of pure LLM planning while keeping the flexibility LLMs bring to natural language understanding.

Sub-approach: llm-task-allocation

The method, in detail

The system runs as a pipeline with five steps:

1. Task Decomposition (Precondition Identifier): The LLM receives the raw task description (e.g., "Put the egg in the fridge") in a few-shot prompt that teaches it to output structured subtasks. For each subtask, the model identifies preconditions (e.g., the robot must reach the egg first) and expected effects (e.g., egg is now in hand). The key insight is that LLMs often generate sensible action sequences better than classical relaxed planning heuristics, because they have seen countless examples of real-world task flows.

2. Task Allocation: A dedicated module matches each decomposed subtask to the right robot based on its capabilities (a quadrotor can pick things up from high shelves; a legged robot can navigate rough terrain). The system also identifies which subtasks can run in parallel to speed up overall execution.

3. PDDL Problem Generation: Each allocated subtask becomes a formal Planning Domain Definition Language problem. Objects (Robot, Egg, Plate, Fridge) are declared with types; the initial state specifies where each object is; the goal specifies what must be true at the end (egg inside fridge). This formal structure is what lets the classical planner reason with mathematical certainty.

4. Fast Downward Planning: The Fast Downward planner takes the PDDL problem and produces a guaranteed collision-free, feasible sequence of concrete actions (e.g., Move(Robot, Kitchen), Pickup(Egg), Move(Robot, Fridge), Open(Fridge), Place(Egg, Fridge)). Classical planners are slow for very large problems, but excellent at finding correct solutions for medium-scale ones.

5. Validation and Iterative Refinement: The generated plan is checked against the domain rules. If it fails validation (e.g., the robot tries to pick up an object it cannot reach), the LLM is asked to regenerate the subtasks with corrected preconditions. This loop repeats until a valid plan emerges.

The specific trick: Most systems choose either pure LLM planning (fast, flexible, but often infeasible) or pure classical planning (slow, correct, but rigid). Enhancing Multi-Agent Systems via Reinforcement Learning with LLM-Based Planner and Graph-Based Policy

The big idea — first principles

The problem. Multi-agent RL on complex tasks is slow because agents must learn everything from scratch. LLM planning is flexible but runs slowly on every robot at every step.

The approach. An LLM planner breaks down the task once and builds a dependency graph showing which agents must coordinate with which. Each robot then runs a learned graph-aware policy that reads this shared graph and coordinates implicitly without calling the LLM again.

What's unique. The dependency graph is the bridge between LLM reasoning (done once, offline) and learned execution (done at full speed, distributed). The policy inherits structure from the LLM's decomposition, so agents learn faster than from raw observations alone.

ICRA 2025 · 5 citations · multi-agent-rl

What it does

LGC-MARL (LLM-based Graph Collaboration MARL) teaches a team of robots to split up complex tasks and coordinate in real time by combining an LLM planner with a graph neural network policy. The LLM breaks down high-level instructions into executable subtasks and maps which agents must work together, then each robot uses a graph-aware policy to decide its own actions without constant LLM queries. This is multi-agent reinforcement learning that inherits reasoning from LLMs but scales faster than pure LLM-based methods.

The method, in detail

The LLM planner takes a natural language task description and the current environmental state (what agents see). It generates an ordered list of executable subtasks—concrete actions like "go to the kitchen" or "pick up the object"—rather than leaving decisions to chance. Crucially, it also builds a directed acyclic graph (DAG) encoding *which agents must coordinate with which others*. For example, if Agent 1 must pick up an object before Agent 2 can move it, the graph captures that dependency. If the planner generates something wrong, a second LLM instance (the critic) flags factual errors and sends feedback back, so the planner can fix its plan in a loop. This avoids long, wasteful LLM tokens spent on dialogue.

The action dependency graph is the core innovation. The LLM outputs this as text describing decision dependencies among agents (e.g., "Agent 1's action must precede Agent 2's action"), which gets converted to an adjacency matrix M. Each row/column represents an agent, and the matrix encodes the partial order of who acts when. Agents read this graph like a schedule.

The graph-based collaboration policy is where the actual robot control happens. Each agent i receives: (1) its own local observation o^i, (2) the adjacency matrix M (the dependency graph), and (3) the set of assigned subtasks T. The agent's policy πm^i reads M to find which other agents' actions it should condition on (its "parents" in the graph), observes those actions, and then picks its own action—ai. Mathematically: πm^i(a^i | o^i, a^parents(i)~M; T). The policy is a neural network trained with policy gradient: ∇log πm^i(a^i | ...) × Q^pim(s, a), where Q^pim is a learned value function. Multiple agents train in parallel using a centralized critic (which sees all observations and actions for better value estimates) but decentralized execution (each robot runs its own policy locally).

Meta-learning is the trick for handling new environments. Instead of retraining from scratch on each new AI2-THOR scene, the agents use meta-learning algorithms (similar to MAML) so the policy can rapidly adapt within a few gradient steps when placed in a new task or environment. The policy parameters are tuned by experience, not by asking the LLM again.

Reward function design is also LLM-driven. The planner generates modular reward functions that balance individual robot rewards (e.g., "get to location X") with team rewards (e.g., "minimize total time"). The LLM reasons through intermediate steps explaining why each component matters, grounding the rewards in the task semantics. This replaces hand-tuned reward engineering.

Training setup: Experience from all agents is collected into a replay buffer D. Batches are sampled, and Q-function is updated via: Q^pim(s, a) ← r + γ × max Q^pim-(s', a'), where Q^pi_m- is a target network (frozen copy updated periodically). Policy is updated using the gradient from the Q-function.

The big idea — first principles

The problem. Heterogeneous robot teams (quadrotor, legged robot, arm) must split long-horizon missions, but LLMs producing infeasible plans for tasks they don't fully understand.

The approach. Expose robot capabilities as API tools to the LLM, so it can only propose feasible subtasks. Assign each subtask to robots by capability. Execute and collect feedback from real robots when tasks fail, then replan via LLM.

What's unique. The LLM reasons at the subtask level using capability-checking APIs as guardrails, keeping it away from low-level action details. The real robot feedback (e.g., "my arm can't reach that shelf") feeds back into replanning, enabling adaptation to real robot limits.

What it does

This work solves the problem of planning complex, long-horizon missions for teams that mix different robot types—quadrotors, legged robots, and arms. Unlike prior LLM-based planners that assume robots are all identical or handle simple tasks, this method grounds the LLM's reasoning in the actual constraints and action spaces of each robot type. It uses an LLM to decompose the overall mission into subtasks, assigns each subtask to the robot best suited for it, and then refines the plan as robots report back what actually worked during execution. This is a mission-planning approach: the LLM stays at the high level, deciding *what* each robot should do given its capabilities, while a scheduler ensures each assignment respects robot constraints.

The method, in detail

Three stages: Subtask Generation, Subtask Assignment, Subtask Refinement

  • Input Setup: The system receives (a) a natural-language mission goal like "carry the package from Room A to Room B and place it on the shelf," and (b) a structured description of the team: for each robot, its name, type, capabilities (traversability, perception, manipulation), and constraints (e.g., a UAV cannot manipulate objects, a wheeled robot cannot climb stairs).
  • Subtask Generation (the LLM's job): The LLM reads the mission and the capability list, then generates a sequence of subtasks. For example: "Subtask 1: Navigate to Room A (any mobile robot), Subtask 2: Pick up the package (robotic arm), Subtask 3: Navigate to Room B with the package (mobile manipulator), Subtask 4: Place the package on the shelf (robotic arm)." The LLM does this using specialized APIs that expose robot capabilities as callable tools—these APIs ground the LLM's reasoning so it cannot suggest impossible actions.
  • Subtask Assignment: Each subtask is matched to one or more robots. The system checks feasibility: Can this robot actually do this task given its action space? For instance, if a task is "fly to 50 meters altitude," only quadrotors can do it. The assignment also considers sequencing: some subtasks may need to happen in parallel, others in sequence.
  • Online Execution and Feedback: Robots execute their assigned subtasks. Each robot reports back: "I succeeded at Task X" or "I failed because I hit an obstacle" or "The shelf is at height 2.5m but my arm only reaches 2.2m." This feedback is critical.
  • Refinement Loop: The LLM receives this feedback and adjusts the plan. If a task fails, the LLM re-decomposes: "Instead of placing the package on the high shelf, place it on the lower shelf," or "Dispatch the larger arm robot instead of the smaller one." The system loops until the mission completes or declares failure.

The key trick: The LLM is never asked to predict the exact low-level actions (joint angles, velocity commands). Instead, it reasons at the subtask level using the API tools, which act as guardrails. This keeps the LLM out of the weeds and lets it focus on *strategic decomposition and assignment*—exactly what LLMs are good at. The actual motion control and feasibility checking stay with classical robot planners or hand-coded controllers on each robot.

Escaping Local Minima: Hybrid Artificial Potential Field with Wall-Follower for Decentralized Multi-Robot Navigation

The big idea — first principles

The problem. Robots using simple force-field navigation (pushed away from obstacles, pulled toward goal) get stuck in dead-ends because attractive and repulsive forces cancel exactly, creating a local minimum.

The approach. Detect when a robot is trapped by checking if the net force drops near zero. When trapped, switch to wall-following mode (trace obstacle boundaries) while gradually rotating the goal direction. Once the way clears, return to force-field mode.

What's unique. The system remembers "Hit" and "Leave" points so robots never loop back to the same dead-end. A learned neural network decides when switching to wall-following helps, avoiding false switches when other robots are nearby.

ICRA 2025 · 4 citations · pathfinding sub-approach

What it does — 2-3 plain sentences

A team of robots each uses only its own sensors (no shared map, no central planner) to navigate together without collisions in complex spaces full of weird-shaped obstacles. The catch: when using simple force-field navigation (each robot is pushed away from obstacles and pulled toward its goal), robots get stuck in dead-ends or corners. This paper solves that by switching to wall-following mode when a robot detects it is trapped. The system learns when to switch using either simple rules or a trained neural network (pathfinding sub-approach: decentralized multi-agent pathfinding with collision avoidance).

The method, in detail — step by step

Setup: Each robot is equipped with a 360-degree range sensor (e.g., LiDAR) and knows its own pose and goal. The robot has no map of the environment and cannot talk to other robots about long-term plans; it only reacts to what it senses right now.

Hybrid APF-WF core:

  • Artificial Potential Field (APF) phase: Each robot computes a total force by:

- Attractive force: pulls the robot toward its goal (proportional to distance)

- Repulsive force: pushes the robot away from obstacles and other robots detected within sensor range

- The robot moves in the direction of this total force vector

  • Local minimum detection: The robot continuously checks if it is stuck. A local minimum occurs when:

- The net force magnitude drops near zero (robot is being pushed and pulled equally)

- The robot is not at its goal (position is far from goal)

- This is detected by checking if force magnitude falls below a threshold for consecutive sensor frames

  • Wall-following (WF) phase – Rule-based switch (RS): When trapped, the robot switches to following obstacle boundaries:

- The robot continues moving along the wall (left-hand or right-hand rule)

- While wall-following, the attractive force vector is gradually rotated to point away from the wall

- The robot remembers "Hit Points" (where it touched the wall) and "Leave Points" (where it escaped)

- This prevents the robot from looping back to the same dead-end

- Once the attractive force vector rotates far enough, the robot returns to APF mode and continues toward the goal

  • Wall-following phase – Learned switch (LS): A Vision Transformer encoder network is trained offline on human expert demonstrations:

- Input: local sensor readings (range data, relative positions of obstacles, distance to goal)

- Output: binary decision—stay in APF or switch to WF

- Solves "false WF" problem: robots sometimes treat nearby other robots as walls and follow them instead of avoiding them

- The encoder learns which situations actually benefit from wall-following vs. pushing through

Training: The learned switch uses expert demonstrations where a human (or optimal algorithm) controls a robot and the network learns when wall-following helps. This is done offline; no online learning during deployment.

Execution loop: At each sensor update:

  • Measure obstacles and other robots in sensor range
  • Compute APF forces
  • Check if trapped using rule-based heuristic (or learned network)
  • If trapped: switch to WF and rotate attractive force gradually
  • If not trapped (or escaped): continue moving under APF
  • Repeat until goal reached or max iterations

The trick that makes it work: The "Leave Point" memory prevents infinite loops—once a robot escapes a local minimum via wall-following, it marks where it escaped and never goes back to the same stuck spot. Combining geometric rules (wall-following) with learning (when to switch) gives the best of both worlds: guaranteed escape from local minima plus adaptation to robot-robot interactions.

Adaptive Task Allocation in Multi-Human Multi-Robot Teams Under Team Heterogeneity and Dynamic Information Uncertainty

The big idea — first principles

The problem. Mixed teams of humans and robots have incomplete information: human fatigue is estimated noisily, robot health arrives late, and team members have different strengths. Assigning tasks once at the start fails as conditions change mid-mission.

The approach. Train two coupled learning layers: one decides the initial assignment before work starts; the other watches during execution and decides whether to reshuffle tasks when someone slows down or becomes unavailable.

What's unique. The system uses auxiliary learning (a conditional VAE + GRU) to reconstruct true state from noisy and delayed observations. This lets the policy reason about actual conditions, not just raw sensor noise, and decide when reallocation is worth the disruption.

*ICRA 2025 · 4 citations · mission-planning (task allocation)*

What it does

Assigns tasks to a mixed team of humans and robots when team members have different strengths, operational conditions change during a mission, and the system has incomplete or delayed state information. Uses two levels of learning: one to make the initial assignment at mission start, another to decide whether and how to reshuffle tasks as the mission unfolds.

Sub-approach: mission-planning — dynamic task allocation.

The method, in detail

Problem formulation: Casts task allocation as a Hierarchical Markov Decision Process (HMDP) with:

  • Team members: i humans (with cognitive abilities, fatigue) + j robots (with sensor specialties, mechanical state)
  • Tasks: k tasks of varying difficulty
  • Static team heterogeneity: human skills, robot sensors, task specs
  • Dynamic state: time-varying fatigue, robot health, task progress — all subject to noise (measurement error) and latency (delayed updates)

Two-level HRL hierarchy:

  • Level 1 — Initial Task Assignment (ITA) at t=0:

- Encodes each human/robot capability and each task requirement using learned embedding layers with positional encoding

- Applies an attention-based policy to find the globally best initial assignment

- Decision made before execution, leveraging static heterogeneity

  • Level 2 — Conditional Task Reallocation (CTR) during execution (t=1 to T):

- Two sub-policies run at each time step:

- π_C: "Should we reassign tasks now?" (binary decision)

- π_TR: "If yes, what is the new assignment?" (reallocation action)

- Feeds forward reconstructed state information (see below)

- Reallocation is costly, so the system learns when to tolerate suboptimality rather than reshuffle

State representation learning (handles information uncertainty):

Addresses two sources of incomplete information:

  • Noisy observations (e.g., human fatigue measured inaccurately):

- A Conditional Variational Autoencoder (encoder-decoder pair, 2 FC layers each with ReLU)

- Encoder takes noisy fatigue + correlated context (hours worked, cognitive load)

- Decoder reconstructs true fatigue conditioned on that context

- Trained with MSE + KL divergence (weight 0.1)

  • Latency (e.g., robot health updates arrive 1-2 steps late):

- Stacked GRU (3 layers, 128 hidden units each) processes time series of delayed observations

- Outputs sequence fed through feedforward network

- Learns to infer current state from outdated history

Final state vector: mean pool over concatenation of reconstructed values + raw observations, fed to both policies.

Reward structure:

  • ITA: Maximize team performance sum + penalty for reallocations (Frobenius norm of reassignment matrix)
  • Condition policy: Gain from performing reallocation vs. staying put, minus frequency penalty (−0.4 · reallocation count / T)
  • Task reallocation: Performance gain, minus cost of assignment changes (−0.2 · change magnitude)
  • Auxiliary losses: cVAE and GRU trained on reconstruction error + KL divergence

Training uses PPO (Proximal Policy Optimization) with learning rate 0.0003, clip range 0.2, batch size 36, entropy coeff 0.01, 20 parallel actors, 10,000 episodes.

Inputs/Outputs:

  • *Inputs*: Current human fatigue/capabilities, robot health/sensors, task queue with difficulty, past allocation history, noisy/delayed state observations
  • *Outputs*: Initial task assignment matrix (humans/robots → tasks); at each step, reallocation decision + new assignment if needed

Key trick: The framework decouples heterogeneity (static, known upfront) from dynamics (uncertain, time-varying), using two separate learned policies and an auxiliary state reconstruction module. This lets it handle high uncertainty without constantly recomputing from scratch.

Realizing Emergent Collective Behaviors Through Robotic Swarmalators

The big idea — first principles

The problem. Swarms of oscillators synchronize (Kuramoto model). Swarms of particles aggregate (Vicsek model). But a robot swarm must do both: coordinate internal states and move as a group.

The approach. Couple each robot's position to neighbors' phase differences (moving toward synchronized neighbors, away from unsynchronized ones) and couple each robot's phase to neighbors' positions (synchronizing with nearby robots). This bidirectional coupling produces emergent collective patterns.

What's unique. This is the first real-robot realization of swarmalator theory. The team demonstrates rotating phase waves, synchronized clusters, and chimera states—patterns that exist purely on theory until now. Decentralized control means each robot runs its own control law with only local neighbor sensing.

What it does

Sub-approach (family): swarm — Agents synchronize *and* aggregate via bidirectional coupling between spatial and phase dynamics, producing patterns from pure oscillation theory (Kuramoto) applied to moving particles (Vicsek-style swarming).

The method, in detail

The swarmalator model: Each robot i has two coupled state variables:

  • Position x_i (spatial location in 2D)
  • Phase φ_i (internal oscillator state, often represented as angle or periodic variable)

The governing dynamics couple these bidirectionally:

  • Position update: A robot moves based on attraction/repulsion to neighbors *weighted by their phase differences*. Phase mismatch determines the strength or direction of spatial interaction.
  • Phase update: A robot's phase synchronizes based on neighbors' relative *positions*. Proximity to neighbors drives phase alignment.

This interplay produces emergent states:

  • Static sync: Robots cluster in space; all phases align at a common frequency.
  • Phase wave: Robots form a rotating or traveling pattern; phases wind monotonically in space.
  • Chimera: Some robots sync, others remain incoherent.
  • Chiral motion: Under coupling asymmetry, robots spiral or orbit rather than collide.

Realization on 15 physical robots:

  • Each robot is equipped with onboard sensors (position via motion capture or local sensing, neighbor detection).
  • Control law: Each robot computes its intended motion and phase rate using only local neighbor state (positions and estimated phases).
  • Frequency coupling: Some experiments vary natural oscillation frequency across the swarm (heterogeneous) or keep it uniform.
  • Chirality: Some robots are "chiral" (inherent preferred rotational sense) vs. "non-chiral" (symmetric coupling).
  • Decentralized execution: No central controller; each robot runs its control law independently.

Key parameters:

  • Coupling strength (how much neighbors' phase affects motion, and vice versa)
  • Sensing range (which neighbors count as "close")
  • Natural frequency (ω)
  • Phase lag or coupling asymmetry (determines chirality)

Emergent behaviors observed:

  • Synchronized phase + clustered position (all together, frequency-locked)
  • Traveling phase waves: positions form spatial pattern; phase rotates uniformly
  • Frequency distributions: robots maintain different individual frequencies yet form collective patterns
  • Stability and robustness: behaviors persist under noise and model mismatch

  • Friction, sensor noise, and latency shift bifurcation thresholds.
  • Small coupling errors compound in decentralized control.

Deploying Ten Thousand Robots: Scalable Imitation Learning for Lifelong Multi-Agent Path Finding

The big idea — first principles

The problem. Classical search-based planning moves many robots collision-free but is too slow for thousands. Pure learning is fast but unsupervised learning on massive multi-agent spaces is prohibitively sample-heavy.

The approach. Train a neural network by imitating an expert search planner (PIBT). The network learns the planner's one-step decisions from local observations. Add a communication module so nearby robots share state, and a collision shield for hard safety. Run it on GPU for massive parallelism.

What's unique. Imitation learning avoids sampling complexity—the network inherits the expert's heuristics instantly, so training is fast. The same trained model handles 1,000 to 10,000 agents without retraining because it operates on local information and parallelizes perfectly on GPU.

ICRA 2025 · 3 citations · pathfinding

What it does

SILLM trains a neural network to learn from pre-computed plans made by a classical search-based algorithm, adds a communication module so nearby robots share local information, and runs the whole system on a GPU to move thousands of robots through a warehouse or warehouse-like space without collisions. This solves the problem that pure learning-based methods are too slow at scale and pure search methods don't scale to ten thousand agents.

Sub-approach: pathfinding — a scalable imitation-learning MAPF solver that combines fast neural-network reasoning with global guidance from search-based methods.

The method, in detail

Lifelong MAPF setup: The system operates in a known 2D grid map with obstacles. Multiple agents (robots, packages) continuously spawn at different locations with goals; when an agent reaches its goal, it immediately receives a new one. The challenge is to compute collision-free, efficient paths for all agents and update them in real time without deadlock.

Imitation learning from PIBT: SILLM does not learn from scratch. Instead, it trains on trajectories produced by a classical search-based planner called Prioritized Implicit Biased search with Collision-Shield (PIBT+Collision-Shield). In each training episode, the search planner pre-solves many (10,000+ agent) instances and records the single-step action it would take for each agent at each timestep given its local view. The neural network learns: "Given my local observations (nearby obstacles, other agents, goal direction), what action should I take?" This is standard behavioral cloning or imitation learning—the network mimics the expert planner's one-step decisions.

Communication module: Each agent runs a small neural network conditioned on its local view (occupancy grid around it, other agents' positions within a radius, goal direction). But isolated local decisions cause deadlock. To break deadlock, agents exchange information with neighbors within communication range—a learned message-passing module aggregates neighbors' states into a "consensus" or "communication" feature, which influences the agent's action choice. This is akin to graph neural networks where agents are nodes and edges exist between nearby agents.

Single-step collision resolution and global guidance:

  • Collision resolution: If two agents would collide according to the network's output, a simple rule-based "collision shield" blocks the move and outputs a no-op or a safe alternative. This ensures collision-free execution by construction.
  • Global guidance: At longer time scales (not every step), a separate "backward Dijkstra" precomputed heuristic (computed once per map) suggests globally efficient directions toward agents' goals. This guides the learned network toward shorter paths, preventing the network from getting stuck in local inefficiency.

Inputs and outputs:

  • Input per agent: Local occupancy grid (5×5 or 9×9 cells around the agent), positions of nearby agents within radius R, goal position (in relative frame), velocity/heading of nearby agents.
  • Output: One of 5 discrete actions: move up/down/left/right, or wait. The collision shield post-processes this.

Scale: The network and communication module are lightweight (fully convolutional or small recurrent). At evaluation time, the system processes all agents' observations in parallel on a GPU using batch matrix operations. This allows the same trained model to handle 1,000 to 10,000 agents without retraining, as long as they fit in GPU memory.

The key trick: Imitation learning avoids the sample complexity of learning from scratch (which would require millions of rollouts). Instead, by imitating an expert search planner, the network inherits the expert's collision-avoidance and path-finding heuristics. The communication and global guidance layers then compress the expert's computation into a single forward pass, so what takes the search planner seconds of search now takes milliseconds on a GPU.

SIGMA: Sheaf-Informed Geometric Multi-Agent Pathfinding

The big idea — first principles

The problem. Each robot has a narrow field of view and no global map. Naive independent decisions lead to deadlock. Communicating everything to everyone is wasteful and slow.

The approach. Use sheaf theory (a topology framework) to prove that global consensus is achievable through purely local communication. Train a neural network to learn this consensus in a hidden layer, so each robot can decide as if it sees the full picture using only local observations from neighbors.

What's unique. Sheaf theory mathematically guarantees that the learned consensus layer is consistent across all robots without explicit global coordination. Each robot runs the same network but computes agreement implicitly—this is coordination without messages.

ICRA 2025 · 3 citations · multi-agent pathfinding

What it does

SIGMA tackles the problem of moving many robots through tight spaces without collisions when each robot can only see a limited area around itself. It combines deep reinforcement learning with sheaf theory—a mathematical framework from topology—to let robots learn a "consensus view" from their local observations, so each robot can act as if it sees the full picture. This is a multi-agent pathfinding approach: it solves coordinated collision-free routing at scale.

The method, in detail

The core insight is that when robots cooperate, they need to agree on what each will do next, but classical learning methods force each robot to decide based only on its own narrow field of view. Here's the three-step process:

1. Sheaf-theoretic consensus model: Sheaf theory (a branch of algebraic topology) describes how local observations at one agent connect to local observations at neighboring agents. The paper proves that global consensus on movements is achievable through purely local communication. The method uses this mathematical structure to guide what the neural network learns.

2. Self-supervised consensus learning: A neural network learns to approximate the consensus in a latent (hidden) space by training on pairs of observations from different agents. The network sees agent A's local view, agent B's local view, and their relative geometry, and learns to compute what both agents would "agree on" in terms of safe movement directions. Self-supervision means the network never needs labeled data—it infers ground truth from the structure of the problem itself.

3. Decentralized decision-making: During execution, each robot independently runs the trained network to compute its own learned consensus feature alongside standard pathfinding features (distances to goals, obstacles, other robots). It then uses deep reinforcement learning policy to pick the next action. Because all robots have the same learned consensus feature, they implicitly coordinate without explicit communication.

The architecture uses Ray for distributed training across multiple workers, storing experience in a replay buffer. Pre-trained models are provided for two environment types: open rooms with obstacles and maze-like corridors.

The core idea in code — sheaf-informed consistency in an RL policy

Sheaf theory principle: When multiple agents cooperate, their local observations should "agree" on the consensus view at each point. The code enforces this via an MLP that produces a learned consensus feature; MSE loss penalizes disagreement between neighbors.

1. Network Architecture (model.py lines 118–250)


class Network(nn.Module):
    def __init__(self, input_shape=configs.obs_shape, cnn_channel=configs.cnn_channel, hidden_dim=configs.hidden_dim,
                max_comm_agents=configs.max_comm_agents):
        super().__init__()
        self.latent_dim = 16*7*7
        self.hidden_dim = hidden_dim
        
        # CNN encoder: obs [B,6,9,9] → latent [B,784]
        self.obs_encoder = nn.Sequential(
            nn.Conv2d(self.input_shape[0], cnn_channel, 3, 1),
            nn.ReLU(True),
            ResBlock(cnn_channel),
            ResBlock(cnn_channel),
            ResBlock(cnn_channel),
            nn.Conv2d(cnn_channel, 16, 1, 1),
            nn.ReLU(True),
            nn.Flatten(),
        )
        
        # Recurrent: latent → hidden state [B,256]
        self.recurrent = nn.GRUCell(self.latent_dim, self.hidden_dim)
        
        # Communication block: multi-head attention + GRU update
        self.comm = CommBlock(hidden_dim)
        
        # MLP for sheaf-informed consensus feature
        self.mlp = nn.Sequential(
            nn.Linear(self.latent_dim, self.hidden_dim),
            nn.Linear(self.hidden_dim, self.mlp_dim),  # mlp_dim=1
            nn.Sigmoid()
        )
        
        # Dueling DQN heads
        self.adv = nn.Linear(hidden_dim + self.mlp_dim, 5)  # Advantage stream
        self.state = nn.Linear(hidden_dim, 1)              # Value stream

Key insight: The mlp module computes a scalar consensus feature per agent. All agents with the same local geometry should produce similar values—enforced by loss below.

2. Sheaf-Consistency Loss in step() and step_test() (lines 210–232, 287–310)

Each step of inference computes:


# Communication mask: which agents can "see" each other
agents_pos = pos  # [num_agents, 2]
pos_mat = (agents_pos.unsqueeze(1)-agents_pos.unsqueeze(0)).abs()
dist_mat = (pos_mat[:,:,0]**2+pos_mat[:,:,1]**2).sqrt()
in_obs_mask = (pos_mat<=configs.obs_radius).all(2)  # Within FOV?
_, ranking = dist_mat.topk(min(self.max_comm_agents, num_agents), dim=1, largest=False)
dist_mask = torch.zeros((num_agents, num_agents), dtype=torch.bool)
dist_mask.scatter_(1, ranking, True)
comm_mask = torch.bitwise_and(in_obs_mask, dist_mask)  # Final neighbor mask

# Apply communication block (multi-head attention)
self.hidden = self.comm(self.hidden, comm_mask)

# MLP outputs consensus feature
mlp_output = self.mlp(latent)  # [num_agents, 1]

# Sheaf-section loss: penalize disagreement with neighbors
sheaf_section_loss = torch.zeros(num_agents, dtype=torch.float32)
for i in range(num_agents):
    neighbors = comm_mask[i].nonzero(as_tuple=True)[0]
    if len(neighbors) == 0:
        continue
    output_i = mlp_output[i]
    loss = 0.0
    for j in neighbors:
        output_j = mlp_output[j]
        loss += torch.nn.functional.mse_loss(output_i, output_j, reduction='sum')
    sheaf_section_loss[i] = loss / len(neighbors)

# Combine with dueling DQN Q-values
if configs.Sec_cons:  # Sheaf-consistency enabled (True by default)
    q_val = state_val - self.lambdas * sheaf_section_loss + adv_val - adv_val.mean(1, keepdim=True)
else:
    q_val = state_val + adv_val - adv_val.mean(1, keepdim=True)

What this does:

  • For each agent *i*, measure MSE between its consensus feature and all neighbors' features
  • Penalize disagreement by subtracting lambdas * sheafsectionloss from Q-values (line 243, 321)
  • lambdas=0.001 (config line 43) is the weighting factor
  • This forces agents to learn representations that agree when they see each other

    for agent_id in checking_list.copy():
        if actions[agent_id] == 0:
            # Stay: reward based on goal
            if np.array_equal(self.agents_pos[agent_id], self.goals_pos[agent_id]):
                rewards.append(self.reward_fn['stay_on_goal'])  # 0
            else:
                rewards.append(self.reward_fn['stay_off_goal'])  # -0.075
        else:
            # Move: check bounds & obstacle
            next_pos[agent_id] += action_list[actions[agent_id]]
            if out-of-bounds or obstacle:
                rewards[agent_id] = self.reward_fn['collision']  # -0.5
    
    # Second round: agent swap conflicts (A→B, B→A simultaneously)
    # Third round: multi-agent collision (3+ agents same cell)
    # Greedy tie-breaking by position hash
    
    # Update positions
    self.agents_pos = np.copy(next_pos)
    self.steps += 1
    
    # Check termination
    done = np.array_equal(self.agents_pos, self.goals_pos)
    
    return self.observe(), rewards, done, info

def observe(self):

def sample_batch(self, batch_size: int) -> Tuple:
    """Prioritized replay: sample high TD-error transitions"""
    
    # Use SumTree for efficient sampling
    idxes, priorities = self.priority_tree.batch_sample(batch_size)
    
    # For each sample: extract sequence of length seq_len (16 steps)
    # and forward_steps (2 steps) for n-step return
    b_obs, b_action, b_reward, b_done, b_steps, b_seq_len, b_hidden, b_comm_mask = [], [], [], [], [], [], [], []
    
    for idx, global_idx, local_idx in zip(idxes.tolist(), global_idxes.tolist(), local_idxes.tolist()):
        
        steps = min(configs.forward_steps, (self.size_buf[global_idx].item()-local_idx))
        seq_len = min(local_idx+1, configs.seq_len)
        
        # Extract observation window
        obs = self.obs_buf[...]
        comm_mask = self.comm_mask_buf[...]
        hidden = self.hid_buf[...]
        
        # Pad if short
        if obs.shape[0] < configs.seq_len+configs.forward_steps:
            pad_len = configs.seq_len+configs.forward_steps-obs.shape[0]
            obs = np.pad(obs, ((0,pad_len),(0,0),(0,0),(0,0),(0,0)))
            comm_mask = np.pad(comm_mask, ((0,pad_len),(0,0),(0,0)))
        
        # n-step return (2-step)
        action = self.act_buf[idx]
        reward = 0
        for i in range(steps):
            reward += self.rew_buf[idx+i]*0.99**i
        
        b_obs.append(obs)
        b_action.append(action)
        b_reward.append(reward)
        b_done.append(done)
        b_steps.append(steps)
        b_seq_len.append(seq_len)
        b_hidden.append(hidden)
        b_comm_mask.append(comm_mask)
    
    # Importance sampling weights
    min_p = np.min(priorities)
    weights = np.power(priorities/min_p, -self.beta)
    
    # Stack and return as PyTorch tensors
    return (
        torch.from_numpy(np.stack(b_obs).astype(np.float16)),
        torch.LongTensor(b_action).unsqueeze(1),
        torch.HalfTensor(b_reward).unsqueeze(1),
        torch.HalfTensor(b_done).unsqueeze(1),
        torch.HalfTensor(b_steps).unsqueeze(1),
        torch.LongTensor(b_seq_len),
        torch.from_numpy(np.concatenate(b_hidden)),
        torch.from_numpy(np.stack(b_comm_mask)),
        idxes,
        torch.from_numpy(weights).unsqueeze(1),
        self.ptr
    )
