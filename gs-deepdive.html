The big picture — connecting the dots

For decades a robot had to store the world three incompatible ways: one format to know where it is (SLAM), another to render photorealistic views for training perception, a third for a planner to reason about objects. Three silos, three systems, and bugs at every seam. The single bet running through almost every paper here is that 3D Gaussian Splatting can be the one shared format for all three — a cloud of small colored 3D blobs that is simultaneously a map, a photorealistic renderer, and a set of taggable objects. That is why robotics grabbed a graphics technique: not for pretty pictures, but as a common language that lets one captured scene feed mapping, training, and reasoning at once. Everything below is people testing how far that one idea stretches.

Six things people are actually trying to do with it:

  • ① Bridge simulation and reality. SplatSim scans a real workspace into a blob replica, trains a manipulation skill inside a physics sim built on it, and runs it on the real robot with no retraining — directly attacking the sim-to-real gap. Robo-GS ties each blob to a mesh so appearance and physics move together.
  • ② Map while moving (SLAM), robustly. CGS-SLAM fights the blob-count explosion with pruning + compression; GARAD-SLAM masks out moving people/cars before they corrupt the map; RGB-only GS-SLAM drops the depth sensor entirely.
  • ③ Run on real hardware. A splat that needs a server GPU is useless on a battery. NGD-SLAM hits 60 FPS on a laptop with no graphics chip by parallelizing tracking and dynamic-masking.
  • ④ Survive hard environments. SeaSplat goes underwater and jointly learns how water absorbs light to recover true color; GaussianRoom handles blank textureless walls with a geometry model guiding where blobs may grow; Endo-2DTAM pushes it inside the body.
  • ⑤ Handle time. Lifelong-mapping work scores each part of the map by how temporary it is and keeps one master map absorbing new visits over months, so it never goes stale.
  • ⑥ Give the map meaning. SemGauss-SLAM bakes object labels into the blobs; BBQ and ReMEmbR put a language model on top so a robot can answer "find the cup near the red bowl" or "what did you see an hour ago?"

The throughline: the field is converging on Gaussian Splatting as a unifying substrate for robot perception, and the 2025 work is the messy, productive phase of making that substrate robust (dynamics, weird environments, time), cheap (compression, real-time), and meaningful (semantics + language) enough to actually live on a robot. The live run further down is that bare substrate — photos → blobs → novel views — that every paper here extends with one twist. Still open: full blob maps on tiny GPU-less hardware; merging maps across many robots in real time; and making the semantic layer reliable outside curated labs.

The problem — in depth

Every robot needs to know what the world around it looks like before it can do anything useful. That sounds simple, but it is not.

A robot's sensors — cameras, laser scanners, motion chips — pour out raw streams of numbers: brightness values, distance readings, tiny acceleration signals. None of that is a "map." The robot has to turn those raw numbers into some stored structure that tells it where things are, what they look like, and how they relate to each other. That stored structure is what researchers mean when they talk about a scene representation — a way the robot holds the world in memory.

For decades, different jobs used completely different structures. If you wanted to track where the robot is while it builds a map (a job called simultaneous localization and mapping, or SLAM), you used one format. If you wanted to render a photo-realistic view of the scene for training, you used a different one. If you wanted a planner to reason about what objects are near each other, you used yet another. Each format was a silo: data captured for one job could not easily feed another. You had to scan the scene, store it three different ways, and keep three systems running.

This is wasteful. Memory is tight on a robot. Processing time is tight. And the seams between the different systems are where bugs and errors creep in.

The deeper problem is that robots operate in the real world, which is messy. Lighting changes. People walk through the scene. Outdoor spaces have no walls to bounce a laser off cleanly. Underwater, light scatters in ways that make every color look wrong. Featureless hallways give a camera almost nothing to anchor on. Any representation that only works in a clean, static, well-lit lab is not good enough.

All of this connects to the central challenge every robot faces: take in an unclear, changing world, decide what to do, move a real body, and do it fast, cheap, safe, and general. A scene representation sits at the very start of that chain. If the stored picture of the world is wrong, noisy, too slow to build, or too large to fit in memory, every step after it — the decisions, the movements — goes wrong too. Getting the representation right is not a detail; it is the foundation.

The approaches — how the field actually tackles it

Building the scene from tiny colored blobs

The sub-problemA robot needs one shared format to simultaneously render photorealistic views for training, map the scene, and reason about objects — not three separate silos with seams that leak bugs.
Blob-based rendering — SplatSim (ICRA). Scan a real workspace, build a Gaussian Splat model, drop it into a physics simulator, and train manipulation skills in photorealistic synthetic images that transfer directly to the real robot without retraining.
Physics-consistent meshes tied to blobs — Robo-GS (ICRA). Each blob is bound to a mesh vertex, so when the robot moves, both the visual appearance and physical geometry update together in the sim.
Semantic labels on blobs — SemGauss-SLAM (IROS). Bakes object labels directly into the blob data so the map understands what things are, not just what they look like.

One captured scene feeds mapping, training, and reasoning at once.

Making maps while moving — and staying on track

The sub-problemBlob maps grow huge instantly because the system keeps placing new blobs everywhere, and moving objects corrupt the map as permanent structure. You need both a small map and a clean one to track accurately while building it.
Pruning and geometric compression — CGS-SLAM (IROS). Discard unseen blobs and compress the rest by sharing shape data across groups, cutting memory 2x without losing visual quality.
Mask dynamic pixels via optical flow — GARAD-SLAM (ICRA). Detects movement by checking which pixels flow against expected camera motion and masks them out before map updates.
Mask dynamics via depth changes — Dy3DGS-SLAM. Watches for depth inconsistency to flag moving objects and prevent them from corrupting the static map.
Skip the depth sensor entirely — RGB-Only Gaussian Splatting SLAM (ICRA). Builds blob maps from color images alone by learning consistent 3D positions across frames, removing a hardware constraint.

A compact, clean blob map lets the tracker stay locked on even when people and objects move through the scene.

Shrinking and speeding up for real hardware

The sub-problemA map that lives on a server GPU is useless on a battery-powered robot. Making blob-based SLAM cheap and live enough for modest edge hardware is essential.
Parallel tracking and masking — NGD-SLAM. Achieves 60 frames per second on a regular laptop (no GPU) by running camera tracking and dynamic masking as concurrent threads so neither blocks the other.
Motion priors as hard constraints — Kinematic-ICP. Uses laser-scan alignment (ICP) plus the robot's known motion model as hard limits on pose estimates, cutting drift with no extra memory.
Fast feature matching via sequence models — MambaGlue. Replaces standard attention (which slows down with feature count) with Mamba, a newer sequence model that scales better.

Blob-based maps that run live on modest laptops and embedded systems, not just servers.

Handling hard environments and long time scales

The sub-problemBlob maps built once go stale, and harsh conditions (underwater light scatter, featureless walls) give the optimizer nothing to anchor on. The representation needs to adapt to time and survive where standard methods fail.
Undo light scatter to recover true color — SeaSplat (ICRA). Learns how water absorbs and scatters light at different depths alongside 3D reconstruction, then reverses those effects to show true object color underwater.
Geometry model guides blob placement — GaussianRoom (ICRA). Trains a second model to estimate surface geometry and tells blobs where they can grow, anchoring optimization on textureless walls.
Score temporary map parts — Ephemerality Meets Lidar-Based Lifelong Mapping. Assigns each laser scan point a score for how temporary it is, capturing short-term and long-term changes across mapping sessions.
Master map absorbs new visits — LiLoc. Keeps one persistent map, updates it with laser/motion/inertial data from each new visit, stays accurate over months.

Blob maps that survive extreme environments and stay current as the world changes.

Giving maps meaning so robots can reason about them

The sub-problemA map is only useful if it can answer semantic questions: "find the cup near the red bowl" or "what did you see an hour ago?" Raw surface geometry alone cannot do this.
Semantic nodes with language reasoning — Beyond Bare Queries (BBQ). Builds a map where each object is a node with a text description; an LLM reasons over the spatial relationships to answer plain-language queries.
Searchable memory of past observations — ReMEmbR. Stores past observations (times, positions, image descriptions) in a searchable database; retrieves and reasons over relevant entries to answer questions about what the robot saw earlier.

Maps that answer spatial and temporal questions, turning raw geometry into a conversational memory.

Where it stands

Gaussian Splatting has moved quickly from a graphics novelty to a practical common format for robot sensing, and the compression and real-time work has made it usable on modest hardware. Systems that handle moving objects, plain surfaces, and tricky lighting environments now exist. What is still open: running a full blob-based map on very small, cheap hardware without a GPU remains difficult; merging maps across many robots in real time is unsolved at scale; and making the semantic layer — the part that knows what objects are — work reliably across diverse, uncontrolled environments is an active area with no settled answer yet.

Robo-GS: A Physics Consistent Spatial-Temporal Model for Robotic Arm with Hybrid Representation

ICRA 2025 · 16 citations · DOI: 10.1109/ICRA55743.2025.11128786 · arXiv: 2408.14873

What it does

Robo-GS builds a digital twin of a real robotic arm (or manipulation scene) that simultaneously looks photorealistic and physically simulates correctly. Starting from monocular video of the robot, it reconstructs a hybrid asset — Gaussian blobs for rendering, a mesh for collision/kinematics, URDF parameters for physics — and links all three so they move together when the physics simulator runs. The result is a Real2Sim asset you can drop into Isaac Gym or MuJoCo and get visually faithful, physically plausible sim data for reinforcement learning or imitation learning, without manual CAD tweaking.

The method, in detail

Inputs. A monocular RGB video of the robotic arm (ideally 360° orbit). No depth sensor needed. The video must have panoptic segmentation labels (instance masks per link/object/background), either pre-computed or inferred. Camera intrinsics/extrinsics come from structure-from-motion (COLMAP or GLOMAP run on the frames first). Optionally, Denavit-Hartenberg (DH) parameters from a CAD model can seed the kinematic chain.

What each Gaussian stores. Standard 3D Gaussian Splatting attributes: 3D center position xp, opacity σp, covariance encoded as scale + rotation (via spherical harmonics SHp), view-dependent color coefficients Cp. Robo-GS adds a semantic label S_p per Gaussian — a categorical tag indicating which robot link or object the Gaussian belongs to. This label is the anchor for the mesh binding.

Building the map — two stages.

*Stage 1 (static Gaussian fit).* Frames are fed through standard 3DGS optimization (gsplat library, v0.8+): initialize a point cloud via COLMAP sparse reconstruction, seed Gaussians at those points, minimize photometric loss on rendered vs. real frames. This gives a Gaussian cloud that renders the scene accurately from arbitrary viewpoints.

*Stage 2 (mesh extraction).* The trained Gaussians are converted to a point cloud (PLY) and fed into a separate mesh reconstruction pipeline (meshrecon/train.py + render.py). Normal maps are pre-computed with StableNormal to stabilize surface orientation. The resulting mesh is cleaned and segmented: each mesh face/vertex gets the same panoptic label as the Gaussians that cover it.

Gaussian-Mesh-Pixel binding (the core trick). Three mappings are composed into one structure:

  • Projection π: each Gaussian center (x,y,z) → pixel (u,v) via perspective projection.
  • Mesh mapping μ: each Gaussian center → its nearest mesh vertices/faces (sharing the same semantic label).
  • Isomorphic composite ϕ = π ∘ μ: pixel ↔ Gaussian ↔ mesh vertex, all one-to-one.

"Isomorphic" here means the correspondence is structure-preserving and differentiable end-to-end — gradient from pixel loss flows back through the Gaussian to the mesh vertices and, further, to physics parameters.

Physics representation and temporal model. Rather than learning a neural deformation field (4D NeRF style), Robo-GS solves explicit rigid-body governing equations. Physics parameters — mass m, inertia matrix I (3×3), friction coefficients, link DH parameters (length ai, twist αi, offset d_i) — are embedded in a URDF file. The LLM is used to infer plausible mass/friction from video trajectory data (the approach is heuristic here, not precisely specified). At time t, each link's Gaussian positions are updated by:

Pt = T0→t · (T0→i)^{-1} · P0

where T is the 6-DOF rigid transform (position + quaternion) coming from the physics solver. This collapses the optimization from 6n free parameters (one per Gaussian) to 6A parameters (one per articulated link, A << n), making the temporal problem tractable and physically plausible.

URDF/simulation pipeline. The full 12-step workflow: (1) video → frames, (2) SfM for poses, (3) train Gaussians, (4) generate normal maps, (5) extract PLY, (6) reconstruct mesh, (7) manually align mesh to world frame and resolve monocular scale ambiguity against a known reference, (8) segment by instance, (9) assign link IDs, (10) fine-tune kinematic/dynamic parameters, (11) generate URDF/MJCF files, (12) run in Isaac Gym or MuJoCo. Steps 7 and 10 have manual intervention — this is not fully automated.

Robotics-specific twist. The paper's contribution over vanilla 4DGS is the physics constraint: Gaussians are not free to drift — they must follow rigid-body dynamics of the articulated link they are bound to. This makes the sim asset physically consistent: the robot's Gaussian appearance updates correctly when you command a joint angle in the simulator, because each Gaussian simply inherits its link's rigid transform.

Run verdict

Not runnable on CPU-only. Gaussian Splatting training with gsplat requires CUDA — the rasterizer is a custom CUDA kernel. StableNormal (normal estimation) also requires GPU. The Gaussian training step (step 3) will refuse to run without a CUDA device.

What does work on CPU: COLMAP/GLOMAP for SfM (step 2, slow but functional), MuJoCo physics simulation (step 12, CPU-capable), and MJCF/URDF generation scripts (step 11, pure Python). The full end-to-end pipeline needs an NVIDIA GPU with at least CUDA 11.8. A mid-range GPU (RTX 3070 class) can train on the demo data; the paper used unspecified NVIDIA hardware. There is no pre-trained checkpoint or viewer-only mode that bypasses the CUDA requirement.

SplatSim: Zero-Shot Sim2Real Transfer of RGB Manipulation Policies Using Gaussian Splatting

ICRA 2025 · 12 citations · DOI: 10.1109/ICRA55743.2025.11128339 · arXiv: 2409.10161

What it does

SplatSim replaces the visual renderer inside a physics simulator (PyBullet) with Gaussian Splat reconstructions of the real robot and real objects. You collect motion-planned demonstrations inside this photorealistic fake world, train an imitation-learning policy on those synthetic RGB images, and deploy it directly on the real robot without any fine-tuning — zero-shot. The key claim is that Gaussian Splats are close enough to real camera images that the policy's visual backbone never notices it has moved to the real world, achieving 86.25% task success versus 97.5% for policies trained entirely on real data.

The method, in detail

What a Gaussian Splat is here. The scene is represented as a set of 3D ellipsoids (Gaussians). Each blob stores: a 3D mean position (where it lives in space), a 3D covariance matrix (its shape and orientation as an ellipsoid), an opacity value, and spherical harmonic coefficients that encode view-dependent colour. Rasterizing millions of these sorted blobs from a camera viewpoint produces a photo-quality RGBA image. The standard 3DGS rasterizer is used with no architectural changes.

Building the robot splat model — three steps:

  • *Capture and reconstruct.* The real robot is photographed from many poses. A standard 3DGS training pipeline (COLMAP for sparse point cloud + differentiable Gaussian rasterization) fits a splat model to those photos. This gives a static cloud of blobs that looks exactly like the real robot arm.
  • *Frame alignment.* The splat cloud exists in camera-reconstruction space, not in PyBullet's coordinate frame. ICP (Iterative Closest Point) aligns them, producing a rigid transformation T.
  • *Link segmentation.* To animate the arm, each Gaussian must be assigned to a specific robot link (forearm, wrist, gripper finger, etc.) so it moves with that link. The paper uses the robot's CAD bounding boxes in simulator space to label Gaussians per link. For articulated parts where bounding boxes overlap (e.g., gripper fingers), a KNN classifier is trained on labelled simulator point clouds to resolve the boundary.

Animating the splat in simulation. At every timestep, PyBullet computes forward kinematics from joint angles, giving a rigid transform (Rt^k, tt^k) per link k. Each Gaussian assigned to link k is moved: its mean transforms as mu' = R*mu + t, and its covariance as Sigma' = R * Sigma * R^T. Object splats (the thing being manipulated) are handled identically using PyBullet's object pose. The rasterizer then renders the full scene — robot + object + background splat — from the virtual camera to produce a synthetic RGB frame.

Policy training. Demonstrations are collected inside SplatSim using motion planners with full access to simulator state (privileged information — exact object positions). 400 demonstrations per pick task. The policy is Diffusion Policy (behaviour cloning): it takes the current RGB image and end-effector pose as input and outputs the next action (position + orientation delta). Data augmentation during training — Gaussian noise, random erasing, brightness/contrast jitter — is critical: without it, success drops from 86.25% to 21%. The robotics-specific twist is that the simulation loop is purely about rendering; the physics/dynamics remain in PyBullet (contact, collision), so you get photo-realism without sacrificing physics fidelity.

Tasks tested. Push-T (planar pushing), apple picking, orange placement, and peg assembly. Evaluated on a Franka Panda arm.

The PyBullet physics side alone is CPU-runnable, but that gives you no rendered images and is useless without the splat renderer.

CGS-SLAM: Compact 3D Gaussian Splatting for Dense Visual SLAM

IROS 2025 · 12 citations · arXiv 2403.11247 · also accepted IJCV 2026

What it does

Standard 3D Gaussian Splatting SLAM systems accumulate tens of thousands of redundant ellipsoid primitives, burning GPU memory and slowing the optimization loop that runs while the robot moves. CGS-SLAM cuts that cost from two angles: it prunes ellipsoids that carry little information using a learnable sliding-window mask, and it compresses the geometric parameters of surviving ellipsoids using a residual vector quantization codebook. Camera pose estimation uses a local-to-global bundle adjustment scheme with a combined photometric, depth, and ICP loss, letting the system stay accurate while the map stays compact.

The method, in detail

Inputs. Sequential RGB-D frames {Ii, Di} with known camera intrinsics. Each frame supplies a color image and a metric depth map (from a depth sensor, not estimated). The system is therefore a dense visual SLAM in the RGB-D regime, not monocular.

What each blob stores. Each 3D Gaussian is a primitive with: position mu in R^3, opacity alpha in [0,1], rotation expressed as a quaternion q in R^4, three scale values s in R^3, and per-Gaussian color c in R^3. The color can be represented as spherical-harmonic coefficients for view-dependent appearance. Together, position + rotation + scale define an oriented ellipsoid in 3D space; during differentiable rasterization, these are projected to 2D Gaussians and alpha-composited front-to-back to produce an RGB image and a rendered depth map.

Sliding-window masking (pruning step). At each SLAM iteration the system works over a local window of the most recent keyframes. For every Gaussian visible in that window a learnable scalar mask logit mn is maintained. A sigmoid converts it to a soft mask Sig(mn) and a straight-through estimator binarizes it: Mn = sg(1[Sig(mn) > epsilon] - Sig(mn)) + Sig(mn). Gaussians with mask value below epsilon are zeroed out of the rendering pass. A regularization term Lmask = (1/Nw) * sum Sig(m_n) penalizes having many active Gaussians, pushing the network to keep only the most useful ones. Frustum culling further limits optimization to Gaussians that actually project into the current frame set. Window sliding: when the window moves forward, the mask state resets for the newly admitted keyframes so that previously pruned Gaussians cannot be permanently eliminated if they re-enter a new window — preventing the system from collapsing the map over time.

Geometry codebook (compression step). The covariance matrices (equivalently, quaternion + scale pairs) of most Gaussians in a static indoor scene are geometrically similar — walls, floors, and table surfaces all produce near-planar ellipsoids with similar orientations. The codebook exploits this. Residual Vector Quantization (R-VQ) runs L=6 cascaded stages. In each stage k, the current residual is quantized to the nearest entry in a learned codebook C^k; that entry is subtracted, and the remaining residual is passed to stage k+1. Reconstructed geometry: lhatn = sum_{k=1}^{L} C^k[i^k] where i^k is the index chosen at stage k. Each index is stored as a 1-byte integer, so the full L=6 stages per Gaussian cost 6 bytes instead of 28 bytes for raw float32 quaternion + scale. The codebook is learned end-to-end jointly with the rest of the SLAM optimization. The reported compression ratio is approximately 2.21x in memory for the geometric parameters.

Map building and online optimization. New Gaussians are spawned where rendered depth disagrees with observed depth (high gradient regions). The system uses an anchor-based scaffold: anchor points sit at voxel grid centers, and each anchor carries a 32-dimensional feature vector plus learnable position offsets. Small per-anchor MLPs decode those features into the Gaussian attributes (color, opacity, geometry) conditioned on viewing direction and distance — this is the Scaffold-GS design for structured Gaussian placement. This structure means the map grows in a spatially organized way rather than scattering primitives randomly.

Local-to-global bundle adjustment. The tracking loss over a local window is:

Lt = sum{pixels p with S(p) > 0.99} (Lcolor + lambda1 * Ldepth + lambda2 * L_icp)

where S(p) is accumulated alpha (only high-confidence pixels count), Lcolor is photometric L1/SSIM, Ldepth is depth L1, and Licp = sumi wi ||R*pi + t - q_i||^2 is an ICP loss that aligns Gaussian center positions to the closest depth observations. Globally, a keyframe database accumulates past observations; periodic global BA re-optimizes all keyframe poses and the global map jointly, using multi-frame associations to reduce drift.

Robotics-specific angle. The compactness is the robotics contribution: the paper targets embedded and real-time deployment where GPU VRAM is a hard constraint. By cutting memory 2x while matching accuracy, the system becomes viable on smaller edge GPUs. The method is framed as a plug-in compatible with the MonoGS and Gaussian-SLAM SLAM frontends.

GARAD-SLAM: 3D Gaussian Splatting for Real-Time Anti Dynamic SLAM

ICRA 2025 · 11 citations

What it does

GARAD-SLAM is a dense RGB-D SLAM system that builds a live 3D Gaussian Splatting map of a scene while simultaneously filtering out moving people and objects so they do not corrupt the map or knock the pose tracker off course. The key twist over prior 3DGS-SLAM work: instead of rejecting dynamic pixels in image space (the standard approach), it reasons about which Gaussian blobs in the 3D map are dynamic and sends those labels back to the front-end tracker. This keeps the underlying map clean without hard-deleting anything — dynamically labelled blobs are penalized during rendering rather than pruned, so the system can recover if an object stops moving.

The method, in detail

Inputs. The system takes a stream of registered RGB-D frames (color image + per-pixel depth, aligned). It expects the TUM/BONN RGB-D format: 640×480, depth in millimetres. No IMU, no LiDAR.

What each Gaussian blob stores. Each 3D Gaussian carries the standard 3DGS parameters: a 3D centre position (mean), a 3×3 covariance encoded as a scale vector + rotation quaternion (the "ellipsoid" shape), an opacity scalar, and spherical-harmonic coefficients for view-dependent colour. On top of that, GARAD-SLAM tags each Gaussian with a dynamic label — a binary classification maintained throughout the system's lifetime.

Map initialization and growth. Depth is unprojected to 3D points using the camera intrinsics, forming an initial point cloud. Each new keyframe adds candidate Gaussian seeds from its depth, which are then optimized via the standard differentiable Gaussian rasterizer (CUDA tile-based renderer). The map grows by densification (splitting and cloning under-covered regions) and is pruned for low-opacity or oversized blobs — the same lifecycle as vanilla 3DGS, except dynamic blobs are never pruned; they are suppressed via penalty instead (see below).

Dynamic segmentation — the Gaussian pyramid network. This is the novel front-end. Instead of running a semantic segmentation network on the RGB image, the system reasons about Gaussians directly:

  • CRF graph over Gaussians. A fully connected Conditional Random Field (CRF) is constructed with one node per Gaussian. The unary potential for each node is derived from three signals: the reprojection error of the Gaussian onto the current frame, the depth variance between the Gaussian's predicted depth and the measured depth, and the observation frequency (how often this Gaussian has been seen and consistently explained static frames).
  • Multi-scale processing (pyramid). Gaussians are grouped into resolution levels — a coarse level pools spatially nearby Gaussians, finer levels deal with individual blobs. This hierarchical structure lets the CRF propagate dynamic decisions from obvious movers (large, fast, high reprojection error) down to smaller or slower neighbours before solving the pairwise energy.
  • Gibbs energy minimization. The pairwise energy term encodes a smoothness prior: neighbouring Gaussians in 3D space are encouraged to share the same label. The system minimizes this energy (likely via iterative belief propagation or graph cuts — the paper doesn't name the solver explicitly) to get a binary static/dynamic assignment per Gaussian.
  • Optical flow correction pass. Sparse optical flow (LK-style tracking of 2D feature points) is computed between consecutive frames. The flow vectors are reprojected onto the Gaussian labels; Gaussians whose projected flow is inconsistent with their CRF label are flipped. This corrects the most common failure mode: a slowly drifting person being mis-classified as static by the CRF alone.

Tracking (front-end). The camera pose for each new frame is estimated by ICP-style minimization between the current depth map and the static Gaussians only. Dynamic-labelled Gaussians are excluded from the pose Jacobian computation. This is the critical coupling: without it, a person walking across the frame would pull the estimated camera rotation or translation toward their motion.

Mapping (back-end optimization). A windowed bundle-adjustment step re-optimizes the Gaussian parameters (position, shape, colour, opacity) over a set of recent keyframes using the photometric rendering loss — the difference between the Gaussian-rasterized image and the actual camera image. For dynamic-labelled Gaussians, a rendering penalty is added to their loss contribution: their opacity is pushed toward zero, suppressing their visual presence in the render without deleting the blobs. If a blob's label flips back to static in a later frame (the person sat down, an object stopped moving), the opacity can recover — this is why penalize-not-prune matters.

Robotics-specific twist. Dynamic-environment robustness. Most 3DGS-SLAM papers test on static indoor scenes; GARAD-SLAM specifically targets the moving-object case that real robot deployments encounter. The decision to operate on Gaussians rather than pixels is architecturally significant: it lets the system exploit the 3D structure of the map (neighbour relationships in world space, consistent depth) rather than making per-frame 2D decisions that have no memory of where the object was a second ago.

GaussianRoom: Improving 3D Gaussian Splatting with SDF Guidance and Monocular Cues for Indoor Scene Reconstruction

ICRA 2025 · 11 citations

What it does

Standard 3D Gaussian Splatting (3DGS) breaks down in indoor scenes because large flat, textureless surfaces (walls, floors, ceilings) give sparse, noisy point cloud initializations, and there is nothing in the photometric loss to prevent Gaussians from drifting off the actual surface. GaussianRoom fixes this by running a neural signed distance field (SDF) in parallel with the Gaussian map and letting the two representations teach each other: the SDF tells the Gaussians where the surfaces are and which blobs to add or remove, while the Gaussians tell the SDF where to concentrate its expensive sampling. Two extra loss terms — one from predicted surface normals, one from predicted edge maps — push the geometry to be sharp in the texture-free regions where the photometric loss is otherwise uninformative.

The method, in detail

Inputs. A set of calibrated RGB images of an indoor scene (from ScanNet or ScanNet++) plus two sets of monocular predictions run offline: per-pixel surface normals (from the Surface Normal Uncertainty network, stored as .npz files) and per-pixel edge maps (from PIDINet, stored as .png files). COLMAP is used first to get an initial sparse point cloud and camera poses.

What each Gaussian blob stores. The standard 3DGS set of per-blob parameters: position (xyz, 3 floats), opacity (1 float), scale along three axes (3 floats, exponentiated), rotation as a quaternion (4 floats), and appearance encoded as spherical harmonic coefficients — one DC term (3 floats for the zero-frequency color) and 15 higher-order terms per color channel. There is a zero-initialized normal slot but it is not actively trained in the Gaussian branch; normals used in the loss are derived from the SDF's gradient.

The SDF branch (NeuRIS). A neural SDF is implemented as an MLP with hash-grid or positional encoding (inheriting from NeuRIS). It takes a 3D query point and returns a signed distance value. During training, a batch of 3D points is sampled along camera rays, the SDF values are queried, and a standard NeuS-style volume-rendering loss is applied. Crucially, instead of sampling points uniformly along each ray (which is expensive), the system uses the Gaussian-rendered depth map to narrow the sampling range to a thin shell around the visible surface — so the SDF only has to resolve geometry where the Gaussians say matter is.

The Gaussian branch (3DGS). Differentiable tile-based rasterization renders the Gaussian cloud into an image. The photometric loss is the standard L1 + SSIM combination used in vanilla 3DGS.

SDF-guided densification and pruning (the key contribution). Vanilla 3DGS adds and removes blobs based on how large the gradient of the rendered image is with respect to blob position — a purely photometric signal. GaussianRoom replaces this with sdfdensifyandprune(). It evaluates the NeuRIS SDF at all current Gaussian centers and computes a sdfdensifyguidance score via a Gaussian weighting (gaussianfun) that is high when a blob is near the zero-level set (i.e., on a surface) and low when it is far away. Blobs that score above 0.95 are cloned or split regardless of photometric gradient — so the system populates surfaces that are featureless but geometrically located by the SDF. Blobs that score low on the complementary sdfpruneguidance are removed. Standard opacity and screen-size pruning is also applied on top.

Anchor seeding. When isanchor=True, runner.genanchor_pts() queries the SDF across a grid, identifies regions close to the zero crossing, and injects new Gaussian seeds there. This is the cold-start mechanism for surfaces that had no COLMAP points at all.

Normal regularization loss. When isgsnorm=True, the rendered Gaussian depth is used to compute per-pixel surface normals (via finite differences over the depth map). These are compared with the monocular normal predictions using both an L1 term and a cosine similarity term, weighted by lambdal1normal and lambdacosnormal. This pushes the Gaussian geometry to match the general surface orientation even in low-texture regions.

Edge regularization loss. The photometric L1 loss is re-weighted per pixel by edge_weight = 2 * sigmoid(edge), where edge is the PIDINet edge-probability map. High-edge pixels (object boundaries, depth discontinuities) receive extra photometric supervision, guiding the Gaussians to stay sharp at those locations.

Training schedule. The GS branch and the SDF branch share a single training loop. They are updated in alternating mini-batches. The SDF-to-GS interaction (densification/pruning calls that query the SDF) is active for a specific iteration window (sdf2gsfrom to sdf2gsend), avoiding disrupting either branch before it has converged enough to give useful geometry.

Robotics angle. The stated motivation is embodied intelligence: a robot navigating an indoor environment needs a dense, geometrically accurate reconstruction of walls, floors, and furniture — not just a photorealistic texture. The SDF produces a clean mesh via marching cubes for downstream planning or collision checking, while the Gaussians provide real-time rendering for a simulator or policy evaluation loop.

Advancing Dense Endoscopic Reconstruction with Gaussian Splatting-Driven Surface Normal-Aware Tracking and Mapping

(Endo-2DTAM) ICRA 2025 · citations: 10

What it does

Endo-2DTAM is a real-time SLAM system for endoscopic (camera-inside-body) video that replaces 3D Gaussian ellipsoids with 2D disk-shaped surfels — a variant called 2D Gaussian Splatting (2DGS). Because each surfel is a flat disk, its orientation directly encodes the local surface normal. The system exploits that normal information in both tracking (pose estimation per frame) and mapping (scene update), achieving sub-2 mm depth reconstruction accuracy in colonoscopy video. It runs in real time and is one of the first GS-SLAM systems designed specifically for deformable, texture-poor, single-camera surgical scenes rather than rigid indoor rooms.

The method, in detail

The representation — 2D Gaussian surfels. Standard 3DGS uses 3D ellipsoids; each stores position, a full 3x3 covariance (encoded as rotation + scale), opacity, and spherical-harmonic color coefficients. The critical problem for surface reconstruction is that a 3D ellipsoid has no single surface normal — it is a volume. 2DGS collapses one scale axis to zero, making each primitive a flat disk in 3D space. Each surfel stores: center position X (3D), two orthogonal tangent vectors (tu, tv) whose cross product tw = tu x tv is the normal, two scale values (su, s_v) for disk size, opacity, and RGB color. This makes the surface normal an explicit, differentiable parameter of every Gaussian.

Inputs. RGB-D frames from an endoscope: color image + calibrated depth map (from a stereo or structured-light source). Camera intrinsics are assumed known. The system also reads ground-truth depth and ground-truth normals (derived on-the-fly via finite differences across the depth map) for supervision.

Initialization. The first RGB-D frame is back-projected into a point cloud. Each point becomes one 2D Gaussian disk, with scale, opacity, and color initialized from that pixel. No pretrained network is used — initialization is purely geometric.

Tracking (pose estimation, per frame). Camera pose is predicted with a constant-velocity motion model (current pose = previous pose + last delta). The predicted pose is then refined via gradient descent while the Gaussian map is held fixed. Three losses drive this:

  • Point-to-point depth loss: L1 distance between rendered depth and ground-truth depth.
  • Point-to-plane loss: L1 distance between the 3D point error projected onto the ground-truth surface normal (N_GT, computed as the cross product of depth gradients). This penalizes error along the normal direction more than tangential drift — an ICP-inspired term that is more geometrically meaningful than raw depth error.
  • Color loss: L1 between rendered RGB and observed RGB, with an affine exposure correction applied (endoscopes have strong illumination variation).

The tracking step runs for 15 iterations per frame. This is deliberately cheap — tracking only moves the camera, not the map.

Gaussian expansion. Every k frames (k=8 in the base variant), the system checks which parts of the current frame are not yet covered by the Gaussian map. Coverage is measured by the rendered silhouette: pixels where the accumulated opacity falls below a threshold (0.5) have missing geometry. New 2D Gaussians are initialized from the RGB-D data at those uncovered pixels and added to the map.

Mapping (scene optimization, per frame). With camera poses fixed, the 2D Gaussian parameters are updated by minimizing:

  • Reconstruction loss: 80% L1 color + 20% SSIM (structural similarity).
  • Point-to-point depth loss (same as tracking).
  • Depth distortion loss: For each ray through the scene, Gaussians are composited front-to-back. The distortion loss penalizes cases where two Gaussians at very different depths both contribute significant weight — it forces depth-ordering consistency and prevents "floaters" and fuzzy surfaces. Formulated as the weighted sum of |zi - zj| over all Gaussian pairs on each ray, weighted by their rendering weights.
  • Normal consistency loss: For each Gaussian contributing to a pixel, its disk normal ni should match the depth-derived ground-truth normal NGT. Loss = sum over contributing Gaussians of wi * (1 - ni . N_GT). This is the key robotics-domain adaptation: it uses the normal built into the surfel representation to regularize geometry, which is critical in the textureless, featureless regions typical of intestinal mucosa.

Hyperparameters: depth distortion weight alpha = 1000, normal consistency weight beta = 0.05. Mapping runs 15 iterations per frame.

Bundle adjustment. Every 100 tracking iterations, a global bundle adjustment jointly optimizes both camera poses and Gaussian parameters over a selected set of keyframes. The combined loss is the full tracking + mapping objective. It runs for 200 iterations.

Pose-consistent keyframe sampling. Rather than selecting keyframes by overlap ratio alone, the system samples keyframes probabilistically based on three signals: translational distance from the current frame, rotational distance (quaternion error), and temporal distance (frame index gap). Each candidate keyframe's probability is P = sum over {dl, rl, t_l} of log2(1 + 1/(l + 0.2)). Frames that are far away in position, rotated differently, and from a different time point all get higher probability. This prevents the map from collapsing onto nearby redundant views — a particular risk in endoscopy where the camera often backtracks.

Robotics-specific twist — medical endoscopy context. Endoscopic scenes are unlike indoor SLAM targets in three ways: (1) the tissue is deformable (the system assumes quasi-static scenes per clip, side-stepping full deformation modeling); (2) there is essentially no rigid texture — surfaces are smooth and pink-pink-pink, making color-based tracking unreliable; (3) depth from an endoscope is much noisier than from a depth camera. The method addresses (2) and (3) by leaning heavily on geometry (the normal-aware losses), while (1) is left as a limitation acknowledged in the paper.

SeaSplat: Representing Underwater Scenes with 3D Gaussian Splatting and a Physically Grounded Image Formation Model

ICRA 2025 · 10 citations

What it does

SeaSplat takes a set of underwater images (with COLMAP camera poses) and builds a 3D Gaussian Splatting scene that simultaneously models the true scene color and the water medium that obscures it. Because water attenuates light in a range- and wavelength-dependent way and adds backscattered glow, standard 3DGS trained on underwater images learns a corrupted appearance. SeaSplat bakes a physics-based underwater image formation model directly into the differentiable rendering pipeline, so the Gaussians learn the restored, in-air color of every point while globally learned medium parameters account for the water. At inference time you can render the scene either as it looks underwater (with the medium re-applied) or as a clean, dewatered novel view.

The method, in detail

Inputs. A directory of undistorted underwater images plus COLMAP sparse reconstruction output (sparse/0/) — the standard 3DGS input format.

What the Gaussians store. Each Gaussian primitive holds the standard 3DGS parameters: mean position (3D), covariance encoded as scale + rotation quaternion, opacity, and color expressed as spherical harmonic coefficients. Crucially, the color SH coefficients here represent the *true in-air scene color J*, not the observed underwater color.

Underwater image formation model. The method adopts the revised SeaThru formation equation:


I = J * exp(-beta_D * Z) + B_inf * (1 - exp(-beta_B * Z))

where I is the observed degraded pixel, J is the true color, Z is per-pixel depth, betaD (attenuation) and betaB (backscatter) are wavelength-dependent (one value per RGB channel), and Binf is the color of water at infinite depth. These four global parameter sets — betaD, betaB, Binf, plus the depth-to-attenuation mapping — are learned jointly with the Gaussians. The coefficients betaD and betaB are implemented as 1×1×3 convolution kernels applied to the depth image, making them differentiable and GPU-friendly.

Depth extraction. A second rendering pass runs the standard Gaussian rasterizer but replaces each Gaussian's color with its z-depth value, producing a per-pixel depth map Z from the same scene representation. This depth feeds directly into the formation model.

Two-phase optimization. Training runs standard 3DGS from scratch for the first 10,000 iterations (flag --seathrufromiter 10000). After that, the underwater image formation model activates and medium parameters start being optimized alongside the Gaussian parameters. This staging prevents the medium model from interfering with initial scene geometry.

Seven loss terms. The total loss is:

  • L_GS — standard 3DGS photometric loss (L1 + D-SSIM on rendered vs. observed image, with the medium re-applied to the Gaussian render).
  • L_bs (backscatter) — dark channel prior applied to backscatter estimate, encouraging the medium model to explain dark regions rather than the Gaussians absorbing them.
  • L_gw (gray world) — pushes the mean of each color channel toward mid-range, preventing trivial solutions where all J goes to zero.
  • L_sat (saturation) — penalizes restored color values above 0.7, preventing the dewatering from overcorrecting to blown-out whites.
  • Lop (opacity) — for pixels whose observed color matches Binf (pure backscatter water column), this drives Gaussian opacity low, removing floaters in open water.
  • L_Z-smooth (edge-aware depth smoothness) — regularizes depth, allowing discontinuities at image edges but penalizing noise in uniform regions.
  • L_Z-recon (depth-weighted reconstruction) — upweights photometric error in far regions that suffer most from medium degradation, guiding geometry in those areas.

Gradient detachment is applied in L_bs: gradients from backscatter loss do not flow back through the depth computation, preventing the medium model from distorting scene geometry.

Robotics-specific twist. The paper is squarely aimed at underwater robotics: the SeaThru-NeRF dataset was collected by an underwater vehicle. A clean, accurate 3D map of the seafloor is essential for AUV navigation and inspection tasks, and recovering true scene color (rather than the bluish/greenish appearance underwater cameras produce) is important for object detection and identification in scientific or inspection missions.

AutoSplat: Constrained Gaussian Splatting for Autonomous Driving Scene Reconstruction

(ICRA 2025 · 9 citations · DOI: 10.1109/ICRA55743.2025.11127564 · arXiv: 2407.02598)

What it does

AutoSplat reconstructs autonomous driving scenes from multi-camera and LiDAR sequences into a 3D Gaussian Splatting representation that can synthesize novel viewpoints in real time — including viewpoints that simulate lane changes or other camera positions not present in the original capture. It treats the scene as three distinct layers (road/sky background, general background, and dynamic foreground vehicles) with separate initialization and constraints for each. The key contribution is a set of geometric constraints and a reflection-based supervision trick that together make Gaussian Splatting tolerate the sparse viewpoints, large outdoor scale, and moving objects that kill standard 3DGS in driving contexts.

The method, in detail

Inputs. A calibrated sequence of N monocular images with per-frame camera intrinsics and extrinsics, synchronized LiDAR point clouds, and 3D bounding box trajectories for dynamic objects (these come from a standard perception stack or annotation). No stereo pair and no depth sensor beyond LiDAR.

Representation. Each 3D Gaussian blob stores: 3D mean position, a 3x3 covariance encoded as a rotation quaternion plus three scale values, opacity, and spherical harmonic (SH) coefficients for view-dependent color. Foreground vehicle Gaussians get an extra per-frame residual SH vector on top of the base SH.

Initialization — background. LiDAR point clouds accumulated across all frames seed the background Gaussians. This gives far better spatial coverage of the road and distant structure than the Structure-from-Motion point clouds that standard 3DGS uses, which often miss flat road surfaces entirely.

Initialization — foreground. A single-image 3D reconstruction network generates a coarse vehicle mesh template from one image of each tracked object. That template is replicated for every frame in which the object appears, placed in world coordinates according to the tracked 3D bounding box, and then scaled along each axis so its bounding box matches the annotated object dimensions. Gaussians are seeded on those scaled template points. This solves the severe problem that driving cameras only see one side of a vehicle — you get a geometrically reasonable full-body initialization without 360-degree capture.

Road and sky geometric constraint. A semantic segmentation model (Mask2Former, pretrained) labels road and sky pixels per frame. Gaussians whose centers fall inside those regions are penalized for having non-zero roll/pitch angles or non-zero vertical scale:

Cg = (1/Ng) * sum( |rolli| + |pitchi| + |sz_i| )

This forces road/sky Gaussians to be flat horizontal or flat vertical discs, which makes them render consistently from any viewpoint angle — essential when you want to synthesize a shifted camera position during a simulated lane change.

Reflected Gaussian consistency constraint. Vehicles are approximately bilaterally symmetric. AutoSplat reflects each foreground Gaussian across the vehicle's symmetry plane using a reflection matrix M = I - 2(aa^T)/||a||^2 where a is the lateral axis of the vehicle. The position, rotation matrix, and SH coefficients (rotated using the Wigner D-matrix to keep the viewing-angle dependence physically correct) are all reflected. These reflected ghost Gaussians are rasterized and compared to the ground-truth image with a standard photometric loss. The result: the unseen far side of every vehicle gets supervised through the reflected view of the near side. Without this, the unseen half of the vehicle is unconstrained and produces garbage when the novel view exposes it.

Dynamic appearance — residual spherical harmonics. A small MLP takes a per-frame temporal embedding Et, a Gaussian's world-space position x, and its base SH coefficients fSH as input, and outputs a residual deltafSHt. The per-frame SH is then fSH + deltafSH_t. This lets the color model adapt to lighting changes, glare, and reflections that change as the vehicle moves. A sparsity loss (weight gamma) penalizes large residuals to prevent flickering.

Training schedule — four phases.

  • Background phase 1 (15k iterations): road and sky regions only, with geometric flatness constraint active.
  • Background phase 2 (15k iterations): all background Gaussians together.
  • Foreground (5k iterations): vehicle Gaussians optimized with reflected consistency loss; background frozen.
  • Joint fine-tuning (10k iterations): foreground and background rendered together; only foreground attributes and background opacity are updated (positions/scales of background are frozen to avoid drift).

Loss is L1 + (1-lambda)*DSSIM, standard for 3DGS, plus the constraint terms.

Robotics-specific twist. The method is squarely aimed at driving simulation: it supports synthesizing novel camera poses for lane-change evaluation, handles moving objects explicitly rather than treating them as noise, and uses the sensor suite (LiDAR + calibrated camera rig) that autonomous vehicles already carry — not a lab scanner.

RGB-Only Gaussian Splatting SLAM for Unbounded Outdoor Scenes

ICRA 2025 · 8 citations

What it does

OpenGS-SLAM is a SLAM system that builds a 3D Gaussian Splatting map of an outdoor scene using only a monocular RGB camera — no depth sensor, no pretrained per-dataset depth model. It simultaneously tracks the camera pose and optimizes the Gaussian scene representation in an end-to-end differentiable pipeline. On the Waymo driving dataset it cuts the translation error of prior 3DGS-SLAM methods to roughly one-tenth of their error.

The method, in detail

The core problem with prior work. Indoor GS-SLAM systems (MonoGS, SplaTAM, etc.) bootstrap camera tracking either from an RGB-D sensor that hands them metric depth directly, or from a monocular depth network that was trained on indoor data. Neither transfers to unbounded outdoor driving sequences, where depth scales are large and vary rapidly, and the effective baseline between consecutive frames is short.

Pointmap regression instead of depth maps. The first stage is a pointmap regression network — specifically built on DUSt3R/CroCo, a transformer that takes a pair of overlapping images and regresses a dense 3D pointmap: for every pixel in each image it predicts the (x, y, z) coordinate of the visible surface point in a shared coordinate frame. This is richer than a depth map: it already encodes the cross-frame geometry, so the relative camera pose between the two frames can be read out by aligning the two pointmaps. The transformer was pretrained on large collections of diverse stereo/multi-view data, giving it a prior over outdoor geometry that no indoor depth model has.

Adaptive scale mapper. Raw pointmaps from DUSt3R come in an arbitrary reconstruction scale that drifts across windows of frames. OpenGS-SLAM adds an adaptive scale mapper that converts pointmap estimates into a metric scale consistent with the growing 3DGS map, preventing scale drift from accumulating into the Gaussian scene representation.

Gaussian scene representation. Each 3D Gaussian blob stores: a 3D mean position, a 3x3 covariance (parameterized as a rotation quaternion and a scale vector), an opacity scalar, and spherical-harmonic coefficients for view-dependent color. These are the standard 3DGS parameters. Gaussians are initialized by unprojecting the pointmap points into 3D at each new keyframe and adding them as new blobs. The map is therefore seeded directly from the pointmap, not from a separate SfM step.

Joint optimization. Camera poses and Gaussian parameters are jointly optimized by minimizing a photometric rendering loss: the differentiable 3DGS rasterizer renders the current Gaussians from the estimated camera pose, and the pixel-level RGB error is backpropagated through both the Gaussian parameters and the pose variables. This tightens the coupling between tracking and mapping — a better map gives better gradients for pose, and a better pose gives better Gaussian placement.

Outdoor-specific adaptations. The system drops the assumption of a bounded scene: Gaussians are placed at whatever depth the pointmap predicts, which may be hundreds of meters. The adaptive scale mapper is the key mechanism that stops the system from collapsing when the pointmap scale changes (e.g., from a close object to a far skyline). No sky modeling or separate dynamic-object mask is applied; the paper focuses purely on static outdoor structure.

Evaluation. Nine driving clips from the Waymo Open Dataset. Metrics: absolute translation error (ATE) for tracking, and PSNR/SSIM/LPIPS for novel view synthesis. OpenGS-SLAM outperforms all prior 3DGS-SLAM baselines on both, with tracking error at 9.8% of the next-best method.

SemGauss-SLAM: Dense Semantic Gaussian Splatting SLAM

IROS 2025 · 8 citations

What it does

SemGauss-SLAM builds a dense 3D map of an environment from RGB-D video while simultaneously tracking the camera pose and labeling every part of the map with semantic category information. Each 3D Gaussian blob in the map carries a semantic feature vector in addition to the usual geometry and color, so the map is queryable for "what object is here?" not just "what does this look like?". The robotics payoff is a single unified representation that supports rendering, localization, and scene understanding without separate modules or post-processing.

The method, in detail

Inputs. RGB-D video (color frame + aligned depth map per timestep). No point cloud scanner or IMU required. The system is indoor-scene oriented (Replica, ScanNet).

What the blobs store. Each 3D Gaussian holds: a 3D center position μ, a radius r (isotropic, not full covariance), an RGB color c, an opacity α, and a 16-channel semantic feature embedding e. The semantic embedding is the novel addition — standard 3DGS uses only geometry+color.

Initialization. At the first keyframe, every pixel's depth reading is unprojected into 3D space using the known camera intrinsics. That produces a point cloud, and each point seeds one Gaussian. DINOv2 (a self-supervised vision transformer trained on diverse imagery) extracts dense 2D feature maps from the color frame; those per-pixel features are projected onto the corresponding new Gaussians to warm-start their semantic embeddings, avoiding random initialization and accelerating convergence.

Tracking (camera pose estimation). While the Gaussian map is frozen, the camera pose for each new frame is estimated by minimizing a rendering loss: the system renders the current map from the estimated pose and compares the rendered color and depth against the observed frame. A constant-velocity motion model initializes the pose estimate, then iterative gradient descent refines it. Only pixels inside the visible silhouette of the rendered map contribute to this loss, which makes tracking more robust. Semantic features are not used during single-frame tracking — only RGB and depth.

Mapping (Gaussian update). When a new keyframe is selected (based on co-visibility: if less than 50% of the current frame overlaps the existing map, a new keyframe is declared), the Gaussians are updated while camera poses are held fixed. The map is optimized with three losses simultaneously:

1. RGB rendering loss (L1 + SSIM against the observed color image).

2. Depth rendering loss (L1 against the depth map).

3. Feature-level loss: ℒf = Σ |Fe − E(p)| where F_e is the per-pixel DINOv2 feature extracted from the current color frame and E(p) is the corresponding feature rendered from the Gaussian semantic embeddings via alpha-compositing. This directly supervises the semantic field.

Densification. When the co-visibility ratio drops below 50%, new Gaussians are instantiated by unprojecting the new keyframe's depth, replicating the initialization step for the newly visible regions. There is no splitting/cloning procedure like vanilla 3DGS; the growth strategy is purely coverage-based.

Semantic-informed bundle adjustment (BA). After a window of keyframes accumulates, the system runs a joint optimization over both camera poses and Gaussian parameters. The BA loss includes a cross-frame semantic consistency term: ℒBA-sem = Σi Σj |Tij · G(Ti, e) − G(Tj, e)|, which warps the rendered semantic feature map from frame i into frame j's viewpoint and penalizes disagreement. Combined with RGB and depth cross-frame terms, this multi-view semantic constraint pulls drifting camera poses back into alignment and sharpens the semantic field simultaneously. This is the paper's most distinctive contribution — using semantic features as a registration signal on top of photometric and geometric signals.

Robotics-specific twist. The primary twist is purely semantic: the map is queryable by meaning, not just appearance. For navigation or manipulation, a robot can ask "where is the table?" by rendering the semantic feature map and matching against a query feature. The scene graph is implicit in the Gaussian field itself. There is no handling of dynamic objects, no LiDAR, no sim-to-real transfer — the paper's focus is indoor static scenes with RGB-D input.

The big picture — connecting the dots

Start with a plain fact: an underwater photo is a lie. Not because the camera is bad, but because the water between the camera and the reef edits the light on its way to the lens. Two things happen at once, and both get worse the farther the light has to travel through water:

  • The water eats color — and it eats warm colors first. Red is gone within a few meters, then orange, then yellow; blue survives longest. So a red coral ten meters away doesn't look dim red — it looks brown, or grey. The loss depends on distance.
  • The water adds a veil — floating particles scatter ambient light back into the lens, like headlights in fog. This lays a blue-green haze over everything, thicker the farther you look.

The key word in both is distance. The same coral looks different depending on how far it is from the camera, because the light travelled through more water. That's the trap: the background is always murkier and bluer than the foreground, and an object's apparent colour changes as you swim around it.

Why this is a real problem, not just an ugly one. A scientist measuring coral health needs the coral's true colour (bleaching shows up as colour change) — but the colour in the photo is corrupted by however much water happened to be in the way. And any attempt to build a 3D model assumes a point looks the same from every angle; underwater it doesn't, so the reconstruction gets confused and tries to "explain" the water's effect as if it were a property of the coral. The water and the scene are tangled together.

So the real question is: can you pull them apart? Given nothing but ordinary photos — no special lights, no distance sensors — can you recover both the true scene and a description of how this particular water distorts light, at the same time? This is a chicken-and-egg: to know a point's true colour you must know its distance (to undo the right amount of water); to know its distance you must build the geometry, which needs consistent colour across views — which you don't have, because of the water. Each answer needs the other.

The unlock. A method that builds a 3D scene from photos already hands you the one thing the water problem was missing: the distance to every point. Gaussian Splatting is exactly that — a 3D model, so it knows how far away everything is. So SeaSplat runs two models locked together: a clean-scene model (the blobs, as if there were no water) and a small water model (how much this water eats each colour per metre, and how much haze it adds per metre).

How they're forced to separate. To match a real photo, SeaSplat renders the clean scene (getting a colour and a distance for every pixel), then pushes that render through the water model — eating the right colour and adding the right haze for each pixel's distance — producing a simulated murky photo. It compares that to the real murky photo, and tunes both models to close the gap. The elegant part: because the distortion depends on distance, and the geometry ties distance to viewpoint, there is only one way to match every photo from every angle at once — the clean model must hold the actual true colours, and the water model must hold the actual water. The system is forced to write every pixel as "true colour (fixed) + water effect (varies with distance)," and that split is the answer.

Then restoration is free: render the clean scene and simply don't pass it through the water — that's the reef with the ocean removed, from any viewpoint. And the deeper idea that ties this back to the whole theme: a good representation doesn't just store what the world looks like, it separates what the world is from what's between you and it. That scene-vs-medium split is what lets you see truthfully through any corrupting channel — water, fog, haze, smoke — and it only became tractable because splatting gives you geometry, and geometry gives the physics the distance it needed. The honest limit: the recovered colours are the model's best explanation of the photos, not a calibrated measurement — physically grounded and self-consistent, but still an estimate.

The main loop

GaussianSLAM.run() (gaussian_slam.py, line 226) iterates over every frame index:

1. Pose initialization

For each frame, a pose candidate is built before Gaussian optimization:


# odometry_type = "gt": take ground-truth pose directly (used for the KITTI branch in the current code)
estimated_c2w = self.dataset[frame_id][-3]

# odometry_type = "const_speed": extrapolate from the last two poses
init_c2w = extrapolate_poses(prev_c2ws[1:])

# odometry_type = "odometer": use Open3D RGBD odometry
odometer_rel = self.odometer.estimate_rel_pose(image, depth)
init_c2w = prev_c2ws[-1] @ odometer_rel

Note: the tracking loop below (Tracker.track) is present but the GaussianSLAM.run() method as committed uses ground-truth pose for KITTI and has the rendered-render tracking calls commented out — the gt-pose branch is active in the committed code.

2. Submap boundary decision

GaussianSLAM.shouldstartnewsubmap(frameid) — triggered either by a fixed frame count (newsubmapevery) or when the accumulated translation/rotation since the last submap start exceeds thresholds (50° or 5 m). On a new submap:

  • savecurrentsubmap() serializes anchor tensors + MLP weights to a .ckpt file.
  • startnewsubmap() reinitializes a fresh GaussianModel but transfers the three MLPs from the old model — so color/opacity/covariance knowledge is warm-started into the new submap.

3. Mapping (every map_every frames)

Mapper.map(frameid, estimatec2w, gaussianmodel, isnew_submap) (mapper.py, line 214):

a. Compute seeding mask — computeseedingmask():

- New submap: a color-gradient edge mask (geometricedgemask) seeds boundary-rich regions.

- Existing submap: pixels where rendered alpha is below threshold or depth error is anomalously high get marked for new Gaussian seeding.

- In the current committed code the mask is overridden by a fixed stride-2 grid (mask[::2, ::2] = True) before use.

b. Seed new 3D points — seednewgaussians(): unprojected to 3D via createpointcloud using the depth map and current c2w; gradient-sampled pixels are blended in to preserve edges.

c. Grow the submap — grow_submap():

Computes camera frustum corners, finds which existing Gaussian anchors fall inside the frustum (computefrustumpointids), then keeps only new candidate points that are farther than newpointsradius from any existing anchor (computenewpointsids). New anchors are voxelized and appended via GaussianModel.addpoints() → densificationpostfix().

d. Optimize — optimizesubmap(keyframes, gaussianmodel, iterations):

Randomly samples from the keyframe set on each iteration (weighted to prefer the current frame). Renders via rendergaussianmodel, computes colorloss + 0.05 * depthloss + isotropicloss, backpropagates, and calls gaussianmodel.optimizer.step(). The optimizer only touches the anchor/offset/anchorfeat/scaling tensors (MLPs are frozen during mapping via fixmlp()).

4. Tracking (when enabled)

Tracker.track(frameid, gaussianmodel, prev_c2ws) (tracker.py, line 113):

  • Initializes the camera pose from the odometry prior.
  • Sets up trainingsetupcamera() on the Gaussian model: all Gaussian/MLP parameter group learning rates are set to 0.0; only camunnormrot and cam_trans get non-zero LRs.
  • Iterates tracking.iterations times: calls computelosses(), which transforms Gaussian centers by the current relative-pose estimate (reltransform @ pts4.T), renders via rendergaussianmodel, computes a weighted color+depth L1 loss, and backpropagates only through the camera parameters.
  • Keeps track of the minimum-loss pose across all iterations and returns that as best_w2c.

Where the core idea lives — the "compact" trick

The key compactness mechanism is the anchor-based neural Gaussian representation inherited from Scaffold-GS, implemented in GaussianModel (src/entities/gaussianmodel.py) and decoded in generateneural_gaussians (src/utils/utils.py, line 229).

Instead of storing a separate position, color, opacity, and full covariance for every rendered Gaussian, the model stores:

  • _anchor: (N, 3) — one 3D anchor per voxel cell
  • offset: (N, noffsets, 3) — per-anchor offsets for n_offsets=5 child Gaussians
  • anchorfeat: (N, feat_dim=15) — compact feature vector per anchor
  • Three tiny MLPs: mlpopacity (feat+view → noffsets opacities), mlpcov (feat+view → 7*noffsets scale+rotation), mlpcolor (feat+view → 3*noffsets RGB)

At render time, generateneuralgaussians runs:


# Compute view-direction and distance for each anchor
ob_view = anchor - viewpoint_camera.campos
ob_dist = ob_view.norm(dim=1, keepdim=True)
ob_view = ob_view / ob_dist

cat_local_view_wodist = torch.cat([feat, ob_view], dim=1)  # [N, c+3]

# MLPs predict per-offset attributes
neural_opacity = pc.get_opacity_mlp(cat_local_view_wodist)   # [N*k, 1]
scale_rot      = pc.get_cov_mlp(cat_local_view_wodist)       # [N*k, 7]
color          = pc.get_color_mlp(cat_local_view_wodist)     # [N*k, 3]

# Derive child Gaussian centers from anchor + scaled offsets
offsets = offsets * scaling_repeat[:, :3]
xyz = repeat_anchor + offsets

Opacity masking further prunes the render list: child Gaussians with neuralopacity <= 0 are dropped before rasterization (mask = (neuralopacity > 0.0)).

Why this is compact: N anchors produce up to N×5 rendered Gaussians, but with far less stored state than N×5 independent Gaussians. The anchor grid is voxel-snapped (see voxelizesample, voxelsize=0.01), preventing duplicate anchor insertion and keeping the count bounded to the unique voxels that have been observed. The add_points method voxelizes before appending:


points = self.voxelize_sample(points, voxel_size=self.voxel_size)

An isotropic_loss in the mapper additionally pushes each Gaussian toward a sphere rather than a long needle, which improves both quality and prevents degenerate splats that would require more Gaussians to cover the same area.

Additionally, the MLPs are shared across submaps: startnewsubmap() copies mlpcolor, mlpcov, mlp_opacity from the old model to the new one. This means the MLP weights encode scene-agnostic rendering priors that carry over, reducing how much the new submap needs to learn from scratch.

Dependencies and why it needs a GPU

CUDA rasterizer — the entire differentiable rendering path depends on two custom CUDA extensions:

  • gaussianrasterizer — installed from github.com/VladimirYugay/gaussianrasterizer (imported in src/utils/utils.py line 8). This is a fork of the 3DGS rasterizer that adds depth output and alpha output as returns from GaussianRasterizer._call_.
  • diff-gaussian-rasterization-w-pose — installed from github.com/rmurai0610/diff-gaussian-rasterization-w-pose, used in src/gsr/renderer.py for the loop-closure registration path. This variant adds differentiable camera pose deltas (theta and rho arguments to the rasterizer).
  • simpleknn — CUDA k-nearest-neighbor used inside GaussianModel.createfrompcd / addpoints to initialize Gaussian scales as log(sqrt(nearestneighbordist)).

Without a GPU these custom C++/CUDA extensions simply will not compile or run. The alpha-composite rasterization requires GPU parallelism to be tractable; on CPU it would be O(pixels × Gaussians).

Other key dependencies:

  • open3d==0.18.0 — RGBD odometry in VisualOdometer, point cloud I/O and statistical outlier removal in Mapper.grow_submap
  • pygicp — ICP used in Tracker.track_icp (the faster-GICP tracking branch, currently present but unused in the committed main loop)
  • faiss-gpu — used in mapperutils.py for large-scale nearest-neighbor queries when computing new point insertion (computenewpointsids)
  • roma — unit-quaternion and rotation-matrix conversions, used throughout tracker and rigidtransformgaussians
  • torchscatter — scattermax in GaussianModel.anchor_growing to aggregate features from candidate child Gaussians to new anchors

SplatSim — code walkthrough

The big picture — connecting the dots

Start from how a robot gets good at anything: practice. To learn to pick up a cup, an arm needs thousands to millions of tries — grabbing, missing, dropping, colliding. Doing that with a real robot is brutal: each attempt takes seconds, the hardware wears out, things break, and a bad move can damage the arm or whatever's near it. A million real attempts is a non-starter.

So you practice in a simulator instead — a physics video-game world you can run faster than real time, in thousands of parallel copies, with no wear and no danger. Train the skill there, then move it to the real robot. Simple idea. It mostly doesn't work, for one stubborn reason: the world in the simulator is not the real world. The skill gets tuned to the sim's quirks, and then reality doesn't match.

For a robot that sees through cameras, the worst mismatch is how things look. In a normal simulator the images are computer graphics — clean, flat-textured, perfectly lit, a bit cartoonish. Real camera images are messy, richly textured, uneven light. A vision policy trained only on the cartoon images has never seen a real photograph; hand it a real camera feed and it's a student who studied from crude sketches being shown a photo — it doesn't recognise what it's looking at, and the skill falls apart. This is the reality gap, and its visual half is what breaks camera-based robots.

The two usual escapes are both unsatisfying. You can make the sim images vary wildly on purpose — random colours, textures, lighting — so the policy learns to ignore appearance and just be robust. But that throws away useful visual information and needs delicate tuning. Or you can hire artists to hand-build photorealistic 3D models of every object and room — accurate, but hopelessly expensive and it still never quite matches your actual workspace. The whole problem lives in the gap between "cheap but fake-looking" and "real-looking but unaffordable."

The unlock: Gaussian Splatting captures reality itself. Instead of an artist modelling a fake workspace, you just take a video of your actual workspace, and splatting reconstructs it into a photorealistic, renderable 3D scene — the real table, the real objects, the real light. It looks real because it is real, rebuilt from real photos. That single fact dissolves the appearance gap almost for free.

So SplatSim builds a bridge: capture the real workspace as a splat → drop that splat into a physics engine, so now the simulated world both obeys physics (the arm can practice touching, pushing, grasping) and renders images that look like real camera feeds → train the vision policy there for as many attempts as you like → put it on the real robot. Because everything it ever "saw" already looked like reality, there's no appearance shock on deployment, and the skill transfers with little or no real-world retraining. That's the "zero-shot" in the title.

The subtle hard part is motion. A splat is a frozen snapshot, but the arm moves and objects move when grasped — so you have to tie the blobs to the physical parts, so that when a joint rotates in the physics engine, the matching blobs move with it and the render stays truthful. (This is exactly what Robo-GS pushes further, welding blobs to a mesh so look and geometry move as one.) And splatting only fixes how things look, not how they physically behave — contact and friction realism is a separate battle.

Why this ties back to the whole theme: the same splat is doing double duty — it's a photorealistic renderer for the policy's eyes and a manipulable object for the physics engine, at the same time. That's the field's core bet again — one representation that many jobs can share — turned into a loop between imagining a skill cheaply and acting it out for real. The honest framing: SplatSim doesn't close the whole reality gap — it closes the appearance half cheaply, which happens to be the half that most breaks vision-based robots. The physics half is still yours to earn.

What the repo is / how you'd run it

The paper in one sentence: instead of building a textured mesh simulator, SplatSim uses 3D Gaussian Splatting (3DGS) — a learned volumetric scene representation — to turn a video of a real robot into a photorealistic simulator. A manipulation policy trained purely on rendered SplatSim images transfers to the real robot without any real-world training data (zero-shot sim2real).

Workflow at a glance

  • Scan the scene (robot + workspace) once with a smartphone. Train a Gaussian splat with the gaussian-splatting sub-repo. This gives you a point_cloud.ply containing millions of Gaussians representing the whole scene.
  • Calibrate the splat to the simulator. You hand-align the splat point cloud to the URDF skeleton in CloudCompare, then copy the resulting 4×4 transformation matrix into configs/object_configs/objects.yaml.
  • Label robot Gaussians by link. Run articulatedrobotpipeline.py, which renders each link independently in PyBullet, runs a KNN in 3D to label every splat Gaussian with a link index, and saves the result to data/labelspath/<robotname>_labels.npy.
  • Generate demonstration trajectories (or load provided ones). Launch a PyBullet server that auto-plans pick-and-place motions and records joint states + object poses as .pkl files in configs/folderconfigs.yaml > trajfolder.
  • Render training images. Replay recorded joint-state trajectories; at each step, run the FK→Gaussian transform→rasterizer pipeline to produce a photorealistic RGB image. Images land in <trajfolder>/<N>/images1/.

The pipeline — traced through the actual code

Step 0: one-time calibration (articulatedrobotpipeline.py)

Before any rendering, you must label every Gaussian in the robot's splat with its robot link index.

  • Load the trained splat into a GaussianModel object (gaussians = GaussianModel(dataset.shdegree); scene = Scene(...)). Extract the 3D means: robotxyz = gaussians.get_xyz.cpu().detach().numpy().
  • Load the robot URDF into PyBullet at the joint angles recorded at scan time (joint_states in objects.yaml).
  • For each link i, hide every other link (changeVisualShape(..., rgbaColor=[1,1,1,0])), then call getoverallpcd() (nine synthetic PyBullet cameras → depth images → 3D points). This gives a point cloud that is geometrically exactly link i.
  • Combine all link clouds into (X, y) and train a KNeighborsClassifier(n_neighbors=10) on URDF space.
  • Transform the real splat Gaussians into URDF space using the calibration matrix from objects.yaml, apply the AABB filter to exclude non-robot Gaussians, then call knn.predict(splat_points) — each Gaussian gets a link label.
  • Save as data/labelspath/<robotname>_labels.npy.

This is the only step that requires the calibration matrix to be already correct. The AABB bounding box is also auto-computed here and written back into objects.yaml.

Step 1: server startup (launchnodes.py → PybulletRobotServerBase.init_)

launchnodes.py reads --robot and instantiates the matching server subclass, e.g. AppleOnPlatePybulletRobotServer. The base class constructor (PybulletRobotServerBase.init_) does several things in sequence:

  • Loads data/labelspath/<robotname>labels.npy and parks it on GPU as self.robotlabels (a long tensor).
  • Starts the ZMQ server (pickling protocol: commandjointstate, getobservations, setobject_pose).
  • Loads the robot URDF into PyBullet as self.dummy_robot.
  • Reads joint_states from objects.yaml and sets the initial configuration.
  • For every object in ENVCONFIG["objects"] (e.g. plasticapple, plate), loads its .ply into a GaussianModel via self.objectgaussians[i].loadply(ply_path).
  • Loads the robot's trained scene (colmap cameras + splat) via Scene(dataset, self.gaussiansbackup, ...). self.gaussiansbackup now holds the static full-scene Gaussian cloud.
  • Pre-computes and caches the calibration transformation tensors (populatetransformationscache) on GPU to avoid recomputation every frame.
  • Picks camera cami from the colmap dataset as the fixed base camera (self.basecamera).

Then serve() sets initial joint positions, calls getcurrlinkstates() to record self.initiallink_states (the reference FK pose), and enters the main loop.

Step 2: receiving a joint command (commandjointstate)

The client (e.g. ReplayTrajectoryAgent) sends a joint state over ZMQ. The server receives it and calls self.robot.commandjointstate(joint_state), which in PybulletRobotServerBase:


for i in range(1, self.num_dofs()):
    self.pybullet_client.setJointMotorControl2(
        self.dummy_robot, i, p.POSITION_CONTROL,
        targetPosition=joint_state[i - 1], force=1000,
    )

PyBullet now knows the new joint angles and will compute their FK when asked.

Step 3: computing link transforms (gettransfomrationlist in robotsplatrender_utils.py)

At render time, prepimagerendering calls gettransfomrationlist(self.dummyrobot, self.initiallink_states):


def get_transfomration_list(robot_uid, initial_link_states, use_link_centers=True):
    new_joints = get_curr_link_states(robot_uid, use_link_centers=use_link_centers)
    transformations_list = []
    for joint_index in range(num_joints):
        input_1 = (initial_link_states[joint_index]["pos"], initial_link_states[joint_index]["q"])
        input_2 = (new_joints[joint_index]["pos"], new_joints[joint_index]["q"])
        r_rel, t = compute_transformation(input_1, input_2)
        ...
        transformations_list.append((r_rel, t))
    return transformations_list

getcurrlinkstates calls p.getLinkState(..., computeForwardKinematics=True) for every joint — this is PyBullet running the full forward kinematics chain. computetransformation (in utils_fk.py) derives the relative SE(3) between the initial and current link pose:


def compute_transformation(pose_a, pose_b):
    r1 = quaternion_to_rot_matrix(q1)
    r2 = quaternion_to_rot_matrix(q2)
    r_rel = np.matmul(r2, r1.T)               # relative rotation
    T = [x2,y2,z2] - r_rel @ [x1,y1,z1]      # relative translation
    return r_rel, T

Result: one (Rrel, trel) pair per link, living on GPU as float32 tensors.

Step 4: segmenting and moving robot Gaussians (getsegmentedindices, transform_means)

prepimagerendering calls getsegmentedindices(...), which:

  • Transforms all Gaussian means from splat space into URDF space using the calibration matrix Trans.
  • Filters to the robot AABB (discards background Gaussians).
  • For each link i, selects the subset of in-AABB Gaussians whose .npy label equals i:
    • 
   condition = torch.where(condition)[0]
   for i in range(p.getNumJoints(robot_uid)):
       segmented_points.append(condition[robot_labels == i])

Then transformmeans(robotuid, pc, xyz, segmentedlist, transformationslist, ...) applies the per-link rigid transform to each group of Gaussians:


for joint_index in range(p.getNumJoints(robot_uid)):
    r_rel, t = transformations_list[joint_index]
    segment = segmented_list[joint_index]
    # Move Gaussian centers
    xyz[segment] = torch.matmul(r_rel, xyz[segment].T).T + t
    # Rotate Gaussian orientations (stored as quaternions → matrix → rotate → back)
    rot_rotation_matrix = (inv_rotation_matrix * scale_robot) @ r_rel @ rotation_matrix
    tranformed_rot = o3.quaternion_to_matrix(rot[segment])
    transformed_rot = rot_rotation_matrix @ tranformed_rot
    rot[segment] = o3.matrix_to_quaternion(transformed_rot)
    # Rotate spherical harmonics (view-dependent color)
    shs_feat = transform_shs(shs_featrest[segment], rot_rotation_matrix)
    shs_featrest[segment] = shs_feat

After the loop, the entire cloud is transformed back to splat space via invrotationmatrix.

The SH rotation deserves special mention. Each Gaussian stores its color as spherical harmonics coefficients (degree 0–3, 15 coefficients × 3 RGB channels). When the Gaussian rotates, those coefficients must rotate too, or the view-dependent highlights will be wrong. transformshs builds Wigner-D matrices for degrees 1, 2, 3 using e3nn.o3.wignerD and applies them as a block-diagonal matrix to the SH bands:


D = torch.block_diag(D_1, D_2, D_3)   # (15, 15)
sh = einops.rearrange(shs_feat[..., :15, :], '... s r -> ... r s')
sh_rot = torch.einsum('...ij, ...rj -> ...ri', D, sh)
shs_feat[..., :15, :] = einops.rearrange(sh_rot, '... r i -> ... i r')

Step 5: placing object Gaussians (transform_object)

For each manipulated object (e.g. the apple), transformobject(self.objectgaussians[i], object_config, pos, quat, ...) does:

  • Apply the object's own calibration matrix (Trans_canonical) to put its Gaussian means into a canonical frame.
  • Apply the object's AABB filter to discard splat noise outside the object boundary.
  • Apply quat (the current PyBullet rigid-body pose) to rotate and translate the object, then map back into robot-splat space via the inverse of the robot calibration matrix.
  • Rotate the object's SH coefficients by the same combined rotation via transform_shs.

Result: a set of Gaussian attributes (xyzobj, rotobj, opacityobj, scalesobj, featuresdcobj, featuresrestobj) in splat space, at the correct current pose.

Step 6: compositing and rendering

Back in prepimagerendering, robot Gaussians and all object Gaussians are concatenated into the single self.robot_gaussian placeholder:


self.robot_gaussian._xyz = torch.cat([xyz] + xyz_obj_list, dim=0)
self.robot_gaussian._rotation = torch.cat([rot] + rot_obj_list, dim=0)
# ... same for _opacity, _features_rest, _features_dc, _scaling

Then render_image calls the 3DGS rasterizer:


rendering = render(camera, self.robot_gaussian, self.pipeline, self.background)["render"]

render is gaussiansplatting.gaussianrenderer.render — the standard 3DGS forward pass: sort Gaussians by depth, project to screen, alpha-blend. The CUDA kernel (diff-gaussian-rasterization) does this efficiently on GPU.

The result is a (3, H, W) float32 tensor; renderimage returns it. getobservations packs it as observations["base_rgb"].

Step 7: saving training data (ReplayTrajectoryAgent / followtrajectoryand_record)

ReplayTrajectoryAgent.act() reads the next .pkl frame from the recorded trajectory, restores object poses via env.robot.setobjectpose(...), and returns the joint angles. When saveimages=True it also saves every *rgb image from obs to <trajfolder>/<N>/images_1/.

In GENERATEDEMOS mode, followtrajectoryandrecord (in simrobotpybulletbase.py) saves a full observations dict as a .pkl every 50 physics steps; this includes basergb (the rendered frame), joint positions, EE pose, and object poses. That pickle file is the training sample for the downstream diffusion policy.

Where the core idea lives

The core contribution — making a static learned scene representation behave like an articulated robot — is implemented in:

splatsim/utils/robotsplatrender_utils.py

The key functions:

  • getsegmentedindices (line 208): groups Gaussian indices by link using the pre-computed KNN labels. This is what allows treating each link's Gaussians as a separate rigid body.
  • transformmeans (line 52): the main loop that applies one SE(3) per link to the corresponding Gaussian subset. Three quantities are transformed: the 3D mean positions (xyz), the orientation quaternions (rot, which determine the covariance ellipsoid shape and orientation), and the spherical harmonic coefficients (shsfeatrest, which determine view-dependent color). All three must be transformed consistently or the rendered appearance will be wrong.
  • transform_shs (line 160): rotates SH coefficients using Wigner-D matrices. This is the mathematically subtle part — naive SH rotation is expensive; using the block-diagonal Wigner-D structure makes it a single batched einsum.
  • transform_object (line 101): maps a separately-scanned object splat from its own canonical frame into the correct world pose, respecting scale differences between the robot-splat and object-splat calibration matrices.

The bridge to PyBullet is in gettransfomrationlist + computetransformation in utilsfk.py (line 40):


r_rel = np.matmul(r2, r1.T)
T = np.array([x2, y2, z2]) - np.matmul(r_rel, np.array([x1, y1, z1]))

This gives the relative rigid-body transform of each link from its reference pose, which is then applied to that link's Gaussians.

The actual call chain per rendered frame in PybulletRobotServerBase.prepimagerendering:


PyBullet FK  →  get_transfomration_list  →  get_segmented_indices
→  transform_means (robot Gaussians)
→  transform_object (for each object)
→  torch.cat all into self.robot_gaussian
→  render(camera, self.robot_gaussian, ...)  →  RGB tensor

Dependencies & why it needs a GPU

| Dependency | Role |

|---|---|

| diff-gaussian-rasterization (CUDA, in submodules/gaussian-splatting-wrapper/gaussian_splatting/submodules/) | GPU rasterizer: projects Gaussians, sorts by depth, alpha-blends. Must be compiled against your CUDA/PyTorch. This is the reason the repo requires a GPU — CPU inference is orders of magnitude too slow for interactive use. |

| simple-knn (CUDA submodule) | Used internally during 3DGS training for neighbor queries. |

| e3nn | Equivariant neural network library. Used here only for its Wigner-D matrix computation (o3.wignerD) and quaterniontomatrix / matrixto_quaternion. |

| einops | Tensor reshape/rearrange shorthand used in transform_shs. |

| pybullet | Physics engine: FK via getLinkState(computeForwardKinematics=True), IK, collision, trajectory planning. Runs CPU-only; it is the "simulator" that drives joint motion. |

| pybulletplanning | Motion planning on top of PyBullet (planjoint_motion) used in demo generation. |

| open3d | Point cloud visualization and I/O used in articulatedrobotpipeline.py and cameras.py. |

| sklearn KNeighborsClassifier | One-time use in articulatedrobotpipeline.py to propagate link labels from URDF point cloud to splat Gaussians. |

| zmq | Socket transport between the server (physics + render) and client (agent). |

| gello_software (submodule) | ZMQ RobotEnv / ZMQClientRobot / ZMQServerRobot node framework that the entire client-server architecture is built on. |

| PyTorch 2.7 + CUDA 12.6 | All Gaussian operations (transform, render) run on GPU tensors. |

The GPU bottleneck is the rasterizer. Each render() call projects and alpha-composites potentially hundreds of thousands of Gaussians. On a modern GPU (RTX 3090 class) this is ~30–100ms depending on resolution and Gaussian count, which determines the achievable rendering rate for data collection.
