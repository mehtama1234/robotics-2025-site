We ran the methods — not just read them

For eleven of the standout 2025 papers we cloned the real code and ran it ourselves, on GPUs and laptop CPUs, to produce the results below. These are our own outputs, not figures lifted from the papers. Each links to the theme where it lives. ⌂ Home

Reading a method tells you what it claims; running it tells you what it does. Every visual here came out of a real run — a self-driving stack turning six camera feeds into a plan, a colon rebuilt from endoscope video, thirty-two robots threading a maze. Where a paper's weights were locked away, we say so and use an honest stand-in.

SparseDrive GPU · Colab L4

End-to-end self-driving from 6 cameras: detection, tracking, motion forecasts, and a planned “turn right” path — all from ~100 sparse tokens in a single forward pass.

clone + run on nuScenes-mini · torch 1.13 / cu116 · the sparse-token idea, executed
What running it taught usThe clean sparse-token story hides fragile plumbing: the planner's anchor must be a 4-D (3,6,6,2) tensor and map ground-truth an empty dict — both undocumented — and on torch 1.13 you hand-write the attention the paper assumes exists.

LightStereo GPU · Colab L4

Depth from two cameras a fixed gap apart: near road warm, far scene cool, the pedestrian and cars resolved as distinct distances — the disparity-to-depth law, live.

MODEST — transparent-object perception CPU · Colab

From a single RGB photo of a clear glass, it estimates depth and segments the transparent object (red) — exactly the case where ordinary depth cameras fail, because the light passes straight through the glass and the sensor reads the table behind it.

L-J-Yuan/MODEST · ClearPose weights · CPU-forced inference · our own glass photo as input
What running it taught usThe repo's only bundled “test image” is the paper's own pipeline diagram — run it as-shipped and you get nonsense. You must supply a real transparent-object photo yourself, and only after a NumPy-2 downgrade, removing the shadowing datasets package, and fixing a device-placement bug does it run at all.

What actually running them taught us

Reproducibility is a spectrum, not a yes/no. One paper ran with a single command (NeuFlow); others needed an hour of dependency archaeology, a gated-weights workaround, or an honest stand-in.

The paper is often the easy part. The undocumented tensor shape, the broken export script, the wrong default checkpoint — these decide whether a method works, and none of them are in the PDF.

Code rots fast. 2025 papers already break against NumPy 2, CUDA 13, and torch's moving API. “State of the art” has a shelf life measured in months.

Domain match beats cleverness. LightStereo's architecture was secondary to using weights trained on the right kind of image.

Reading a paper tells you the idea; running it tells you the cost — and the cost is where the real understanding lives.
