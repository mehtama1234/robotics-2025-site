Language models that plan the job

54 papers · the decide part of the loop — turning a spoken goal into a safe, ordered set of robot steps

The big picture — connecting the dots

Language models are unreliable planners on their own — they invent steps a robot cannot do, ignore the actual room layout, and forget what happened minutes ago. But they are exceptional at understanding human intent in natural language. The insight threading through almost every paper here is that a language model should be a flexible idea-generator paired with a grounding layer that checks, adapts, and constrains — not a planner left alone to hallucinate. A robot planning a task needs three things the model lacks: memory of what the world actually looks like, a way to test whether each step is possible before acting, and context about which choices matter for tasks later. The papers below show different ways of bolting those things onto a language model so the output shifts from conversational text that sounds right to executable plans that work.

Five things people are actually trying to do with it:

  • ① Keep the model aware of the real world. KARMA maintains both a persistent 3D map and a timestamped log of recent changes, feeding both into the language model when it plans. E2Map tags locations with scores from past attempts so the model learns which parts of the space are risky. TR-LLM feeds observed movement trajectories plus scene context into the model so it can anticipate what the people in the scene are about to do — planning that accounts for humans, not just the empty room.
  • ② Test each step for feasibility before committing. ConceptAgent pairs the language model with a tree-search planner that backtracks when a proposed step turns out impossible. Enhancing Robustness in Language-Driven Robotics builds a verification layer that checks preconditions and detects mistakes in real time as the robot executes.
  • ③ Ground plans in written rules, not just the model's knowledge. SayComply retrieves relevant operational rules and safety policies from a structured database before the model writes each step. 3DWG uses structured visual grounding to anchor language understanding in what the robot can actually see and manipulate.
  • ④ Adapt general plans to the specific robot and place. AdaptBot generates a plan with a language model, then checks every step against a knowledge graph of facts about the environment — if something does not fit, it asks a human for clarification and stores the answer. Multi-Floor Zero-Shot Object Navigation Policy extends single-floor planning to reason about which floor likely holds the target without task-specific retraining.
  • ⑤ Act in a way that fits the social setting, not just the goal. A plan can be perfectly efficient and still be rude, unsafe, or unwelcome around people. GRACE weighs whether an action is socially appropriate — not only whether it achieves the task, but whether it is acceptable to the humans nearby — so the plan respects social norms, not just task logic.

The throughline: language models have made robots genuinely more flexible at understanding goals, but planning is not language work — it is a discipline that requires checking, memory, and commitment to ground truth. The 2025 work is the productive phase of learning how to couple the model's linguistic flexibility with hard constraints: a checked plan, a traced-out world, and verification that steps work before the robot commits. Everything below is a different angle on that same coupling. Still open: making the entire pipeline reliable and predictable enough to trust with safety-critical tasks; building long-term memory that scales to homes where the robot lives for years; and balancing the model's adaptability with formal guarantees that the plan is safe.

The problem — in depth

Every time you hand a robot a task in plain words — "clean up the kitchen" or "find my keys" — you are asking it to do something remarkably hard. The robot must figure out what you mean, break that meaning into concrete physical steps, check that each step is actually possible in the room it is in right now, and do all of this without hurting anyone or breaking anything.

Older planning systems handled this by having a person write out every rule by hand in advance: if the cup is on the table and the hand is empty, then pick up the cup. This works for narrow, fixed jobs, but it falls apart the moment something unexpected happens or the goal changes. A human cannot write rules for every possible kitchen layout, every possible object, every possible instruction.

The breakthrough idea here is to use the same kind of AI that powers conversational chatbots — systems trained on enormous amounts of text so that they understand language the way a person does — to do the step-making instead. These systems, called large language models (LLMs), can take "clean up the kitchen" and produce a reasonable list of steps without anyone pre-writing the rules. That is genuine progress.

But it brings new problems. These AI systems were trained to produce text that sounds right, not steps that are physically possible. They invent steps the robot cannot carry out. They do not know where the robot is, what the room looks like, or what rules the site has about safety. They forget what happened earlier in a long task. They plan each task as if it is the only task the robot will ever do, which leads to choices that are cheap now but costly later.

These problems matter because they sit at the exact center of what makes robots hard. A robot must take in an unclear, changing world, decide what to do, move a real body, and do all of that fast, cheap, safe, and across many situations — not just the ones it was trained on. The decide step is where the plan either holds together or falls apart. If the plan is wrong, everything downstream — every move the robot makes — is wrong too.

The approaches — how the field actually tackles it

Giving the language model a memory of the world

In plain termsThe robot keeps a running diary of the room—what's where, what moved—so when the AI needs to plan the next step, it's working from facts instead of guessing.
The sub-problemA language model knows language but not the specific room the robot is in right now. It needs a structured record of what the robot has seen so it can make plans grounded in real places, not hallucinations.
Memory logging — KARMA (ICRA). Maintains two separate logs: a persistent 3D map of the whole space that does not reset between tasks, and a short-term log of recent changes (an object moved, a drawer opened) that updates constantly.
Experience map with emotion — E2Map (ICRA). Tags every location in the robot's map with a score recording how well the robot's own past attempts there went, so the language model plans around places where things failed before.
Knowledge graph for task planning — L3M+P (ICRA). Stores everything the robot knows in a structured web of facts that updates whenever the robot sees or hears something new; when a task arrives, the language model reads the relevant parts and a separate classical planner turns that into executable steps.

The language model supplies flexible understanding of the goal, while the structured memory supplies the grounding the model lacks on its own.

Checking that each step is actually possible before acting

In plain termsBefore the robot actually moves, someone checks whether the plan makes physical sense—kind of like reviewing a checklist for "is there a cup there?" before asking the robot to grab it.
The sub-problemA language model can write steps that look plausible but cannot be carried out in the real world. You need a checking layer that tests each planned step against actual physical conditions before the robot moves.
Tree search with precondition checking — ConceptAgent (ICRA). Pairs the language model with a tree search process (Monte Carlo Tree Search) that tries many possible action sequences and checks at each node whether the required conditions are actually present; if a step is impossible, the search backtracks and tries a different path.
Real-time step verification — Enhancing Robustness in Language-Driven Robotics (IROS). Wraps a smaller on-board language model in a checking system that tests each step for feasibility before the robot commits to it, then detects and corrects mistakes on the fly when they occur anyway.

The language model acts as a first-draft generator, not a trusted authority—the checking layer catches what the model gets wrong before the robot moves.

Writing plans in a form that can be verified and executed reliably

In plain termsInstead of the AI writing freeform sentences, push it to write in a simple code-like format that a computer can read and check for mistakes automatically—no ambiguity, no reinterpretation needed.
The sub-problemMake the language model produce plans in a structured, checkable form from the start — not free text, but code or formal logic that a separate system can test for correctness without depending on the model being right.
Rule-grounded planning — SayComply (ICRA). Organizes a site's operations manuals and safety rules into a tree-shaped database and retrieves relevant passages before the language model writes each step, so the plan is grounded in actual written rules.
Syntactically correct code generation — LTLCodeGen (ICRA). Sidesteps the language model's tendency to write incorrect formal logic by using code generation rules that guarantee the output is syntactically correct; that correct code feeds directly into a motion planner.
Linguistic frame parsing — FrameCRL (ICRA). Avoids large language models entirely at plan time by parsing each spoken instruction using a structured set of linguistic meaning units (FrameNet frames) to extract precise goals, then passes those to a formal task planner.
Preference maps — Path Planning Using Instruction-Guided Probabilistic Roadmaps (ICRA). Uses a language model to convert stated travel preferences into a cost map (a number assigned to every location indicating how much the robot should prefer or avoid it), which the path planner reads directly.

Get the output of the language step into a form that can be checked or executed mechanically, without depending on the model's judgment.

Adapting the plan to the specific robot and environment

In plain termsA plan that works in theory might not work in this kitchen, with this robot, on this Tuesday. Constantly check the plan against what's actually here and ask a human for help if something doesn't fit.
The sub-problemA general plan written by a language model may be fine in the abstract but wrong for this robot in this room with these constraints. Ground plans against the actual setup instead of the model's generic knowledge.
Knowledge graph grounding — AdaptBot (ICRA). Generates a general plan with a language model, then checks every step against a structured knowledge graph of known facts about the specific environment; when a step doesn't fit, the robot asks a targeted question to a nearby human and stores the answer.
Multi-floor reasoning — Multi-Floor Zero-Shot Object Navigation Policy (ICRA). Extends single-floor visual search to reason about when to switch floors in a multi-story building, using visual and language-based understanding to guess which floor likely has the target without task-specific training.
Contextual object relationships — Language-Guided Object Search in Agricultural Environments (ICRA). Asks a language model which objects tend to appear near which other objects, then uses those relationships to plan a search route covering the most probable spots first in an unfamiliar setting.

Robot can adapt a general plan to the specific constraints and layout it actually faces, not just what the model assumes.

Planning ahead across many tasks, not just the current one

In plain termsInstead of just finishing this job as fast as possible, the robot thinks ahead: "If I put this here now, will the kitchen be a mess for the next task?" It trades speed today for ease tomorrow.
The sub-problemMost planners optimize for the task in front of them. But a robot used all day needs to make choices that keep future tasks easy too—trading off finishing now against leaving the space ready for what comes next.
Anticipatory state estimation — Anticipatory Planning for Performant Long-Lived Robot in Large-Scale Home-Like Environments (ICRA). Uses a graph neural network to estimate how hard future tasks are likely to be given the current state of the room, then chooses actions balancing task completion with keeping the space in a state where future tasks stay easy.

Robot plans for a long day, not just the next step, making choices that leave the space ready for tasks to come.

Where it stands

Language models have made robots genuinely more flexible at the decide step: they can now accept open-ended goals in plain words and produce reasonable starting plans without hand-coded rules. The main open problems are reliability and trust — these models still invent impossible steps, still fail to account for safety rules they were not shown, and still struggle when a task runs long enough that memory and context matter. The checking and grounding techniques in these papers reduce failure rates but add complexity, and most have been tested only in specific domains or simulated settings. Making this whole pipeline fast, safe, and general enough to run on any robot in any environment is the work still ahead.

KARMA: Augmenting Embodied AI Agents with Long-and-Short Term Memory Systems

The big idea — first principles

The problem. When a language model plans a task for a robot mid-way through it, the model has forgotten what the world looks like and what just changed—it treats each step as if it's starting fresh, leading to plans that ignore moved objects or updated states.

The approach. Maintain two structured records as the robot moves and acts: a long-term 3D map of the whole space, and a short-term log of recent changes. Feed relevant excerpts from both into the prompt before each planning step so the model sees both the permanent layout and what just shifted.

What's unique. Earlier systems asked the LLM to track state internally; here memory is external and structural (scene graphs + timestamped logs), injected into prompts without retraining the model. The robot treats memories like reference materials, not learned knowledge.

ICRA 2025 · 5 citations · memory-agent

What it does — 2-3 plain sentences

KARMA gives a household robot two separate memory systems that work together when the robot plans its next action. Long-term memory stores a 3D map of the entire space as a scene graph (a structured representation of what objects are where and what they are), while short-term memory tracks recent changes—when something moved or changed state. When an LLM is asked to plan the next step for a multi-step task, it receives relevant excerpts from both memories as context, so it knows not only what the house looks like generally, but what has changed since the robot last looked.

Sub-approach: memory-agent — a system with long-and-short-term memory augmentation that an LLM consults during planning.

The method, in detail

The system works in a cycle during task execution:

  • Long-term memory (LTM) construction: As the robot observes its environment (via computer vision), the system builds a 3D scene graph—a structured format where each object is a node with properties (type, location, state) and edges represent spatial relationships. This graph is persistent and grows or updates as the robot explores.
  • Short-term memory (STM) recording: Simultaneously, the system logs dynamic changes—"apple moved from counter to sink", "drawer opened", "pot is now on stove". These entries are timestamped and track what has changed since the long-term model was last updated.
  • Memory replacement strategy: Short-term memory has a fixed size. When it fills up, the system uses an adaptive replacement policy: it keeps entries that are relevant to the current task or recent history, and discards older or less pertinent changes. The paper does not specify the exact algorithm, but the strategy is designed to preserve critical information (e.g., "the target object moved here") while dropping noise.
  • LLM prompting with memory: When the LLM is asked "what should the robot do next?", instead of giving it only the task description, the system constructs a prompt that includes:

- The original high-level task (e.g., "wash an apple and put it on the countertop")

- Relevant objects and their locations extracted from the long-term scene graph

- Recent changes from short-term memory (what just happened)

- The robot's current state and capabilities

  • Plan generation and execution: The LLM decomposes the task into a sequence of primitive actions (grasp, move, place, navigate). After each action, the robot updates both memories based on what actually happened, then re-prompts the LLM for the next step. This closes the loop: the agent adapts its plan if objects moved unexpectedly or if the real world differed from what was predicted.

Key technical trick: Memory-augmented prompting without retraining. The LLM is not fine-tuned; instead, the right memories are injected into the prompt context. This makes the approach plug-and-play and compatible with any LLM (the paper used OpenAI's models, but the method is agnostic).

Multi-Floor Zero-Shot Object Navigation Policy

The big idea — first principles

The problem. A robot searching a multi-story building doesn't know which floor holds the target without searching each one exhaustively—floor transitions take time and add risk, so wasting them matters.

The approach. Separate the search into two loops: on each floor, do classical visual exploration with semantic segmentation. When stairs appear, ask a language model whether switching floors is worth it given what you're looking for, then use a vision-language model to evaluate each new floor before committing.

What's unique. Coupling spatial search (visual mapping on each floor) with semantic reasoning (LLM floor-choice, VLM target verification) so the robot doesn't brute-force floors but reasons about likelihood before moving.

ICRA 2025 · 5 citations · language-navigation

What it does — 2-3 plain sentences

A robot searches for objects in buildings where the target might be on a different floor from where it starts. The system extends single-floor visual search to reason about when and how to move between floors, using visual understanding and semantic reasoning to decide which floor is likely to have the object without needing any training data specific to the building or task. Sub-approach: language-navigation—the framework uses visual-language models and LLMs to guide exploration across spatial boundaries.

The method, in detail

Input and observation:

The robot navigates using RGB-D images and its pose (position and orientation). It builds a semantic map as it explores, recording where it has seen different object categories. The map persists across single-floor exploration but must reinitialize when moving to a new floor.

Three-stage pipeline:

  • Semantic mapping and candidate generation: As the robot moves on a floor, RGB-D frames are converted to a 2D bird's-eye-view semantic map using a pretrained segmentation model (Mask2Former). Unexplored or frontiers of interest are scored as candidate waypoints for the next step.
  • LLM-based floor reasoning: When the agent reaches stairs or boundary markers (e.g., an elevator), an LLM (Qwen2) is prompted to decide whether to attempt a floor transition. The prompt includes the current floor, object type being searched for, semantic map summary, and exploration statistics. The LLM outputs a yes/no decision and reasoning.
  • VLM-based target verification and inter-floor navigation: Once inter-floor movement is attempted, a vision-language model (Qwen2-VL-Int4, quantized for speed) evaluates images taken at candidate locations. It scores confidence that the target object is present. The model combines image region descriptions from semantic segmentation with natural-language reasoning about whether this floor is likely to contain the object.
  • Stairway detection and navigation: The system identifies staircase or elevator features in the semantic map and uses navigation primitives (geometric path-following) to physically traverse them. After crossing to a new floor, the map is cleared and re-mapped from the new floor.

Training and optimization:

Zero-shot: no training on the test environment or dataset. The models (Qwen2 LLM, Qwen2-VL-Int4 VLM, Mask2Former segmentation) are all pretrained on large text and image corpora. The only adaptation is prompt engineering—writing natural-language instructions that guide the LLM and VLM to make sensible floor-transition decisions.

The trick that makes it work:

Decoupling single-floor navigation (handled by classical semantic mapping and exploration) from multi-floor reasoning (handled by LLM prompt-based decision-making). The LLM acts as a commonsense filter: it asks "does this floor make sense for finding a kitchen?" rather than blindly trying stairs. The VLM adds visual grounding by re-evaluating target plausibility after each floor change.

E2Map: Experience-and-Emotion Map for Self-Reflective Robot Navigation with Language Models

The big idea — first principles

The problem. A language model planning a path doesn't know which locations are physically risky—it treats an empty room as a blank slate each time, leading to repeated collisions in tight or awkward spots.

The approach. After each navigation attempt, capture images of what went wrong, feed them to an LLM to describe the event in words, then score that event for emotional impact (how much it hurt, how much was the robot's fault). Encode those emotions as Gaussian bumps on a spatial map, making risky areas naturally repellent to a planner.

What's unique. Encoding learned risk as continuous spatial distributions (not binary obstacles) so the planner sees gradients and can find genuinely better paths around troublesome spots, and fusing LLM semantic understanding with embodied spatial memory.

ICRA · 4 citations · language-navigation

What it does — 2-3 plain sentences, and which sub-approach it is

E2Map lets a robot that is navigating to a goal by following instructions from a large language model (LLM) learn from what actually happened when things went wrong. Instead of just trusting the LLM's general knowledge, the robot builds a spatial map where each location is tagged with both what the LLM thinks and how well the robot's own attempts there worked, encoding success or failure as a spatial emotional response (positive or negative "feeling" for that spot). After each navigation attempt, the map updates, and the next time the robot plans a path, it avoids places where it previously struggled. This is the language-navigation sub-approach: it combines LLM-based path planning with real-world experience grounding.

The method, in detail — step by step, plain words but technical

Input to the system: A high-level natural-language goal ("Go to the kitchen"), the robot's current position in a 2D environment, and a continuous stream of observations (RGB images, odometry, event timestamps).

Core data structure—the Experience-and-Emotion Map:

A grid map overlaid on the environment where each cell stores two things:

  • *Visual-language features* (learned by LSeg, a pre-trained vision-language model): These encode what objects are visible in that location using open-vocabulary object detection—essentially rich descriptions of what is at each spot without needing pre-trained labels.
  • *Emotion parameters*: These are not discrete labels but continuous spatial distributions modeled as weighted sums of multivariate Gaussian distributions. Each event (collision, slipping, success) creates a Gaussian bump centered at the location where it happened, with its shape and intensity reflecting the severity of the experience.

How emotions are encoded and stored:

When an event occurs (e.g., the robot bumps into a wall), the system captures three timestamped RGB images—before, during, and after the event—and sends them to GPT-4o (a vision-language model) with step-by-step reasoning instructions. GPT-4o outputs a natural-language description of what happened (e.g., "The robot hit an obstacle while turning"). Then a second LLM (Llama3 running locally) reads this description and two emotional criteria:

  • *Upsetness*: How much does this event matter to the agent's mission? (Did it slow down task completion or cause a hard crash?)
  • *Guiltiness*: Does the agent feel it caused this problem, or was it an external factor? (The system distinguishes self-caused mistakes from environmental surprises.)

These two numeric scores are combined into an *emotion value* (a continuous scalar, not discrete). This emotion value parameterizes a Gaussian distribution placed at the event location. The Gaussian's standard deviation (σ) follows the Weber-Fechner law—a psychophysical principle meaning emotional response scales logarithmically with stimulus intensity: σk^new = σk · vk · log(semo / T), where s_emo is the emotion score and T is a normalization constant. This makes the robot's spatial memory blur out gradually from high-emotion events, capturing how humans remember traumatic experiences with hazy peripheral details.

Planning with the emotion map:

When the robot needs to navigate to a goal, it converts each emotion Gaussian into a navigation cost in the D* pathfinding algorithm (a real-time planning method that recalculates paths as the map changes). High-emotion regions become navigation obstacles—the robot naturally avoids them. After each navigation attempt, if a new event occurs, the map updates (one-shot adaptation), and the robot immediately replans using the updated cost landscape.

The training/optimization part:

There is no offline training. The system learns online: each time the robot experiences an event, it updates the map and improves the next plan immediately. This is what "one-shot behavior adjustments" means—no iterative re-training required.

The trick that makes it work:

Unlike reinforcement learning (which needs thousands of trials) or static methods (which only use LLM priors), E2Map fuses two knowledge sources—the LLM's commonsense understanding of places and the robot's embodied memory of what went wrong—into a single spatial representation. By encoding emotions as continuous Gaussians rather than binary obstacles, the cost landscape has smooth gradients that the planner can use to find genuinely better paths. The robot doesn't memorize "don't go here ever" but learns "this area is risky, plan around it cautiously."

ConceptAgent: LLM-Driven Precondition Grounding and Tree Search for Robust Task Planning and Execution

The big idea — first principles

The problem. A language model drafts a plan step-by-step, but each step assumes preconditions the model can't see—the gripper must fit, the object must be reachable, the next step's prerequisite must hold. The robot only discovers this is wrong *after* attempting the step and failing.

The approach. Before the robot executes any step, verify the preconditions formally against the 3D scene. If a step is impossible, use tree search (Monte Carlo Tree Search) to explore alternative action sequences from that point, backtracking and trying different paths until one succeeds.

What's unique. Treating LLM-generated plans as drafts, not gospel—a formal precondition grounding layer catches impossibilities before wasted robot moves, and tree search lets the system recover without throwing away the whole plan.

ICRA 2025 · 4 citations · grounding

What it does — 2-3 plain sentences, and which sub-approach it is.

ConceptAgent takes a high-level task (like "clean up the kitchen") and breaks it into robot-executable steps using a language model, but crucially verifies each step before the robot attempts it—checking whether the preconditions (the things that must be true before the step can work) are actually met in the real world. When a step fails, the system detects this and replans immediately rather than crashing. This is a grounding approach: it anchors LLM plans in what the robot can actually perceive and do, preventing hallucinations from causing real-world failures.

The method, in detail — step by step, plain words but technical: the exact inputs, the model/method, the training or optimization setup, and the specific trick that makes it work.

Inputs: High-level task instruction (natural language), real-time perception of the environment (3D scene graph + object segmentation + spatial relationships), and a library of parameterized robot skills (navigate, grasp, manipulate, ask a visual question).

Core trick: Predicate Grounding + Monte Carlo Tree Search (MCTS)

  • LLM Decomposes the Task: The language model (Llama 3.1 8B/70B or GPT-4) reads the task and generates an abstract action sequence. For example, "pick up the cup on the table" becomes navigate(table) → checkgraspfeasibility → grasp(cup) → navigate(sink).
  • Predicate Grounding—Formal Verification: For each action, the LLM also generates preconditions in a formal predicates language (e.g., precondition(grasp): objectvisible AND notobstructed AND within_reach). Before the robot executes an action, the system checks whether those predicates are true in the current 3D scene graph. If a precondition fails, the action is blocked.
  • Embodied Monte Carlo Tree Search: When a naive LLM plan fails at any step, ConceptAgent does not give up. Instead, it treats the failed step as a node in a tree, generates alternative action sequences via MCTS (a search algorithm that explores action branches and scores them), and scores each branch using the LLM's judgment ("is this a sensible way to recover?"). The system backtracks and tries a different path.
  • Closed-Loop Feedback: After each action succeeds or fails, the perception system updates the 3D scene graph. If an action's expected outcome did not happen ("I tried to grasp the cup but failed—why?"), the system feeds that mismatch back to the LLM for replanning.
  • Skill Execution: Once a verified plan exists, the robot executes learned parametric skills (navigation via classical motion planning + LLM guidance, grasping via pre-trained grasp estimators, manipulation via trajectories). These skills accept high-level parameters from the LLM plan.

Why it works: By verifying preconditions before execution and using tree search to recover from failures, ConceptAgent avoids the problem where an LLM predicts an impossible action and the robot gets stuck. The formal grounding layer acts as a safety net.

GRACE: Generating Socially Appropriate Robot Actions Leveraging LLMs and Human Explanations

The big idea — first principles

The problem. A language model knows vacuum cleaners shouldn't run during sleep time, but doesn't know whether to vacuum before guests arrive or after they leave—social context isn't in its training data, and different people have different norms.

The approach. Classify each scenario as certain (everyone agrees on appropriateness) or uncertain (people disagree). For certain scenarios, trust the LLM's score directly. For uncertain ones, train a neural network to refine the score by learning from human explanations—what makes an action inappropriate in this home's specific context.

What's unique. Pairing LLM common sense with machine-learned human preferences via a conditional autoencoder, so the robot adapts not just to rules but to the actual preferences of the people sharing the space.

ICRA 2025 · 3 citations · socially-aware action generation

What it does

GRACE solves the problem of robots that behave socially awkwardly even when they know correct general rules. A household robot might know it shouldn't vacuum during a party, but not whether to vacuum before guests arrive or after they leave—rules that a person in that home would understand immediately. The system blends two knowledge sources: what a large language model (LLM) knows from common sense, and what the actual people in the home want based on their explanations. This is the socially-aware sub-approach: the robot generates actions that match both general social norms and specific person preferences.

The method, in detail

The system works in two parallel paths depending on how certain the LLM feels about a situation.

Step 1: Classify the scene as certain or uncertain. For each room scene (kitchen, living room, etc.) and each potential robot action (cleaning, serving, etc.), collect human scores (on a 1–5 scale) from multiple people. Compute the spread (variance) across those scores. If the human scores cluster tightly, the scene is "certain"—everyone agrees. If they scatter widely, it's "uncertain"—people disagree, so LLM common sense alone will not work. Use K-means++ clustering plus trained ML classifiers (SVM or Random Forest) to learn which scene features predict certainty.

Step 2: Query the LLM for initial scores. Convert the scene description (object locations, room type, time of day, number of people present) into plain English. Query an LLM (GPT-4o works best) separately for each potential action, asking for a social-appropriateness score. The model returns token probabilities; multiply each candidate score by its LLM confidence to compute a weighted score.

Step 3: For certain scenes, output the LLM score directly. The LLM knows what to do, so trust it.

Step 4: For uncertain scenes, refine the score using human preferences via a conditional autoencoder. This is the novel component. Build a neural network autoencoder with separate encoders for two inputs: (a) the LLM score and (b) a vector encoding of human explanations (like "the robot is too close to people" or "it's the person's busy time"). A shared encoder combines these into a latent representation. Then train two separate decoders: one that outputs a refined score (more aligned with what actual humans want), and another that generates an explanation describing why the robot should or shouldn't do that action. The key trick: condition both decoders on a binary flag. Set it to mode 0 to correct the LLM score; set it to mode 1 to generate an explanation from a score.

Training the autoencoder: Collect human annotations on MannersDB (750 scenes) and MannersDB+ (3,000 scenes with 9,238 human annotators). Each human labels up to nine explanation categories (busy vs. available, safe vs. dangerous, robot too close, etc.) as binary or three-way votes. Encode these as a 7-dimensional vector. Use nested 5-fold cross-validation, 200 epochs, batch size 32, ADAM optimizer (learning rate 1e-3). Loss balances MSE for scores and binary cross-entropy for explanations with α=0.6.

Output: A refined social-appropriateness score and optionally a generated explanation ("the robot shouldn't vacuum now because you're on a call").

AdaptBot: Combining LLM with Knowledge Graphs and Human Input for Generic-to-Specific Task Decomposition and Knowledge Refinement

The big idea — first principles

The problem. An LLM writes generic abstract steps ("fetch the kettle"), but the robot doesn't know if a kettle exists in this kitchen or where it's stored. The LLM's general knowledge doesn't match this specific environment's layout and constraints.

The approach. Check each LLM step against a knowledge graph recording facts about this kitchen (objects, locations, capabilities). When the KG can't answer—when it doesn't know where the kettle is—ask a human. Store that answer in the KG so future tasks benefit from it.

What's unique. Using the KG as a memory of this home's specifics that accumulates over time, so the initial cost of human feedback pays dividends as the robot builds domain knowledge for this particular space.

ICRA 2025 · 3 citations · grounding approach to task planning with knowledge graphs

What it does — 2-3 plain sentences

AdaptBot solves the problem that when a language model generates abstract action sequences (e.g., "prepare breakfast"), those plans often ignore domain-specific constraints and limitations of the particular robot, kitchen, or workspace. Rather than relying only on the LLM's general knowledge, AdaptBot checks each abstract step against a structured knowledge graph (a database of facts about objects, actions, and their preconditions specific to that domain), refines impossible steps when the KG reveals they won't work, and asks a human a targeted question when the KG cannot decide—then stores that answer for future tasks. This is a grounding approach: it grounds generic LLM plans in concrete environmental and agent-specific knowledge before the robot acts.

The method, in detail — step by step, plain words but technical

The system operates as a loop with three components working together:

Step 1: LLM generates a generic plan. The embodied agent receives a high-level instruction (e.g., "make tea"). It sends this to an LLM (GPT-3.5 in the implementation) along with a prompt that asks for a sequence of abstract actions. The LLM, trained on broad web knowledge, produces a reasonable sequence like ["fetch kettle", "fill kettle with water", "place kettle on stove", "wait", "pour into cup"]. These actions are abstract—they do not yet account for where the kettle actually is or whether the stove exists in this environment.

Step 2: Check each step against the Knowledge Graph. Before the robot executes any action, the system queries a domain-specific knowledge graph (a structured database built manually or learned from past interactions). The KG contains facts such as:

  • Object locations: kettle @ cabinet_bottom
  • Action preconditions: fillwater requires (object=kettle AND location=kitchensink)
  • Agent capabilities: robotarm canreach objects within 1.5m
  • State constraints: stove hasfuel=true AND thermostatset=high

For each abstract step, the system resolves it against these facts. For example, "fill kettle with water" becomes grounded as: the system looks up where the kettle is (cabinet_bottom), checks if the robot can reach that location, verifies the kitchen sink exists and is reachable, and confirms the kettle type matches what the fill action expects.

Step 3: Detect unresolvable steps and ask humans. When the KG cannot ground a step—for example, the location of a "saucepan" is not recorded, or the action "heat stove" has no known preconditions in this domain—the system does not guess. Instead, it generates a focused question for a human: "Where should I look for a saucepan?" or "What steps should I take to heat the stove?". The human provides an answer, which is then added to the KG. Crucially, this new fact is stored persistently, so the next time any task mentions a saucepan, the KG already knows.

Step 4: Refine the plan and execute. Once all steps are grounded and all queries answered, the robot executes the concrete action plan. If execution fails (e.g., a step was preconditioned on a state that changed), the system detects this, re-queries the KG to replan, and may ask the human again if needed.

The core trick: The system separates generic reasoning (LLM) from specific knowledge (KG). The LLM is fast and broad but hallucination-prone; the KG is narrow but accurate. Human feedback fills gaps in the KG only when needed, turning one-off questions into reusable knowledge. This is much cheaper than fine-tuning or retraining the LLM for each new task or domain.

Enhancing Robustness in Language-Driven Robotics: A Modular Approach to Failure Reduction

The big idea — first principles

The problem. Small language models run on edge devices but misstate what will be true after a step completes, leaving the robot in the wrong state for the next step—the model is locally wrong, breaking downstream actions even when each individual step is plausible.

The approach. Before execution, ask a forward model "if we do this step, what will definitely be true afterward?" Compare that ground truth to what the LLM said should happen. If there's a mismatch, reject the plan and replan. During execution, real-time sensor feedback catches mistakes and triggers correction immediately.

What's unique. Layering outcome verification and live feedback on top of the LLM so small models don't derail long task chains—the verification layer catches logical errors early, and feedback prevents divergence from compounding.

IROS · 3 citations · grounding

What it does

This work wraps a small language model in a corrective architecture that catches and fixes the model's planning mistakes before the robot executes them. Instead of trusting every step the model proposes, the system checks each one against what's actually physically possible, then recovers gracefully when something goes wrong anyway. This is the grounding sub-approach: the LLM's abstract steps are grounded in concrete, verified preconditions and feedback.

The method, in detail

Problem setup: Small language models run on edge devices (CPU/modest GPU) to decompose household tasks like "pick up the fork and put it in the drawer" into robot actions. But small models often make logical errors: they propose steps that the robot can't execute, or they misstate what should happen after a step completes, leaving the robot in the wrong state for the next step.

Core innovation: The system formalizes task planning as a goal-conditioned POMDP (partially observable Markov decision process). This mathematical framing lets you define two specific failure modes:

  • Subgoal mischaracterization: The LLM's plan says "grasp fork," but doesn't specify where the fork should be or what the robot's gripper should look like after—causing the next step ("insert into drawer") to fail because conditions aren't met.
  • Missing subgoals: The LLM's high-level steps don't map 1:1 to robot primitives; hidden setup steps are needed (e.g., moving the arm out of the way before opening a drawer).

The module:

  • Expected Outcomes Module: Before execution, for each LLM-proposed step, the system runs a forward model or simulation asking: "If we do action X, what will definitely be true afterward?" It compares this ground-truth outcome against what the LLM said should happen. If there's a mismatch (the LLM's next step requires the fork to be at position P, but executing step 1 leaves it at position Q), the planner rejects that sequence and re-plans.
  • Feedback Mechanism: When the robot actually tries an action, real-world sensors feed back what happened. If reality diverges from the expected outcome (gripper slip, object moved unexpectedly), the system detects this immediately and either corrects the next step or replans from the current state.
  • Local Inference: All computation happens on-device using small models (7B–13B parameters), not cloud calls.

Why it works: Rather than asking the LLM to be perfect, the system accepts that small models hallucinate, then builds a verification layer that catches errors before they propagate. Feedback allows one-shot recovery without full replanning in most cases.

TR-LLM: Integrating Trajectory Data for Scene-Aware LLM-Based Human Action Prediction

The big idea — first principles

The problem. An LLM predicting what a person will do next has only semantic knowledge ("kitchens are for cooking"), missing the spatial geometry—where people actually move in kitchens and toward which objects. LLM guesses can be wildly wrong about direction and distance.

The approach. Encode observed human movement as images (trajectories as heat maps), run a U-Net model trained on thousands of recorded trajectories to predict destination zones. Multiply that spatial prior by the LLM's semantic scores, refining the prediction.

What's unique. Spatial grounding via learned trajectory patterns (episodic memory of movement data) anchoring semantic knowledge, so geometry constrains what the LLM can predict.

IROS · 3 citations · memory-agent

What it does

A robot predicting human behavior receives two types of information: linguistic common sense from a large language model and precise geometric patterns from recorded human movement (trajectories). The system fuses them so that when an LLM would normally guess wrong due to poor spatial understanding, the trajectory component corrects it based on where people actually moved in similar situations. This is a memory-agent approach because the robot uses recorded past human trajectories as episodic memory to improve real-time prediction.

The method, in detail

Input: A scene description (room layout, objects, time of day, conversation snippets, action history), plus a sequence of observed human movement coordinates over the last ~3 seconds (trajectory).

Trajectory encoding: The past movement is converted into images. Each trajectory point becomes a 2D coordinate plotted on a blank 256×256 pixel canvas using Gaussian smoothing, creating a heat map of movement intensity. Time is encoded across multiple image channels: 90 past timesteps of coordinates, 90 timesteps of heading direction (which way the person was facing), and a binary scene map showing which floor areas are walkable. This 3-channel encoding feeds into a U-Net (a standard image segmentation model trained on 7,000+ real household trajectories from the LocoVR dataset).

U-Net trajectory model: Outputs a probability map showing which areas of the room are likely destinations. This map is overlaid with object locations, producing per-object destination scores: if the model predicts "person is moving toward the kitchen," objects in the kitchen get high scores.

LLM two-stage prompting: Stage 1 gives the LLM full scene context (time, person's location, recent conversation, known objects, what they've done so far) and asks it to brainstorm *all* plausible target objects and actions in free-form text. Stage 2 asks the LLM to rank those objects on a 4-tier scale (A=high probability, B=moderate, C=low, D=very low), which is converted to numerical scores (15, 10, 5, 1) and normalized into a probability distribution over objects.

Fusion: Multiply the LLM's object probabilities by the trajectory model's object scores. The result: a refined distribution that benefits from semantic knowledge (LLM) and spatial geometry (trajectory). A third LLM prompt then outputs the most likely action for that target object.

Training: The trajectory model is trained with Adam optimizer (learning rate 5e-5, batch size 16) on ground-truth destination labels for 100 epochs, using binary cross-entropy loss. On an NVIDIA RTX 4080, this takes 30–35 hours. The LLM component (GPT-4 or similar) is used zero-shot; no fine-tuning.

Key trick: The system gracefully degrades. If the scene description is incomplete or the LLM's prediction is wrong, the trajectory component's physical constraints act as a reality anchor—the model defaults to predicting motion toward areas where people actually tend to move, even if that contradicts initial semantic reasoning.

SayComply: Grounding Field Robotic Tasks in Operational Compliance Through Retrieval-Based Language Models

The big idea — first principles

The problem. A language model planning field inspection on a construction site doesn't know the site's actual safety rules, power line locations, or equipment specs—it makes confident guesses that violate regulations or put the robot at risk.

The approach. Organize the site's operational manuals, safety procedures, and equipment specs into a hierarchical database. Before the LLM writes each step, retrieve the relevant rules and procedures, passing them alongside the task description so the model sees written ground truth, not just its training.

What's unique. Tree-structured retrieval prioritizing compliance over task speed—the loss function weights safety heavily, forcing the LLM to prefer feasible-and-safe steps over ambitious-but-risky ones.

What it does

SayComply enables robots to plan complex multi-step field tasks while strictly adhering to domain-specific operational manuals and safety procedures. Rather than letting a large language model (LLM) invent task steps freely, the system grounds each step in the actual written rules—checking against hierarchical manuals for environmental procedures, robot capabilities, and site-specific safety constraints before committing to an action. This is the grounding sub-approach: the LLM decomposes a goal into steps, but continuously validates each step against external knowledge (in this case, retrieved operational compliance rules).

The method, in detail

The core insight is that naive LLM-based planners hallucinate infeasible steps because they lack access to domain-specific operational knowledge. SayComply organizes all knowledge into a hierarchical database (three levels, three knowledge domains):

Knowledge Organization:

  • Level 1 (Current State): Real-time observations of robot and environment (from sensors)
  • Level 2 (Site Instructions): Expert-written procedures specific to this location (e.g., "do not operate near power lines")
  • Level 3 (Reference Manuals): Generic safety and operational documents (e.g., equipment specs, general hazard protocols)

The three knowledge domains are: Environment (site layout, hazards), Operations (task procedures), and Embodiment (robot capabilities and constraints).

The Retrieval Process:

When a user gives a goal ("inspect the field for damage"), the system applies tree-based retrieval-augmented generation (RAG)—a custom retrieval strategy that outperforms standard RAG:

  • Convert user query into a vector embedding (dense representation)
  • For Level 2 & 3: Use cosine similarity to retrieve the top-2 most relevant site-specific instructions, then identify corresponding reference manuals
  • For Level 1: Ask the LLM to select which real-time databases are relevant (by title/description)
  • Concatenate all retrieved passages and send them alongside the user query to GPT-4

The Planning & Compliance Check:

The LLM receives:

  • User's high-level goal
  • Retrieved context from all three levels
  • Implicit instruction to generate executable steps

After each step generation, the system checks: "Do the preconditions of this step exist?" and "Is this step safe under the retrieved constraints?" If not, backtracking occurs and the planner re-searches the action space.

The Key Trick:

A weighted objective function heavily prioritizes compliance: the loss function includes both task-completion probability and compliance probability, with a weight β ≫ 1 on compliance. This forces the LLM to prefer safe feasible steps over ambitious but risky ones.

3DWG: 3D Weakly Supervised Visual Grounding via Category and Instance-Level Alignment

The big idea — first principles

The problem. A robot given "the chair to the left of the table" in natural language must find the exact 3D location in a point cloud. Existing systems need manual bounding box labels for every object instance to train, which doesn't scale.

The approach. Use two separate neural pathways: one that aligns *which type* of object is being described (category-level) by comparing scene embeddings against negative examples, and another that pins down *which specific instance* when multiples exist (instance-level) by reasoning about spatial relationships like "left of the table."

What's unique. Learning from scene-query pairs alone (no bounding boxes), letting the dual-branch design cleanly separate semantic matching from spatial disambiguation.

ICRA 2025 · 2 citations · grounding

What it does

This paper solves the grounding sub-approach: translating natural language object descriptions into exact 3D locations in point cloud scenes. Given a text query like "the chair to the left of the table," the system finds which 3D box in a sparse point cloud corresponds to that description—without needing manual bounding-box labels to train on. The core trick: separate the problem into two parallel branches: one that figures out *what type* of object is being described (category-level), and another that pinpoints *which specific instance* when multiple identical objects exist (instance-level).

The method, in detail

Inputs: A 3D point cloud (N points, each with 3D coordinates + features like color/normals) and a natural language query. No bounding boxes are provided during training—only the query-scene pairing.

Visual pathway: A pre-trained 3D object detector (e.g., VoxelNet or PointNet++) scans the scene and proposes m candidate object locations. Each proposal gets a dense feature vector (D-dimensional embedding) capturing its geometry and appearance.

Text pathway: A BERT language model processes the query. The special "[CLS]" token at the start becomes a single "sentence-level category knowledge" vector summarizing what type of object is wanted. Using a Scene Graph Parser, the system also extracts phrase-level embeddings—e.g., "chair" as one phrase, "left of the table" as another.

Fusion: A stack of transformer layers (multi-head attention) blends the proposal embeddings and text embeddings in shared space, producing aligned proposal representations, sentence vectors, and phrase vectors.

Category-level branch (solves ambiguity about *what* object to find):

  • Classify each proposal into likelihood of being a chair, table, lamp, etc. using an MLP.
  • Extract the target category word from the query (e.g., "chair").
  • Align the sentence-level category embedding against all proposals using cosine similarity, ranking proposals by how well their features match "a chair."
  • Negative category trick: Replace the target word in the query with a similar word (e.g., "stool" instead of "chair") and train the model to *reject* those proposals—this prevents misclassification within similar categories via an InfoNCE contrastive loss.

Instance-level branch (solves complexity when multiple chairs exist):

  • Compare each phrase embedding ("left of the table") against all proposals.
  • Rather than requiring bounding box supervision, use the query-scene pairing itself: proposals that make *spatial sense* given the text get boosted.
  • Extract spatial relationship phrases ("left of," "next to") and train a classifier to predict whether two objects have that relationship. If the query says "left of the table," proposals to the left of detected tables score higher.

Loss function and training: Four weighted losses combine: category sentence loss (λ₁=0.4), phrase negation loss (λ₂=0.005), phrase similarity loss (λ₃=0.005), and spatial relationship loss (λ₄=0.6). Standard supervised learning on scene-query pairs, but no manual bounding boxes—only the fact that a query applies to that scene.

Inference: Both branches output a confidence score for each proposal. At test time, the system picks the proposal with the highest confidence from whichever branch is more confident overall.

The core idea in code — the experience-and-emotion map

The emotion map is a continuous-valued spatial grid where each cell stores a Gaussian distribution that evolves in response to events. Here's how it's represented and updated:

Each cell (i, j) in the emotion grid stores the superposition of weighted Gaussian bumps placed at that cell:

  • When an event occurs at coordinate target_coord, the code adds a new Gaussian centered at that location
  • The Gaussian's covariance matrix encodes how far the emotional "blur" extends
  • The weight parameter normalizes overlapping Gaussians

    """Set initial parameters of emotion 1) covariance 2) initial weighting factor for occupied grid cells."""
    # For every free cell in the obstacle map, create a Gaussian with:
    # - covariance = identity matrix * self._cov_coef (default 8 pixels)
    # - weight = 1 / (number of overlapping Gaussians)
    for i, j in zip(zero_height_indices, zero_width_indices):

        mode.cov = np.identity(2) * self._cov_coef  # 2x2 covariance matrix

AdaptBot — code walkthrough

What the repo is / how you'd run it

This is a Python framework for grounding abstract LLM-generated task plans against a domain-specific knowledge graph (KG) represented as RDF triples. The system loops: ask an LLM for a task decomposition → validate each step against the KG → ask humans to fix what the KG cannot resolve → update the KG persistently → re-execute.
