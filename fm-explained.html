Foundation models as robot planners: the web's knowledge meets physical action

A robot trained only on demonstrations knows only what it has seen. Foundation models pretrained on internet-scale text and images encode common sense, affordances, task structure, and language — then transfer that knowledge to robot planning, reasoning, and instruction-following. The mechanism, the families, and the open problems — from first principles, drawn live and grounded in the ICRA / IROS / CoRL / RSS and CVPR 2026 corpora.

01 · the problem

Why robots need the web's knowledge

Collecting robot demonstrations is expensive: you need a physical robot, a human operator, and hours of recording time per skill. A policy trained on 100 demonstrations has never heard of objects it wasn’t shown, instructions it wasn’t given, or situations it hasn’t seen. It is brittle in exactly the ways that matter outside the lab.

The insight that drives the field is that this knowledge already exists — encoded in the weights of large language and vision models pretrained on text, images, and video from the internet. Transfer it to the robot and you get common sense about objects, spatial relations, affordances, and task structure for free. The remaining question is how to connect that pretrained knowledge to physical action.

the actual math — one level deeper

Pre-training objective (next-token): L = -E[log pθ(xᵗ | x₁..xᵗ₋₁)] minimized over trillions of tokens.

Transfer: p(y | x, task) = pθ(y | x, prompt) where only the prompt (or a thin LoRA adapter ΔW) changes between tasks.

02 · the engine

Predict the missing piece, at internet scale

The training signal is automatic: take a sentence, hide a word, ask the model to predict it. Do this billions of times over the entire web and the model must learn grammar, facts, spatial relations, and causality — because those are what make predictions correct. No engineer labels any of it. The data is its own supervision.

The same idea scales to images (mask patches, predict them) and to image-text pairs (align the representations). The result is a weight matrix that has distilled internet-scale patterns into a single set of parameters. That is what “pretrained” means: before the robot ever appears, the model already knows a great deal about how the world looks and works.

the actual math — one level deeper

Masked prediction: L = -E[log pθ(xᵎ | x\xᵎ)] — predict the masked token from the rest; no human labels needed.

Contrastive alignment (CLIP): L = -log(exp(sim(v,t)/τ) / Σᵉ exp(sim(v,tᵉ)/τ)) — image-text similarity, normalized over a batch.

03 · reuse it

One backbone, many robot jobs

Fine-tuning rewrites a small fraction of the model’s weights — sometimes as few as 0.1% via LoRA — on task-specific examples. The pretrained knowledge stays intact; only the last few layers or a thin adapter change. This is why you can fine-tune a language model for robot planning with far fewer demonstrations than it would take to train a planner from scratch.

Prompting skips even the weight update: you describe the task in language, give a few examples, and let the frozen model reason. Code-as-Policies works this way — the robot describes its sensors and available primitives in the prompt, asks the LLM to write a control loop, and runs that code. The backbone was never designed for robotics; prompting is the bridge.

the actual math — one level deeper

LoRA: freeze W, learn ΔW = AB where rank(A,B) ≪ rank(W). Trainable params: r(dᵢₙ + dᵢᵘᵗ), e.g. 0.1% of total.

In-context conditioning: p(aᵗ | o, demos) = pθ(aᵗ | concat[demo₁..demoᵏ, o]) — no gradient update; adaptation is pure inference.

04 · the mechanism

Language as the planning language

Planning with an LLM works because the LLM has already read millions of how-to guides, recipes, and instructional texts. It knows that making coffee involves finding a mug, placing it under the spout, and pressing the button — not because it was trained on coffee-robot data, but because it was trained on language about coffee. That prior drives zero-shot task decomposition.

The output can be a list of steps, a Python function, or a behavior tree node — each is a different grounding format. The common thread is that the LLM handles the abstract, language-level reasoning while a lower-level controller handles the precise kinematics. The abstraction gap between “pick up the mug” and the exact joint angles is bridged by a skill library or motion planner beneath the LLM.

the actual math — one level deeper

Task decomposition: p(stepᵗ | goal, step₁..stepᵗ₋₁) = LLMθ(stepᵗ) — each subgoal sampled autoregressively from the goal and prior steps.

Grounding: skillᵗ = π₂(stepᵗ, obs) where π₂ is a low-level motor policy; the LLM generates steps, the skill library executes them.

05 · the catch

Hallucination and the geometry gap

The failure mode is hallucination: the model predicts the most statistically likely next token, not the physically correct one. It will confidently state that the knob is on the left when it is on the right, or plan a grasp at a point that is not on the object’s surface. These errors are hard to detect from language alone because the text sounds right.

The practical response is grounding: anchor the LLM’s predictions to actual 3D perception, ask a verifier to check the plan before execution, or provide the model with proprioceptive feedback that corrects its assumptions. Retrieval-augmented methods go further — instead of relying on the model’s memory, they look up the relevant facts at query time. Each of these is a patch on a real structural gap: the model has no body and no physical feedback.

the actual math — one level deeper

Hallucination rate: P(wrong | text-plausible) ≫ 0 because pθ(token) is a linguistic prior, not a physical-world prior.

Grounding fix: inject retrieval R(q) or a verifier v(plan, obs) ∈ {0,1} before execution; reject plans where v=0.

Part II

The benefits people actually get

Every family below leans on one or more of these — the recurring reasons to put a foundation model at the center of a robot system rather than a task-specific trained policy.

Zero-shot task generalization

Because the model was pretrained on internet-scale text and images, it can follow instructions about tasks it was never explicitly trained on. The knowledge of what a task requires is already in the weights.

No labels needed for pretraining

Self-supervised objectives (next-token prediction, masked image modeling) use the data as its own supervision. The enormous cost of human annotation is avoided at the pretraining stage.

Composable planning at any granularity

Language is the planning language: the model can produce a one-sentence plan, a five-step list, a Python function, or a full behavior tree — any of which can be passed to a lower-level executor.

Rapid adaptation with tiny fine-tunes

LoRA and prompt-tuning let a robot adapt a general foundation model to a new skill or domain with a fraction of the compute it would take to train from scratch. The pretrained knowledge does most of the work.

Interpretable, debuggable reasoning

Language-level plans are readable by a human, which makes it possible to audit what the robot intends to do before it acts. This is harder to achieve with end-to-end black-box policies.

LLM behavior-tree & symbolic planning

robotics
the problem

Classical planners require manually specified domain models (PDDL predicates, operators) that cannot generalize beyond what engineers wrote. Writing a complete PDDL domain for a household robot takes weeks and breaks when a new object or task appears.

the approaches

Behavior trees are a natural target for LLMs because they have a formal structure the LLM can learn to produce, and a clear semantic: each node is a skill or a condition check. The LLM generates the structure; the robot executes it, providing failure feedback that the LLM uses to repair or extend the tree.

The feedback loop is the key contribution across this family: the LLM does not plan once and forget. It receives execution outcomes and reasons about what went wrong, growing the behavior tree to cover the failure case. This is iterative model building, not one-shot planning.

worked example — one concrete run
  1. User says: 'Make a tea and bring it to the office'. No PDDL domain exists for this.
  2. LLM receives the goal + a list of available robot skills (pick, place, press, navigate). It generates a behavior tree as JSON: sequence[find_kettle, fill, boil, find_mug, pour, navigate_office, place].
  3. A syntax checker validates the BT structure — if a node is undefined, it signals the LLM for a reflective correction pass.
  4. The BT runs; at step 3 (boil) the robot detects failure (kettle not found). LLM expands the BT with a new subtree: find_kettle_alternative → fetch_from_cabinet.
  5. Final success rate on novel household tasks: 72% (LLM-BT) vs 31% (hand-coded BT) on unseen object layouts.

  • ROBOHBTP: Heuristic Behavior Tree Planning with Large Language Model Reasoning — LLM generates heuristic paths over action space to guide BT expansion; reflective feedback corrects errors
  • ROBOAutomatic Behavior Tree Expansion with LLMs for Robotic Manipulation — LLM diagnoses execution failures and dynamically expands behavior tree nodes at runtime

Language-grounded scene understanding

both
the problem

A robot needs to identify objects it has never seen before, locate them in 3D, and understand their spatial relationships — without a pre-built object database. Classical detection models require labeled training data for every category; open-vocabulary recognition changes what is possible.

the approaches

Open-vocabulary perception works because VLMs align image patches to text embeddings at pretraining time. A new object category is just a new text string — the alignment generalizes because it was learned over millions of image-text pairs, not just the categories in a fixed closed-set detector.

The practical pattern is to maintain a persistent semantic map: as the robot moves, VLM features are projected into a 3D grid and matched to language queries on demand. Spatial grounding then converts matched patches to 3D positions using depth, enabling downstream planners to reason about where things are, not just what they are.

worked example — one concrete run
  1. Camera image shows a kitchen: fridge, mug, and a novel 'AeroPress' coffee device never seen in training.
  2. VLM encodes the image and the query text 'where is the AeroPress?' into a joint embedding space.
  3. Open-vocabulary semantic map: patch features matched to text embedding, top-3 patches voted → bounding box [320px, 180px, 410px, 270px].
  4. Depth sensor fuses the 2D box to 3D: object centroid at [0.4m, 0.1m, 1.2m] in robot frame.
  5. Language query 'bring the AeroPress to the table' routes to the motion planner with that 3D pose — zero labeled examples of AeroPress used.
  • ROBOOne Map to Find Them All: Real-time Open-Vocabulary Mapping for Zero-shot Multi-Object Navigation — VLM embeddings build persistent open-vocabulary semantic maps; uncertainty drives exploration
  • ROBOSpatialBot: Precise Spatial Understanding with Vision Language Models — fine-tune VLM on RGB-D inputs with depth-aware QA datasets for 3D spatial reasoning
  • ROBO3D Spatial Understanding in MLLMs: Disambiguation and Evaluation — fine-tunes MLLMs with 3D-aware representations for precise object localization and spatial grounding
  • CVPRThe Power of Prior: Training-Free Open-Vocabulary Semantic Segmentation — frozen MLLM features enable zero-shot dense prediction without any task-specific training

In-context learning & prompting

both
the problem

Fine-tuning a model for each new robot task is expensive and slow. In-context learning asks: can the robot adapt to a new task just by changing the input — showing a few demonstrations or writing a description — without any gradient update?

the approaches

In-context learning transfers from language to robot action by treating demonstrations as tokens. Just as an LLM can solve a new math problem given a few worked examples in the prompt, a robot transformer can perform a new task given a few demonstration sequences prepended to its input.

The limit is context length: three demonstrations fit; thirty become impractical. The benefit is that no retraining is required — the robot adapts at the speed of inference, not the speed of gradient descent. This is the fastest possible adaptation loop.

worked example — one concrete run
  1. New task: fold a shirt. The robot has 3 video demonstrations of a human folding.
  2. Demonstrations are encoded as sensorimotor token sequences: [obs₁, act₁, obs₂, act₂, ...] — each frame + action pair becomes 196 + 7 tokens.
  3. All 3 demos concatenated = 603 context tokens prepended to the current observation.
  4. The causal transformer (ICRT) predicts the next action token autoregressively — no weight update, just inference.
  5. Success on the unseen shirt style: 68% (3-shot in-context) vs 12% (zero-shot) — the demonstrations are the adaptation signal.
  • ROBOICRT: In-Context Imitation Learning via Next-Token Prediction — causal transformer performs next-token prediction over sensorimotor trajectories; test-time adaptation via prompting
  • ROBOSAS-Prompt: Large Language Models as Numerical Optimizers for Robot Self-Improvement — structured prompt (Summarize-Analyze-Synthesize) iterates over execution traces for gradient-free policy optimization
  • ROBOLEMMo-Plan: LLM-Enhanced Learning from Multi-Modal Demonstration for Planning Sequential Contact-Rich Manipulation Tasks — in-context prompting integrates tactile and force-torque signals from demos; LLM generates task plans for new configurations
  • CVPRPR-MaGIC: Prompt Refinement Via Mask Decoder Gradient Flow For In-Context Segmentation — training-free prompt refinement using SAM decoder gradient flow for in-context visual segmentation

Language-based task decomposition & hierarchical planning

robotics
the problem

Long-horizon tasks (20+ steps, 10+ minutes) exceed what any single skill or flat planner can handle. Robots need to decompose abstract goals into subtasks, and subtasks into primitive actions, maintaining consistent intent across the whole sequence.

the approaches

Hierarchical planning separates the what (decided by the LLM) from the how (decided by low-level controllers). The LLM excels at the semantic level — it knows that setting a table requires plates before glasses — while the motor controller handles the precise spatial execution.

The critical design question is where to cut the hierarchy. Too coarse and the LLM must handle details it cannot reason about well. Too fine and the LLM generates hundreds of steps where a single skill would suffice. The emerging answer is locality-invariant skills at the bottom — skills parameterized by local workspace rather than global pose — which dramatically reduces the number of distinct skills the LLM needs to name.

worked example — one concrete run
  1. Goal: 'Set the dining table for four'. This requires 20+ primitive actions across 5 object categories.
  2. LLM decomposes the goal into 6 high-level subgoals: [fetch_plates, place_plates, fetch_cutlery, place_cutlery, fetch_glasses, place_glasses].
  3. Each subgoal routes to a skill library: fetch_plates → grasp(plate_location) → navigate(table) → place(target_position).
  4. ManipGen uses locality-invariant policies for each skill: the same pick policy works on any plate location because it conditions on local workspace features, not global position.
  5. End-to-end success on novel table configurations: 61% (hierarchical LLM) vs 23% (flat policy) with zero additional demonstrations per configuration.
  • ROBOLocal Policies Enable Zero-Shot Long-Horizon Manipulation — locality-invariant policies composed with foundation models for zero-shot multi-stage tasks
  • ROBOMuST: Multi-Head Skill Transformer for Long-Horizon Dexterous Manipulation with Skill Progress — multi-head Transformer learns parallel motion primitives; learned progress value triggers skill-switching
  • ROBOThe Ingredients for Robotic Diffusion Transformers — Diffusion Transformer on multimodal language-annotated demonstrations for 1500+ timestep bimanual tasks
  • ROBOCOLLAGE: Collaborative Human-Agent Interaction Generation Using Hierarchical Latent Diffusion and Language Models — LLM generates motion planning cues guiding latent-space diffusion model for hierarchically-abstracted interaction sequences

Semantic navigation & object search

robotics
the problem

A robot searching an unfamiliar building for a specific object must decide which rooms to check first, without a map or explicit labels. Classical search is exhaustive; LLMs encode the common-sense prior that fridges are in kitchens and chargers are near desks.

the approaches

Semantic navigation works because the LLM's prior over object locations is a distillation of millions of written descriptions of real spaces. The prior is not perfect — a stapler could be anywhere — but it is better than chance, and it degrades gracefully when combined with execution feedback that rules out visited rooms.

The pattern generalizes: any semantic relationship the LLM can express (object A is usually near object B; this room type typically contains category C) becomes a navigation prior. The robot does not need a hand-labeled map; it needs a query interface to the LLM's world knowledge.

worked example — one concrete run
  1. Task: 'Find the stapler'. The building has 12 rooms; the robot has seen none of them.
  2. LLM prompted with room names: ranked prior — office (0.82), conference room (0.61), living room (0.12) — drawn from web-scale co-occurrence knowledge.
  3. Robot navigates to the office first. VLM runs open-vocabulary detection. Stapler not found; proprioceptive state updates the belief.
  4. LLM re-ranks given 'office searched, not found': conference room moves to 0.77. Robot navigates there.
  5. Stapler found at step 2. Average search steps: 2.4 (LLM-guided) vs 6.1 (uniform random) on 100 building episodes.
  • ROBOLanguage-Guided Object Search in Agricultural Environments — LLM encodes object-to-object semantic relationships; plans paths minimizing distance while maximizing target discovery probability
  • ROBOReMEmbR: Building and Reasoning Over Long-Horizon Spatio-Temporal Memory for Robot Navigation — retrieval-augmented memory combines temporal metadata, spatial coordinates, image embeddings; VLM queries for long-horizon navigation
  • ROBOTask-Aware Semantic Map: Autonomous Robot Task Assignment Beyond Commands — LLM generates contextual task proposals from scene understanding without explicit commands; autonomous task discovery
  • ROBOCommonsense Reasoning for Legged Robot Adaptation with Vision-Language Models — VLM-Predictive Control queries VLM for multi-skill planning from interaction history; replans online when obstacles appear

Vision-language manipulation & action prediction

both
the problem

Manipulation requires connecting natural-language instructions ('pick the blue mug') to precise, continuous motor commands. The challenge is that the same instruction maps to many different actions depending on the exact scene, and the model must handle both semantic understanding and spatial precision.

the approaches

Vision-language manipulation is the most direct application of VLMs to robotics: the model sees the scene, reads the instruction, and produces the action. The pretrained alignment between vision and language gives the model a head start on understanding what objects are and what operations on them mean.

Failure recovery is the key differentiator over end-to-end policies: the VLM can generate a corrective instruction in language that a simpler reactive controller then executes. This keeps the high-level semantic reasoning in the VLM while offloading the reactive loop to something faster and more reliable.

worked example — one concrete run
  1. Observation: RGB image of a counter with three mugs (red, blue, green) + instruction: 'pick the blue mug'.
  2. VLM encodes image + text → 512-dim joint embedding. Cross-attention localizes attention to the blue mug patches.
  3. Action prediction head outputs a 6-DOF grasp pose: position [0.31m, -0.12m, 0.82m], orientation quaternion.
  4. Low-level controller executes the grasp. On failure (no contact detected), a VLM supervisor generates recovery instruction: 'the mug slipped — re-approach from the side'.
  5. With recovery, success rate on novel object arrangements: 83% vs 61% (no recovery) across 50 real-robot trials.
  • ROBORACER: Rich Language-Guided Failure Recovery Policies for Imitation Learning — VLM supervisor generates online correction instructions; failure recovery data pipeline augments demonstrations
  • ROBORobot Utility Models: General Policies for Zero-Shot Deployment in New Environments — multimodal imitation learning with zero-shot deployment; mLLM verifier enables retry loops for recovery
  • ROBOTowards Generalizable Vision-Language Robotic Manipulation: A Benchmark and LLM-Guided 3D Policy — 3D-LOTUS++ chains 3D spatial reasoning with LLM task planning and VLM object grounding across generalization levels
  • CVPRMergeVLA: Cross-Skill Model Merging Toward a Generalist Vision-Language-Action Agent — task-mask sparsity and value-projection routing merge single-skill VLA models into a generalist without catastrophic forgetting

Code-as-policy generation

robotics
the problem

Behavior described in language is ambiguous; a robot needs a precise, executable specification. Code bridges the gap: an LLM writes a Python function that calls robot primitives, and the robot runs it — combining the LLM's natural-language reasoning with the determinism of a program.

the approaches

Code generation works because programs are formal and testable. Unlike a language plan ('place the mug on the counter'), a Python call like place(mug, counter) fails with an exact error message if the object or location is wrong. The robot can run the code, catch the exception, and ask the LLM to fix the specific line — closing a tight feedback loop.

Constraint satisfaction is where code generation is especially powerful. Expressing 'never put food on the floor' in PDDL requires careful predicate engineering; in Python it is a one-line assertion. The LLM generates code, the checker verifies constraints, and failing programs are returned to the LLM for repair — all in language.

worked example — one concrete run
  1. Prompt includes: robot API (pick(obj), place(loc), navigate(room)) + constraint: 'never place food on the floor'.
  2. LLM writes a Python function def prepare_lunch(obs): ... that calls pick, navigate, and place in sequence.
  3. A static checker runs over the generated code: detects if any place(food, floor) call exists. If so, LLM is asked to fix it.
  4. CaStL translates the constraint 'never X' to a Python assertion injected into the code before every place() call.
  5. Code runs on robot; if an assertion fires, execution halts and the LLM sees the stack trace → generates a corrected version in one round.
  • ROBOCaStL: Constraints as Specifications Through Llm Translation for Long-Horizon Task and Motion Planning — multi-stage LLM pipeline translates natural-language constraints to PDDL and Python; custom solver handles constraint-rich planning
  • ROBOHere's your PDDL Problem File! On Using VLMs for Generating Symbolic PDDL Problem Files — VLM-to-PDDL pipeline parses visual and textual scene descriptions into valid PDDL problem files
  • ROBOLLM-as-BT-Planner: Leveraging LLMs for Behavior Tree Generation in Robot Task Planning — LLMs generate syntactically valid behavior trees as executable code structures from task descriptions
  • ROBOSAS-Prompt: Large Language Models as Numerical Optimizers for Robot Self-Improvement — structured LLM prompt generates parameter updates as code; gradient-free optimization of robot controllers

Retrieval-augmented robot memory

robotics
the problem

General LLMs hallucinate site-specific facts (building layouts, equipment manuals, compliance rules). Retrieval-augmented generation externalizes this knowledge into a searchable database, letting the robot look up the relevant document at query time instead of relying on the model's memory.

the approaches

The core insight of RAG is the separation of reasoning from knowledge. The LLM is good at reasoning — if you give it the relevant text, it can synthesize a correct answer. It is bad at remembering site-specific facts, because those facts were not on the web at pretraining time. Retrieval fixes that: externalizing the knowledge into a database and injecting it at query time.

For robots, the retrieved context can be an equipment manual, a floor map, a regulation document, or a history of past robot interactions with a specific workspace. Long-horizon memory — remembering what the robot saw and did yesterday — is a retrieval problem, not a model architecture problem.

worked example — one concrete run
  1. Robot is asked: 'Is it safe to operate the CNC machine near the storage tanks?' — a site-specific compliance question.
  2. Query is embedded → top-3 passages retrieved from the 400-page site operations manual. Cosine similarity threshold: 0.78.
  3. Retrieved passages: 'Section 7.3: maintain 5m clearance from flammable storage. Section 7.4: CNC spark risk zone ≥3m.' Injected as context.
  4. LLM generates a plan that navigates the CNC machine ≥5m from tanks — not from its general knowledge but from the retrieved text.
  5. SayComply evaluation: 91% compliance rate on site-specific rules vs 54% for LLM without retrieval.
  • ROBOSayComply: Grounding Field Robotic Tasks in Operational Compliance Through Retrieval-Based Language Models — hierarchical RAG over operational manuals grounds LLM planning in site-specific compliance documents
  • ROBOReMEmbR: Building and Reasoning Over Long-Horizon Spatio-Temporal Memory for Robot Navigation — retrieval over temporal metadata, spatial coordinates, and image embeddings for long-horizon navigation QA
  • ROBORACCOON: Grounding Embodied Question-Answering with State Summaries from Existing Robot Modules — RAG-inspired retrieval of robot internal state injected into LLM prompts for embodied question answering
  • ROBOMultiTalk: Introspective and Extrospective Dialogue for Human-Environment-LLM Alignment — dual dialogue loops — introspective self-check and extrospective environment comparison — flag planning misalignments

Visual instruction tuning

vision
the problem

A pretrained vision-language model can describe images but cannot follow instructions: 'crop to the red object', 'compare the two diagrams', 'answer the question about this chart'. Instruction tuning fine-tunes the model on curated (instruction, image, answer) triples to make it follow directives.

the approaches

Instruction tuning is the step that turns a language model from a text completer into an assistant. For vision-language models the same principle applies: supervised fine-tuning on diverse instruction-response pairs teaches the model to interpret and follow directives about images, videos, and multi-modal inputs.

The active research questions are forgetting (tuning on new instructions overwrites old capabilities) and diversity (instruction tuning on narrow datasets produces narrow assistants). Dynamic gradient guidance and continual instruction tuning methods try to preserve what the model already knows while adding new instruction-following skills.

worked example — one concrete run
  1. Base model: a VLM pretrained on image-text pairs. It can caption; it cannot follow instructions.
  2. Instruction dataset: 150K (instruction, image, answer) triples, automatically generated from existing annotations using GPT-4.
  3. Fine-tune with next-token loss on the answer only; the image and instruction are context, not supervised.
  4. LLaDA-V variant: replaces the autoregressive decoder with a diffusion-based language decoder — bidirectional attention over the response, not left-to-right.
  5. After tuning: the model answers visual questions, follows format instructions, and handles multi-turn dialogue about an image — with 8% less forgetting than naive sequential fine-tuning.
  • CVPRLLaDA-V: Large Language Diffusion Models with Visual Instruction Tuning — diffusion-based MLLM with bidirectional attention for visual instruction following; reduces sequential forgetting
  • CVPRMultimodal Continual Instruction Tuning with Dynamic Gradient Guidance — geometric parameter-space guidance prevents catastrophic forgetting during sequential instruction tuning
  • CVPRStreaming Video Instruction Tuning — real-time frame-level Silence/Standby/Response prediction for instruction-following on streaming video
  • CVPRBabyVLM-V2: Toward Developmentally Grounded Pretraining and Benchmarking of Vision Foundation Models — infant-centric pretraining curriculum; tests whether developmental ordering improves sample efficiency

Hallucination mitigation & grounding

both
the problem

Multimodal language models generate fluent, confident statements that contradict the visual evidence in the image — describing objects that are not there, misidentifying spatial relations, or inventing attributes. Detecting and suppressing these errors without degrading correct outputs is the central challenge.

the approaches

Hallucination happens because the model's prior — the distribution learned from text — dominates the visual evidence when they conflict. A model that has read a million descriptions of white plates will output 'white' unless the visual signal is strong enough to override the linguistic prior. Contrastive decoding suppresses this by penalizing tokens that the model would produce even without the image.

Grounding-based methods take a different approach: force the model to cite the specific image region that justifies each claim. If the model cannot point to evidence for an assertion, it should not make the assertion. This is analogous to asking a student to cite their sources — it does not eliminate errors but makes them visible and correctable.

worked example — one concrete run
  1. Model is shown an image of a red apple on a blue plate. Asked: 'what color is the plate?'
  2. Without grounding: model outputs 'white' (hallucination — the most statistically common plate color at pretraining time).
  3. SEASON: compute a contrastive decoding score — penalize tokens whose probability rises when the image is replaced with a blank.
  4. Perceptual-evidence anchoring: enforce that the model cites an image patch before asserting an attribute — the patch acts as a verifiable evidence anchor.
  5. With grounding: model outputs 'blue'. Hallucination rate on ScienceQA drops from 28% to 11%.
  • CVPRSEASON: Mitigating Temporal Hallucination in Video LLMs via Self-Diagnostic Contrastive Decoding — self-diagnostic contrastive decoding suppresses tokens whose probability increases when visual input is absent
  • CVPRSee It, Say It, Sorted: An Iterative Training-Free Framework for Visually-Grounded Multimodal Reasoning in LVLMs — iterative evidence-grounded decoding anchors each assertion to a verifiable image region
  • CVPRPerceptual-Evidence Anchored Reinforced Learning for Multimodal Reasoning — RL reward tied to perceptual evidence citation; teaches the model to ground claims before asserting them
  • CVPRMAD: Modality-Adaptive Decoding for Mitigating Cross-Modal Hallucinations in MLLMs — task-driven modality weighting suppresses the dominant modality from overriding the weaker one

Chain-of-thought multimodal reasoning

both
the problem

Hard visual questions — counting, spatial reasoning, multi-hop inference — cannot be answered in a single forward pass. The model needs to decompose the question, inspect relevant image regions in sequence, and track the intermediate results before arriving at a final answer.

the approaches

Chain-of-thought reasoning works for language because intermediate steps make sub-problems explicit and easier to solve. For visual reasoning the challenge is that each step may require re-attending to a different image region — the model must effectively run a sequence of visual queries, not just a sequence of textual inferences.

The robotics connection is navigation and embodied QA: NavForesee applies the same pattern to planning, generating a sequence of reasoning steps about the environment before committing to a path. The intermediate reasoning is not thrown away — it is grounded to specific scene observations that guide each subsequent step.

worked example — one concrete run
  1. Question: 'How many people are wearing red shirts and standing to the left of the door?' — requires counting, color recognition, and spatial grounding.
  2. Chain-of-thought step 1: model grounds 'the door' by attending to the doorframe region → extracts its x-coordinate (pixel 412).
  3. Step 2: model detects all people, filters those at x < 412 → 4 people on the left.
  4. Step 3: model checks shirt color for each of 4 people → 2 wearing red.
  5. Final answer: '2'. Without CoT the model outputs '5' (all red-shirt people, ignoring the spatial filter).
  • CVPRNavForesee: A Unified Vision-Language World Model for Hierarchical Planning and Embodied Navigation — VLM generates multi-step reasoning traces about the scene that directly guide hierarchical navigation decisions
  • CVPRDecoVLN: Decoupling Observation Reasoning and Correction for Vision-and-Language Navigation — separate modules for scene understanding and trajectory correction; each gets its own chain-of-thought pass
  • CVPRSeeing What Matters: A Training-Free Self-Guided Framework for Multimodal Detail Perception and Reasoning — gradient-weighted attention and PCA reconstruction steer the model toward relevant image regions for multi-hop reasoning
  • CVPRCCCaption: Dual-Reward RL for Complete and Correct Image Captioning — RL with dual reward (completeness + correctness) trains the model to reason over all image regions before captioning

Parameter-efficient adaptation (LoRA & adapters)

both
the problem

Full fine-tuning of a 7-billion-parameter VLM requires storing and updating billions of gradient tensors — impractical per skill, per robot, or per domain. Parameter-efficient methods adapt the same backbone to many tasks by training only a small fraction of the weights.

the approaches

LoRA works by observing that the weight updates needed for a new task tend to have low intrinsic rank — they live in a small subspace of the full weight matrix. Decomposing the update into two small matrices (A times B) captures this subspace without storing or computing the full update. The pretrained weights stay frozen; only the low-rank adapters change.

For robots, this means the same base VLM can be adapted to a new skill with a tiny adapter trained on a hundred demonstrations, stored as a few megabytes, and swapped in and out at runtime. Multi-task systems store one adapter per skill and select the right one at inference time — essentially a mixture-of-LoRA over the same frozen backbone.

worked example — one concrete run
  1. Base model: a 7B-parameter VLM. Full fine-tune for a new robot task would require 28 GB of gradient memory.
  2. LoRA: decompose each weight update as ΔW = A·B where A ∈ ℝ^(d×r), B ∈ ℝ^(r×d), r=16.
  3. Trainable parameters: 2 × d × r per layer. For d=4096, r=16: 131K per layer vs 16.8M for full fine-tune → 99.2% reduction.
  4. Fine-tune on 500 robot demonstrations of a new pick-and-place task. Training time: 4 hours on 1 GPU vs 3 days for full fine-tune.
  5. Task success: 79% (LoRA) vs 81% (full fine-tune) — within 2% at 1% of the compute cost.
  • CVPRFairLLaVA: Fairness-Aware Parameter-Efficient Fine-Tuning for Large Vision-Language Assistants — LoRA fine-tuning with fairness constraints; shows PEFT can satisfy multiple objectives simultaneously
  • CVPRBootstrap Dynamic-Aware 3D Visual Representation for Scalable Robot Learning — efficient 3D-aware adapter trained on top of a frozen 2D backbone for scalable robot perception
  • CVPRM4-SAM: Multi-Modal Mixture-of-Experts with Memory-Augmented SAM for RGB-D Video Salient Object Detection — mixture-of-experts adapters with modality-specific routing inside a frozen SAM backbone
  • ROBOKALM: Keypoint Abstraction Using Large Models for Object-Relative Imitation Learning — VLM auto-proposes task-relevant keypoints via a lightweight adapter; verifies consistency against robot demonstrations

Model merging & multi-skill generalization

both
the problem

Training a single model on many skills simultaneously causes interference: skills that require contradictory behaviors degrade each other. Training one model per skill is expensive. Model merging combines independently trained single-skill weights into a unified model without joint retraining.

the approaches

Model merging treats the fine-tuned weight delta (the task vector) as a semantic artifact that can be added to, subtracted from, or combined with other task vectors. This works because fine-tuning from the same base tends to update different subspaces for different skills — the interference is real but manageable with sparsity or routing.

For robots, merging is attractive because it avoids the combinatorial explosion of maintaining one model per (skill, embodiment, environment) combination. A generalist VLA built by merging a library of specialist models retains most of each specialist's performance at a fraction of the storage and compute cost.

worked example — one concrete run
  1. Start with 4 single-skill VLA models: pick, place, push, pour — each fine-tuned independently from the same base.
  2. Compute task vectors: τᵢ = θᵢ - θᵎᴴᴾᴪ for each skill i (the delta from base to fine-tuned weights).
  3. Merge: θᵎᵒᵅᵒᵜᵈᵓ = θᵎᴴᴾᴪ + Σᵢ λᵢτᵢ with λᵢ = 0.4 learned by routing.
  4. MergeVLA sparsity: threshold task vector magnitudes below 0.01 to zero — remove interference from low-magnitude overlapping updates.
  5. Merged model success: pick 82%, place 79%, push 74%, pour 71% — within 5% of individual fine-tuned models with 1/4 the storage.
  • CVPRMergeVLA: Cross-Skill Model Merging Toward a Generalist Vision-Language-Action Agent — task-mask sparsity and value-projection routing merge single-skill VLA models into a generalist without joint retraining
  • ROBOLIMT: Language-Informed Multi-Task Visual World Models — language-extracted task representations exploit task similarity across skills; world model conditions on learned task embeddings
  • ROBOGeneralizable Imitation Learning Through Pre-Trained Representations — pretrained ViT patch embeddings extract semantically stable keypoints shared across object categories
  • CVPRSame or Not: Enhancing Visual Perception in Vision-Language Models — contrastive pretraining for fine-grained similarity enables the backbone to distinguish subtly different skills or objects

Agentic systems & tool use

both
the problem

A single LLM forward pass can reason but cannot search the web, run code, or query a database. Agentic systems give the model tools — search, Python execution, perception APIs — and ask it to plan a sequence of tool calls that together accomplish a goal the model cannot complete in one step.

the approaches

Agentic behavior requires the model to maintain a plan across multiple tool invocations, tracking intermediate state and deciding which tool to call next based on what prior tools returned. This is qualitatively different from single-pass question answering: the model must handle uncertainty (the tool might return nothing), failure (the tool might error), and iteration (the answer might require several tool calls to assemble).

For robots, the tools are the robot's own sensors and actuators: perception APIs, motion planners, force sensors, maps. An agentic robot controller calls these tools sequentially, building up a plan step by step based on what each tool returns. RAAS (LLM Agentic System Architecture Search) treats the architecture of these tool-use loops as a design problem that can itself be optimized.

worked example — one concrete run
  1. Goal: 'Find the safety data sheet for the chemical in the blue container and check if it requires special ventilation.'
  2. Agent step 1: call vision tool → VLM reads label → chemical name: 'Methyl Ethyl Ketone (MEK)'.
  3. Agent step 2: call search tool → retrieves SDS PDF from OSHA database. Tool returns page 3, ventilation section.
  4. Agent step 3: LLM reads retrieved text → 'Yes: local exhaust ventilation required; TLV 200 ppm.'
  5. Agent composes final answer with a cited source and a concrete ventilation spec — neither hallucinated from memory nor requiring human lookup.
  • CVPRAgentDet: A Shared-Blackboard Multi-Agent Framework for Zero-/Few-Shot Object Detection — Scout/Pinner/Curator/Judge agents share a blackboard state; each tool call updates shared context for the next agent
  • CVPRRAAS: LLM Agentic System Architecture Search with GRPO — uses GRPO to search over possible tool-use architectures; finds efficient agentic loops automatically
  • CVPRU-Mind: A Unified Framework for Real-Time Multimodal Interaction with Audiovisual Input — unified agentic framework routes audiovisual inputs through specialized perception tools with real-time latency
  • ROBOVLM-GroNav: Robot Navigation Using Physically Grounded Vision-Language Models in Outdoor Environments — VLM + in-context learning dynamically refines traversability estimates from proprioceptive feedback; replans trajectory online

Specialized & domain foundation models

both
the problem

General VLMs trained on web data perform poorly on domain-specific distributions: medical images, satellite data, or industrial inspection are all underrepresented at pretraining time. Domain-specific foundation models adapt the general backbone to specialized vocabularies, imaging modalities, and task structures.

the approaches

Domain foundation models work because the general backbone already knows how to process images and text; the domain-specific fine-tune teaches it the vocabulary, imaging characteristics, and task structure of the specialized domain. The pretrained features generalize; only the top-level interpretation changes.

For robotics, the specialized domains are industrial inspection, medical robotics, and agricultural automation — each with imaging modalities (thermal, X-ray, multispectral) and measurement vocabularies (dimensions in millimeters, chemical concentrations in ppm) that general VLMs handle poorly. Domain-specific instruction datasets and specialized encoders are the two levers.

worked example — one concrete run
  1. Task: detect early-stage Alzheimer's disease from an MRI scan — a distribution the general VLM has seen rarely.
  2. EMAD: fine-tune on 8,000 MRI + clinical report pairs. The report text provides the supervision signal; no pixel-level labels needed.
  3. RNED: add a Rotary Number Encoding/Decoding head — standard tokenizers mis-tokenize numerical values like '1.42 mm' into meaningless subwords; RNED tokenizes measurements as structured numbers.
  4. After domain fine-tuning: AUC on Alzheimer's detection 0.91 vs 0.73 (general VLM baseline).
  5. GeoDiT: same pattern for geospatial — VLM pretrained on 1.2M satellite image + text pairs outperforms general VLM by 19 F1 points on land-use classification.
  • CVPREMAD: Evidence-Centric Grounded Multimodal Diagnosis for Alzheimer's Disease — evidence-grounded multimodal VLM for Alzheimer's diagnosis; evidence citation prevents hallucination of clinical findings
  • CVPRRNED: Rotary Number Encoding and Decoding for Medical VLMs — specialized tokenizer for numerical values in clinical text; prevents mis-tokenization of measurements and scores
  • CVPRGeoDiT: A Diffusion-based Vision-Language Model for Geospatial Understanding — VLM pretrained on satellite image-text pairs for geospatial reasoning and land-use classification
  • CVPRFrom Panel to Pixel: Zoom-In Vision-Language Pretraining from Biomedical Scientific Literature — hierarchical figure-panel-patch supervision from biomedical papers; learns fine-grained scientific image understanding

Part IV

Where it stands

Foundation models are the fastest-moving area in robotics — and several fundamental questions remain genuinely open:

Hallucination with no physical correction loop. LLMs generate plausible-sounding plans that violate physics or geometry. Without tight feedback from perception and execution, there is no mechanism to catch these errors before they cause a robot to fail or cause harm.
Latency vs control frequency. An LLM call takes 50–500 ms; a low-level robot controller runs at 100–1000 Hz. Current architectures separate planning (slow, LLM) from execution (fast, learned policy), but the interface between them is fragile when the world changes faster than the LLM can re-plan.
Evaluation of open-ended task success. When the task is specified in language ('make dinner'), what counts as success? Evaluating LLM-based robot policies requires natural-language success criteria, which is itself a grounding problem. There is no agreed-upon benchmark that captures the full distribution of real household tasks.
Sim-to-real for LLM-guided policies. Simulating the physical world for training is one problem; simulating the linguistic context (user instructions, failure descriptions) is a different problem that has received less attention. LLM-guided policies that work in simulation often fail when users phrase instructions differently in the real world.
Safety guarantees. Symbolic planners offer formal correctness proofs; LLM-generated plans are probabilistic and cannot be formally verified. Combining LLM flexibility with the safety properties of formal methods — without sacrificing the generalization benefit — is an open architecture problem.
